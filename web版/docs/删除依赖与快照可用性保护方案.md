# 删除依赖与快照可用性保护方案

## 1. 结论先行（TL;DR）

| # | 结论 | 判定 |
|---|---|---|
| 1 | 备份任务 → 仓库为**强依赖**：建任务、跑任务都要求仓库存在且有地址 | ✅ 有守卫（404 / 运行期失败） |
| 2 | 仓库 → rclone conf 段为**强依赖**：`rclone:remote:path` 里的 remote 必须始终在册 | ❌ **无守卫**（删段不检查引用） |
| 3 | 仓库删除有「default 禁删 / 有任务 / 有活跃作业」三道门 | ✅ 已实现 |
| 4 | 仓库被**其他仓库任务当镜像仓**引用，删除时不做检查 | ❌ 缺口 |
| 5 | 快照数据不随记录删除，但**应用侧入口随仓库行消失** | ⚠️ 数据在、打不开 |

**核心判断**：系统保护了「任务没删就想删仓库」，却没保护「任务还在、仓库还在，却把仓库的地基（rclone 远端）删了」。后者的表现是**删除成功、无报错**，之后快照列表 / 文件浏览 / 恢复全部失败——比直接报错更危险。

一句话口径：**不是禁止删除，而是让删除先看见依赖、看见后果、并留得下退路。**

> v1.2 已把这句话落成 15 条可执行决策（§9），P0 范围与验收见 §8。

## 2. 依赖链现状取证

### 2.1 依赖方向

```
备份任务(backup_tasks)
   └─ repo_id ──→ 仓库(repos: url / host_tag)
                    ├─ url = rclone:<remote>:<path> ──→ rclone.conf 段（type=rclone）
                    ├─ 后端凭据 cred.<repo_id>.*（config 表，AES 加密）
                    └─ 密码文件 passfile_path(repo_id)（restic 仓库口令）
                                  │
快照数据（restic repo）────────────┘ 只能经「仓库行 + 口令 + 凭据」到达
```

快照数据**不在本应用数据库内**，只存在于 url 指向的位置（本地目录 / S3 / WebDAV / rclone 远端）。数据库持有的只是**指针 + 钥匙**。

| 操作 | 端点 | 现有校验 | 缺口 |

## 3. 逐场景后果与可恢复性

| 场景 | 当前行为 | 快照能否打开/恢复 | 可恢复条件 |
|---|---|---|---|
| **A. 任务还在 → 删仓库** | 409 `REPO_NOT_EMPTY` 拒绝 | 不受影响 | 无需恢复 |
| **B. 任务还在 → 删 rclone 段** | **允许** | **否**：restic 解析不了 remote，列表/浏览/恢复全失败，备份任务下次执行失败 | 重建**同名** remote + 同类型 + 同凭据；若为 crypt 段，还需**同 crypt 密码 + 同 filename_encryption/encoding**，否则**永久不可读** |
| **C. 先删任务 → 再删仓库（不 purge）** | 允许 | 否（应用侧）：`current_repo_id` 404 / url 缺失 | 重建**同 id + 同 url**；密码文件仍在（未 purge）→ 立即恢复；`cred.<id>.*` 已被清除，非 rclone 后端需重填凭据 |
| **D. 同 C 但 `purge_disk=true`（本地）** | 允许，rmtree 内容 + 删密码文件 | **永久否** | 无（不可逆） |
| **E. 删镜像仓（被别仓任务引用）** | 允许 | 该仓已复制快照孤立 | 重建同 id/url；另需修引用方任务的 mirror 配置 |
| **F. 删 crypt 段（其底层 remote 仍在）** | 允许 | 否：加密层消失，密文无法还原 | 重建同名 crypt 段 + **同密码/同文件名策略**；密码丢失 = 永久 |

**关键差异**：C 是「可救」，D 是「不可救」，B/F 是「取决于你是否还记得密码」。三者目前在 UI 上是同一种确认门，用户无法区分。

### 3.1 现有删除文案的缺陷（实证）

`frontend/src/i18n/locales/zh-CN.ts:845-846` 原文：

> 「确定删除该仓库？删除后将一并移除该仓库的凭据、任务历史记录与运行日志，操作不可撤销；**仓库内的 restic 快照不受影响**。……」

「不受影响」字面成立（数据没删），但会诱导用户理解为**之后还能用**。实际是：数据在、入口没了。

**v1.2 定稿文案（D7）**——按分支两套，彻底删掉「不受影响」：

| 分支 | 中文终稿 | 英文终稿 | 门 |
|---|---|---|---|
| 默认归档 | 「将归档该仓库，{days} 天内可原样恢复。快照数据不会被删除，归档期内仍可浏览与恢复；凭据与密码文件在归档期内保留，期满后自动清除。」+「该仓库当前有 {m} 个快照」 | `Archiving keeps it recoverable for {days} days. Snapshot data is not deleted and stays browsable during that period; credentials and the password file are kept until expiry.` | 单次确认（无关键词） |
| 勾 `purge_disk`（仅本地 FS） | 「将销毁该仓库的目录内容与密码文件，**不可归档、不可恢复**，快照数据将永久丢失。」 | `This destroys the repository contents and password file. It cannot be archived or restored, and snapshots are permanently lost.` | 输入仓库名确认 |

> **不再显示「任务数」**：`ensure_deletable` 要求 `tasks=0` 才允许删除（`repo_repo.py:208-213`），故删除门里的任务数**恒为 0**，没有信息量；动态统计只保留「快照数」与「被镜像引用数」。

## 4. 防范措施设计（四层）

### L1 删除前置校验（后端，零副作用，先校验后清理）

沿用 `repos.py:494-498` 既有纪律：**校验 → 清理 → 删行**，拒绝即零损失。

1. **rclone 段删除加引用扫描**（D1/D2/D3/D4）
   - 扫 `repos.url` 形如 `rclone:<remote>:`（**带尾冒号 + remote 完整相等**，避免 `foo` 误命中 `foobar`）；
   - 扫 conf 内 `type=crypt` 且 `remote=<remote>:...` 的段（**传递依赖**，复用 `classify_crypt_remote`）；
   - 命中 → 409 `RCLONE_REMOTE_IN_USE`，`data` 形如 `{remote, repos:[{id,name}], dependent_remotes:[name]}`；
   - **落点 = 路由层**（`routers/repos.py` 先查后调 `delete()`），服务层不接触 DB（守 A1 红线）；
   - **P0 只阻断 + 给清单，不做「批量改指向」**（改指向留 P2）——前端把 blockers 渲染成可跳转条目，用户自行改仓库 URL；
   - **crypt 段不再要求「强制导出才允许删」**：改为删除时**自动归档整段配置**（见 L4-2），blokers 额外标 `crypt: true` + 提示「密码丢失将永久不可读」。

2. **仓库删除加镜像引用扫描**（D5）
   - `backup_tasks.mirror_repo_ids` 是 JSON 文本列（`task_repo.py:216` 写入、`:372` `_load_list` 读取）→ 用 **`json_each` 精确匹配**，不用 `LIKE '%"id"%'`（避免前缀/子串误命中与转义问题）；
   - 命中 → 409 `REPO_IN_USE_AS_MIRROR`，`data` 带引用任务清单 `[{id,name}]`；
   - 落点：`repo_repo.py:194-216` `ensure_deletable` 内扩展，与既有三门同批；
   - **全量生效**（不区分存量/新建）；P1 开工前先跑一次**只读体检**统计影响面（仅 SELECT，零改动）。

3. **快照计数缓存失效补齐**（D11）
   - 仓库删除成功后同时调 `invalidate_snapshot_catalog()`（现仅 `invalidate_repo_status_cache()`，`repos.py:523`）；
   - rclone 段删除后同样失效（可能连带影响其他仓库）；
   - 归档 / 恢复 / 释放 ID 路径同样失效。

### L2 依赖阻断与受控解除

- 409 统一携带 `blockers`（类型 / id / 名称），前端直接渲染「先处理这些」。
- 两条受控出口，默认关闭：
  - **改指向**（P2）：把引用该 remote 的仓库 url 批量切到新 remote（remote 重命名场景），再允许删段；
  - **强删**（P2）：显式 `force=true` + 关键词确认，仅限「快照确认可放弃」。
- **不提供静默强删**：crypt 段删除且密码丢失是不可逆的。

### L3 删除提示（前端分级，让后果可见）

| 位置 | 现状 | 改造（v1.2） |
|---|---|---|
| rclone 段删除（`components/settings/RcloneConfigPanel.vue:285-299`，`NPopconfirm`） | 一句话确认 + OAuth 加重提示 | 列表接口增 `used_by_repos`；`>0` 时**禁用删除按钮** + 展示引用清单；`=0` 才走 popconfirm（OAuth 加重提示保留）；文案注明「删除后整段配置将归档 {365} 天，可一键恢复」 |
| 仓库删除（`pages/repo/index.vue:2192-2210` `ConfirmGate` + `zh-CN.ts:845-848`） | 静态文案，含误导性「快照不受影响」 | 按 §3.1 两档文案 + 动态「快照数 {m} / 被镜像引用 {k}」；归档分支无关键词，purge 分支关键词 = 仓库名 |
| 任务删除 | 无特别提示 | 明示「不删除快照；快照仅经 forget/prune 删除」 |

**快照数口径 = 仓库内快照总条数**（D6，`len(records)`），**不是** `counts_by_tag` 的 tag 求和——后者只统计带 tag 的快照，手工 `restic backup` 或被 `tag --remove` 摘掉 task tag 的会漏计，会让用户低估后果。

**为什么能直接复用 TTL 缓存（机制说明）**

1. **缓存结构**：模块级 `_tag_counts_cache = {repo_id: (时间戳, {tag: 计数}|None, ttl, 连续失败数)}`（`snapshot_catalog.py:36-37`）。**key 是仓库 id**，一次探测服务该仓库的全部任务。
2. **一次探测、Python 侧分组**：单次 `restic snapshots --json` → 按 tag 分组计数，不逐任务跑 restic（避免 N 次子进程）。命中缓存直接返回；未命中加锁后**双检**再探，防并发重复探测（`:82-89`）。
3. **失败退避**：不入正常 TTL，改 `30→60→120→240→300s` 指数退避（`:102-108`），期间返回 `None`。**`None` = 不可知 ≠ 0**（`:15-17`），UI 显示「不可知」，避免误告诉用户「从没备过」。
4. **删除门怎么用**：打开对话框 → 查一次；命中缓存 0 成本，冷缓存也就一次探测（`SNAPSHOT_COUNT_TIMEOUT_SECONDS=5s` 上限）。冷缓存期间显示「统计中」，**不阻塞删除门**；失败显示「不可知」。

### L4 快照可用性保护

1. **仓库软删除 / 归档（替代硬删行）**（D8/D15）
   - 迁移 `0009_repo_archive.sql`：`repos.deleted_at TEXT NULL` + 索引；
   - **`DELETE /api/repos/{repo_id}` 默认语义改为「归档」**，彻底删除需 `hard=1`（D8）；
   - 归档 = 置 `deleted_at`，列表默认过滤；快照页/归档页提供只读浏览与恢复；
   - **归档期间不清 `cred.<id>.*`、不删密码文件**（现 `repos.py:502-510` 立即清凭据，是「重加即失忆」的根因）；
   - **default 仓库禁止归档**（D15，沿用 `repo_repo.py:196` 现硬禁）——default 是兜底，归档会打崩 `current_repo_id` 回落逻辑；
   - 彻底删除 = 独立动作，二次确认 + 关键词。

2. **rclone 段删除自动归档 + tombstone**（D3/D10）
   - **自动归档（新增，替代原「强制导出」）**：`delete()` 在 `rclone_config.py:549` 已经 `_dump_sections()` 把整段读进内存，落库仅多一条 INSERT——**成本近乎为零**；
   - 归档内容：该段**完整 key-value**（`type`/`url`/`user`/`pass`/`password`/`password2`/`filename_encryption`…）。这些值是 rclone **混淆态**、非明文，但**等价于凭据**；
   - **红线约束（S3）**：API **永不回**归档值（只回 `has_config: true` + 键名列表）；日志不写；审计 detail 只记 `remote`/`type`/键数；归档表**排除在配置导出之外**；
   - 恢复 = 一键**写回**该段 + 重新探测可达；crypt 段恢复后快照立即可读（前提：底层 remote 仍在，即场景 F 而非 B）；
   - **保留期 365 天**（D3 定案，与 tombstone 同档）；到期自动清除并记审计；
   - 列表标注「已删除，曾被 N 个仓库使用」，给出恢复指引。

3. **可访问性巡检**
   - 定期对每个仓库做 `cat config` 探测（复用 E30 探测链路），失败时仓库卡片红色告警「仓库不可达，快照暂不可恢复」；
   - 避免用户点进快照页才吃 500。

4. **远程仓库数据清理的诚实边界**
   - `purge_disk` 仅本地 FS 生效（`repos.py:527-535` 已明示 422）；远程后端只能给桶内路径 + 操作指引，并由应用记审计。

5. **`purge_disk` 与归档互斥（v1.1 订正）**
   - `purge_disk` 做两件事且**均不可逆**：清空仓库目录内容 + 删密码文件（`repos.py:527-535`）。**口令一删，即使数据残留也打不开**——恢复能力归零。
   - 因此与归档**互斥**：勾选 `purge_disk` 时归档选项自动关闭并禁用，提示「数据将被销毁，归档恢复能力失效」；不允许「既归档又删数据」这种自相矛盾的承诺。
   - 勾选后的最终语义：**数据销毁 + 仅留墓碑**（名称/地址/类型/删除时间，**不含密码与凭据**），记录上标「数据已销毁，不可恢复」。
   - 该勾选**仅本地 FS 出现**（`frontend/src/pages/repo/index.vue:2206`）；远程后端传 `purge_disk` → 422（`repos.py:534`），即远程仓库永远是「数据保留 + 需人工清」，天然落回归档路线。

6. **归档页（新页面，D13/D16/D17）**
   - 入口：**数据导航组新页** `/archive`（`BasicLayout.vue:105-110` 的 `group-data` 当前只有 `snapshots`，正好空着一个位置）；
   - **三段 Tab（复用共用 `SegmentedTabs`，与审计页「日志 / 保留策略」同形态）**：

     | 分区 | 内容 | 对应保留期键 |
     |---|---|---|

## 5. 归档记录生命周期（三档）

| 阶段 | 保留内容 | 能力 | ID 占用 |
|---|---|---|---|
| 第 0–30 天（活跃归档期） | 元数据 + 密码文件 + 凭据 | 一键原样恢复，快照立即可读 | 占用（防同名误撞旧数据） |
| 第 31–365 天（墓碑期） | 仅元数据（名称/地址/类型/归档时间/归档时快照数） | 恢复需重新提供密码与凭据 | 占用，可手动释放 |
| 第 366 天后 | 元数据可清 | 无自助恢复 | 释放 |

### 5.1 `purge_disk` 路径（唯一破坏性分支，v1.1）

| 勾选状态 | 快照数据 | 记录 | 能否恢复 |
|---|---|---|---|
| 不勾（默认） | 保留 | 归档 30 天 → 墓碑 → 清除 | 能，一键恢复 |
| 勾 `purge_disk`（仅本地 FS） | **销毁**（目录内容 + 密码文件） | 墓碑（不含密码/凭据） | **不能** |

- 二者**互斥**：勾 `purge_disk` 时归档选项自动关闭并禁用（见 §4 L4-5）；不允许「既归档又删数据」。
- 远程仓库无此分支：前端不显示勾选（`repo/index.vue:2206`），后端传参 422（`repos.py:534`）——远程只能「归档保留 + 人工清理」。
- **保留天数全部可配置（D16）**：`retention.repo_archive_days`（默认 30）、`retention.repo_tombstone_days`（默认 365）、`retention.rclone_archive_days`（默认 365）；`<=0` = 不启用自动清理（永久保留），与 `retention.audit_days`/`retention.audit_archive_days` **同一语义与同一套 `_resolve_days(key, default)` 读取方式**；配置入口在**归档页第三分区「保留策略」**（对齐审计页把保留策略并入本页的既有做法，2026-10-26 从设置页迁入，不再回设置页）。
- **手动通道始终开放**：「立即彻底删除」与「释放 ID」互不影响，均二次确认。
- **释放 ID（D9）**：强制输入仓库名确认 + 文案「旧快照将无法再与本应用关联」+ 审计 `repo.id_release`；**不自动删数据**（守 §6 双轨红线）。
- **为什么不是永久**：一条记录仅几百字节，数据库不在乎；真正的成本是 ①ID 被永久占用，同名仓库永远建不出来；②密码文件长期躺在磁盘上。
- **为什么不是立即删**：30 天是「手滑后悔窗口」，也是唯一能让数据「零成本恢复」的窗口。

## 6. 快照数据处理（双轨，唯一出口）

| 轨道 | 归宿 |
|---|---|
| **归档记录**（DB） | 30 天 → 365 天 → 清除，逐档降级 |
| **快照数据**（repo 存储） | **始终保留**，唯一出口是用户手动清理（不可逆） |

**硬性红线**：归档只清「怎么找回」，**永不动数据**；清理数据必须是独立动作、独立确认、独立审计，两者绝不耦合。

合法减少快照的两条路径：

1. **forget + prune**（日常正路）：forget 只摘快照记录，`prune` 才回收数据块；保留策略（keep-last/daily/weekly…）即此路径。
2. **整仓清空**（极端）：`purge_disk=true`，仅本地 FS。

防空间膨胀不靠自动删，靠三件事：

- **看得见**：归档页展示地址、归档时间、归档时快照数；本地仓库报磁盘占用。
- **点得动**：「清理数据」按钮独立于「删记录」，确认门 + 关键词，文案明确不可恢复。
- **留得下痕**：清理动作写审计（谁 / 何时 / 哪个仓库）。

### 11.2 偏差（如实登记，均有理由；处置见 11.3）

1. **「强删（force 绕过引用）」未实现**——P2 原列 L2 受控出口含「`force=true` + 关键词」。落地时判断：绕过引用检查等于把 P0 的硬阻断作废，且 rclone 段强删后可恢复性归零；改为**只提供「改指向」这条正路**（`POST /api/rclone/config/{remote}/repoint`），引用不解决就删不掉。若后续确需强删，须先补审计动作与二次确认设计。

   **处置结论（owner 2026-11-01 裁定为永久设计，非待办）**：force 强删**永久不做**。「有引用但想删段」的死锁正路是**先 repoint 再删**（`repoint` 已覆盖该场景）；若将来出现 repoint 也覆盖不了的情形，须另立方案并先补审计动作与二次确认设计，不在本文开口子。
2. **「改指向」审计动作独立于 S6 清单**——新增 `repo.repoint`（纯配置写入、无删除副作用，与 `repo.update` 同性质），故危险清单仍为 **23 项**，未因该动作扩项。

   **处置结论（owner 2026-11-01 裁定：维持不入清单，23 项不变）**：依据是与 `repo.update`（同样可改仓库 url）同类先例一致，且 repoint 非删除、可逆、带 `repo.repoint` 审计留痕；两个「改 url」入口若一个算危险一个不算，反而制造口径分裂。
3. **可访问性巡检为「按需探测」而非独立后台巡检任务**——复用 E30 `GET /api/repos/{id}/status`（30s 服务端缓存）与仓库页逐行查询，未新增 `maintenance-repo-health` 调度任务：页面打开即探测，结论直接驱动横幅与行标签。若需「无人访问也持续探测」，可后续把同一探测挂进维护任务域（不改前端）。

   **处置结论（owner 2026-11-01 裁定：维持按需 + 记产品待办）**：维持现状不做独立巡检。无人值守探测会把「探测哪些仓 / 多久一次 / 失败是否告警」三件事一并拖入，而通知域尚未定型；页面驱动在有人使用场景下已足够。待通知/告警需求定型后，把同一探测挂进 `maintenance-*` 域即可（不改前端），届时另立工单。
