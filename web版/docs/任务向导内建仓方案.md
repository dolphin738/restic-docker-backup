# 任务向导内建仓方案（A 方案）

> 版本：**v0.1**（2026-10-28 初稿）
> 状态：**设计待确认，未开工**（本文只做现状取证与落地规划，零代码改动；§10 裁决后进入实施）
> 定位：**不改关系模型**（仍是「仓库下挂任务」，一仓可多任务），只把「每个任务配一座独立仓库」变成**创建向导里一次就能走完的默认路径**。与《暂缓存档-任务多仓库C方案-2026-10-28.md》的关系见 §0.2。
> 关联：架构 §4.7/§4.8（repos / backup_tasks）、§5.1 E35（任务创建）、E39–E44（仓库管理端点）、《云端仓库安全基线》v1.4（`keys/` 与 init 后中性化）。
> 证据基线：`main @ 82326b4`。行号以该提交为准，代码演进后以符号名复核。

---

## 0. 定位

### 0.1 一句话

今天要「一个任务一座独立仓库」，用户得跨两个页面走 6 步（仓库页建仓 → 设密码 → 初始化 → 测试 → 切当前仓库 → 任务向导建任务）；本方案把这 6 步压进**任务向导第③步**，一次走完，且不引入任何新的数据模型约束。

### 0.2 与 C 方案的关系

| | A 方案（本文） | C 方案（暂缓存档） |
|---|---|---|
| 关系模型 | 不变（任务归属一个仓，一仓可多任务） | 反转（任务不归属仓，可配多目的地） |
| 数据迁移 | **零迁移** | 关联表 + 三段迁移 |
| 目的 | 降低「一任务一仓」的操作成本 | 改变「任务与仓的关系」语义 |
| 互斥性 | 不互斥：A 可先做，C 若将来上，A 的建仓子表单可直接复用为「目的地编组器」 | — |

结论：**A 是低风险的前置改善，先做 A 不挡 C 的路**；反之若先做 C，A 的这部分工作会被 destination editor 吸收。

## 1. 目标与非目标

**目标**

1. 向导第③步支持「新建一座专属仓库」并就地完成 建仓 → 设密码 → 录凭据 → 初始化 → 连通测试；
2. 新建完成后自动把当前仓库切到新仓，任务直接落到新仓（`POST /api/repos/{id}/backup-tasks` 是 repo 作用域，必须切）；
3. 用户中断向导时，已建的仓库**可见、可撤销、可续用**，不产生"看不见的半成品"；
4. 全程零新增数据库列、零迁移。

**非目标**

1. 不强制 1:1（不加唯一索引、不拒绝「同仓第二任务」）；
2. 不改 `backup_tasks` / `jobs` / `repos` 表结构；
3. 不改任务 API 作用域（仍 `/api/repos/{repo_id}/backup-tasks`）；
4. 不解决凭据加密的多仓隔离缺口（§2.3 记录，另案）。

## 2. 现状取证

### 2.1 创建路径现状：跨两个页面 6 步

| 步 | 动作 | 落点 |
|---|---|---|
| 1 | 仓库页「新建仓库」→ 填类型/地址/凭据 → 落库 | `pages/repo/index.vue:459-511`（`openCreate` / `runCreate`） |
| 2 | 设密码（行内按钮，密码文件缺失才出现） | `POST /api/repos/{id}/password`（`routers/repos.py:885-960`） |
| 3 | 初始化（在"未初始化"结论上给入口，走 **rebuild**） | `POST /api/repos/{id}/rebuild`（`repos.py:963-1102`） |
| 4 | 测试连接 | `POST /api/repos/{id}/test`（`repos.py:608-658`） |
| 5 | 切当前仓库 | `ui.setCurrentRepoId(id)`（`stores/ui.ts:85-92`） |
| 6 | 任务向导建任务 | `components/TaskWizard.vue` 五步 |

第 3 步之所以走 rebuild，是因为**全仓没有独立的 init 端点**：`grep '"init"'` 的唯一调用点在 `repos.py:1050`（rebuild 内部）。

### 2.2 关键发现一：rebuild 不能承担「新建后初始化」

`rebuild_repo` 先 `_repo_local_path(repo.url)` 判断本地后端，**远程后端直接 422**（`repos.py:995-1001`），因为它的语义是「清空目录内容再 init」。而新建仓库最需要 init 的场景恰恰是 s3 / b2 / azure / sftp 这些**远程后端**（本地目录直接 `restic init` 也能建，但远程没有"清空"这回事）。

结论：**必须新增独立 init 端点**，语义为「在空/未初始化的仓库上执行 `restic init`」，不做任何清空动作，因此对远程后端同样安全可用。

### 2.3 关键发现二：凭据加密是**全站单例**，密钥源固定为 default 仓库密码

`main.py:211` 只构造一个密码学实例：

```python
credential_crypto = CredentialCrypto(settings, repo_id=DEFAULT_REPO_ID)   # 固定 default
encryption = EncryptionState(credential_crypto)
config_repo = ConfigRepo(db, encryption=encryption)
```

`CredentialCrypto._derive_key()` 的密钥 = HKDF(**default 仓库密码文件**, info 含 `"default"`)，`ConfigRepo._maybe_encrypt` 对所有敏感键共用这一实例（`config_repo.py:163-169`）。

由此得到两条与实施方案直接相关的结论：

1. **写 `cred.{新仓id}.*` 不依赖新仓密码文件**，只依赖 **default 仓库密码文件存在**。所以"建仓 → 设密码 → 录凭据"的严格顺序**不是**必须的；真正的 422 前提是 `CredentialKeyUnavailableError`（`errors.py:173-184`，422），即 default 密码文件缺失/不可读。
2. **多仓库凭据共享同一把密钥**（HKDF info 恒 `"default"`），`enc:v2` 声称的"跨仓库密钥隔离"目前**并未生效**——`crypto.py:97-105` 的 docstring 自己也写着「当前仅 default；R-023 多仓库时按仓库派生」，多仓库落地时没跟进。这是既有安全缺口，**不在本方案范围**，但必须在 §8 风险登记，避免被当成 A 方案引入的问题。

### 2.4 关键发现三：向导第③步是只读 + 硬门禁

- 只读展示 `ui.currentRepoId` 的 url，无任何选择/新建入口（`TaskWizard.vue:856-871`）；
- 新建任务必须"测试通过"才能离开第③步：`step3Blocked = step === 3 && !isEdit && !testPassed`（`TaskWizard.vue:665`）；
- 镜像目的地候选来自 `listRepos()`，并按「url 非空 + `passfile_status=configured`」禁用（`:323-331`）。

推论：**未初始化的仓库无法通过第③步**（`test_repo` 走 `restic cat config`，未初始化必失败），所以"在向导内建仓"如果不带 init，用户会卡死在门禁上——这就是第 3 步（init）必须内嵌的原因。

### 2.5 关键发现四：草稿不记仓库

`DRAFT_KEY = 'restic-web:wizard-draft:v1'` 的 `DraftEnvelope` 只有 `{step, form, savedAt}`（`TaskWizard.vue:157-163`）。若建仓发生在第③步而草稿不记仓库 id，用户刷新/重进会**重复建仓**（同一 id 409）或**留下孤儿仓库**。

## 3. 目标流程（用户旅程）

第③步给三个选项，**默认选中"新建专属仓库"**：

| 选项 | 说明 |
|---|---|
| A. 新建专属仓库（默认） | 内嵌建仓子表单，走完即用 |
| B. 使用当前仓库 | 现状行为（只读展示 + 测试连接） |
| C. 复用其他已有仓库 | 从 `listRepos()` 选一个（等价于切换当前仓库），并提示「该仓已承载 N 个任务」 |

### 3.1 内嵌建仓的时序（前端编排，后端各步幂等）

```
① GET  /api/repos/_new_id                     预填 id（r<YYMMDD>-xxxxxx，可留空）
② POST /api/repos            {id?, name, url, host_tag}
③ POST /api/repos/{id}/password  {}           生成强随机密码，明文一次性回显（SecretReveal）
④ PUT  /api/config           cred.{id}.*      凭据多键写入（422 CREDENTIAL_KEY_UNAVAILABLE → 提示先配 default 密码）
⑤ POST /api/repos/{id}/init  （新增端点）      restic init + keys/ 身份中性化
⑥ POST /api/repos/{id}/test                   自动跑一次，ok 才算通过（复用第③步门禁）
⑦ ui.setCurrentRepoId(id) + draft.provisionedRepoId = id
   → 第④⑤步照旧；第⑤步提交时落到新仓
```

顺序约束说明（据 §2.3 修正）：③ 与 ④ 的先后**不是**安全约束，先设密码只是为了让"仓库自身可用"（init 需要密码文件，⑤ 依赖 ③）；④ 与 ⑤ 可互换，但建议 ④ 在 ⑤ 前——init 失败时凭据已录好，重试 init 无需重填。

### 3.2 每步失败的可恢复性（幂等契约）

| 步 | 失败 | 处理 |
|---|---|---|
| ② | 409 id 重复 | 提示换 id，或「检测到你已建过该仓库 → 直接使用它」跳 ③ |
| ③ | 422 密码文件已存在 | 视为已完成（跳过），继续 ④ |
| ④ | 422 密钥不可用 | 明确文案：`默认仓库密码文件缺失 —— 先到仓库页为 default 设置密码`（这是唯一真实阻断，见 §2.3） |
| ⑤ | 409 已初始化 | 视为成功（幂等），继续 ⑥ |
| ⑤ | 远端不可达 / 桶不存在 | 映射可操作文案（restic 退出码 + 最后一行），保留已建仓库供重试 |
| ⑥ | 测试失败 | 按 `failure_kind` 分流（凭据错 / 网络 / 未初始化），给"重试 / 回仓库页处理"两个出口 |

## 4. 后端改造

### 4.1 新增端点 `POST /api/repos/{repo_id}/init`

```
POST /api/repos/{repo_id}/init          （无请求体）
→ 200 {ok: true, already: bool, key_neutralized: bool}
```

语义与约束：

| 项 | 规则 |
|---|---|
| 前置 | 仓库存在（否则 404 `REPO_NOT_FOUND`）；`url` 非空（否则 422）；密码文件 `configured`（否则 422「请先设置仓库密码」） |
| 幂等 | 先 `restic cat config` 探测；已连通 → 200 `{already: true}` 直接返回（**不重复 init**） |
| 执行 | `restic.build("init")`（S2 白名单内已有 `init`，`constants.py:16`）+ `REPO_INIT_TIMEOUT_SECONDS`（120s） |
| 后置 | `neutralize_repo_key(...)`（`repos.py:1072-1078` 同款，失败只记日志不阻断） |
| 后端类型 | **不限制**——本地与远程后端均可（与 rebuild 的关键差异，见 §2.2） |
| 冲突 | 该仓库有 running/pending job → 409 `JOB_CONFLICT`（复用 rebuild 的检查，`repos.py:1003-1006`） |
| 审计 | 新增动作 `repo.init`（detail：`{already, key_neutralized}`，无凭据/无口令） |
| 缓存 | `invalidate_repo_status_cache()`（init 改变可连性） |

### 4.2 复用抽取

`rebuild_repo` 内 1039-1077 行的「init + keys 中性化」抽成模块级私有函数：

```python
async def _restic_init(request, repo_id: str, repo_url: str, password_file: Path, *,
                       log_prefix: str = "restic-init-") -> None
```

rebuild 与新端点共用；rebuild 的第 1 步（清空目录）保持私有，不进公共函数——**清空是 rebuild 独有的破坏性语义**，不能被 init 端点误用。

### 4.3 审计与错误码

| 项 | 内容 |
|---|---|
| 审计动作 | `AUDIT_REPO_INIT = "repo.init"`（新增常量）。**不进 S6 危险 20 项清单**（init 不删数据，与 `repo.rebuild` 同档：有审计但不在危险枚举） |
| 错误码 | 不新增；复用 `REPO_NOT_FOUND`(404) / `VALIDATION_ERROR`(422) / `JOB_CONFLICT`(409) / `RESTIC_FAILED`(500) |
| 文档同步 | 架构 §5.1 端点表加 E52（或 R-023 段内追加）+ §11 追溯矩阵；无需改 §5.0 错误码表 |

## 5. 前端改造

### 5.1 第③步改为三态

`TaskWizard.vue:856-911` 由「只读 + 测试 + 镜像多选」改为：

```
[ 新建专属仓库 (默认) ] [ 使用当前仓库 ] [ 复用其他仓库 ]
─────────────────────────────────────────────
（新建分支）仓库类型 / 地址字段组 / 凭据 / 仓库名 / host_tag
            → [ 一键创建并初始化 ]  （loading，最长 120s，分步展示进度文案）
（当前分支）只读 url + 状态 + 测试按钮（现状原样）
（其他分支）仓库下拉（含"已承载 N 个任务"提示）+ 选中即切当前仓库
─────────────────────────────────────────────
镜像目的地多选（保持现状，`:897-910`）
```

默认选"新建"的触发条件：当前仓库 `GET /api/repos/{id}/backup-tasks` 已有 ≥1 个任务（读到就默认新建并提示「当前仓库已被 N 个任务共用」）；否则默认"使用当前仓库"（不打扰首任务用户）。

### 5.2 建仓子表单：抽常量，不抽整页

| 抽什么 | 从哪抽 | 抽到哪 |
|---|---|---|
| `CRED_FIELDS`（按类型列出的凭据键） | `pages/repo/index.vue:843-...` | `utils/repoCredentials.ts`（新） |
| URL 组译 | **已抽好**：`utils/repoUrl.ts:87 composeRepoUrl` | 直接复用 |
| 类型预设 | `repo/index.vue` 内的 `REPO_TYPE_PRESETS` 同源 | 同上文件 |

**不抽 `RepoForm.vue`**：`repo/index.vue` 2593 行、表单与列表/编辑/删除/重建深度耦合，整页抽组件的回归面远大于收益（P5 起多次拆分已证明代价）。向导内只做**精简版表单**（建仓必需字段：类型 / 地址 / 凭据 / 名称 / host_tag），字段模型复用同一 `RepoUrlFields` 接口。

### 5.3 草稿扩展（必须）

```ts
interface DraftEnvelope {
  step: number
  form: TaskFormState
  savedAt: string
  provisionedRepoId?: string   // 新增：本次向导内已建成的仓库
}
```

- `restoreDraft()` / `discardDraft()` 要处理该字段：恢复草稿时若 `provisionedRepoId` 存在 → 第③步直接显示"已创建 rXXX（点击切换/撤销）"，**不再重复建仓**；
- 键名保持 `v1`，新字段可选（旧草稿无该字段 → 视为未建仓，向后兼容）。

### 5.4 中断、回滚与孤儿仓库

| 场景 | 处理 |
|---|---|
| 用户点"取消/返回"离开向导 | 若本次已建仓 → 提示「已创建仓库 rXXX 但尚未创建任务」：①继续编辑 ②撤销（删除该仓库）③保留（稍后在仓库页处理） |
| 撤销 | `DELETE /api/repos/{id}`（无任务引用时可删；`purge_disk` 由用户勾选，默认不删磁盘） |
| 全局仓库被切走 | 记录 `previousRepoId`，撤销/取消时 `setCurrentRepoId(previousRepoId)` 回滚；保留则维持新仓（用户预期"这个仓是我的了"） |
| 多标签页/刷新 | `provisionedRepoId` 在草稿里 → 重进不重复建仓 |

## 7. 验收断言（DoD）

**后端**

1. `POST /repos/{id}/init`：未设密码 → 422；url 空 → 422；已初始化 → 200 `already=true` 且**不重复执行 init**（日志/耗时断言）；有活跃 job → 409。
2. **远程后端可 init**（s3/memory 或 mock：断言不走 `_repo_local_path` 分支）——与 rebuild 的 422 形成对照用例。
3. init 成功后 `GET /repos/{id}/test` 返回 ok=true；`keys/` 已完成身份中性化（沿用 `test_repo_keys.py` 的断言方式）。
4. 审计出现 `repo.init`，detail 不含口令/凭据。
5. `verify_redlines.sh` 19 项全绿；新端点挂 `require_session` + 写方法过 Origin 校验。

**前端**

6. 向导第③步默认态正确：当前仓有任务 → 默认"新建"；无任务 → 默认"使用当前仓库"。
7. 内嵌建仓全链路（含密码一次性回显、凭据写入、init、自动测试）一次通过。
8. 建仓后任务落到新仓：`POST` 的路径 repo_id == 新建仓库 id（断言 `task.repo_id`）。
9. 中断向导 → 提示三选项；"撤销"后仓库消失且其他任务不受影响。
10. 草稿恢复不重复建仓（带 `provisionedRepoId` 的草稿恢复后第③步呈"已创建"态）。
11. `pnpm test`（i18n parity / naive-imports）、typecheck、build 全绿。

## 8. 风险与处置

| # | 风险 | 影响 | 处置 |
|---|---|---|---|
| 1 | **孤儿仓库**（建仓后放弃向导） | 仓库列表里出现无任务的仓 | §5.4 三选项提示 + 撤销；仓库页本就支持删除 |
| 2 | **全局仓库被切走** | 用户离开向导后发现"当前仓库变了" | 记录 `previousRepoId`，取消即回滚 |
| 3 | init 耗时长（远端新建桶/大延迟） | UI 卡 30-120s | 分步进度文案 + 120s 超时（`REPO_INIT_TIMEOUT_SECONDS`）+ 超时后保留仓库可重试 |
| 4 | default 密码文件缺失 | 录凭据 422，用户不知为何 | §3.2 专用文案指路（唯一真实阻断，见 §2.3） |
| 5 | **凭据加密多仓未隔离**（既有缺口） | 任一仓密码泄露不直接影响，但 default 密码是全局单点 | 本文不改，登记为独立技术债（建议另案按 `cred.{repo_id}.*` 前缀派生实例） |
| 6 | 精简版表单与仓库页表单漂移 | 两处字段不一致 | 共用 `utils/repoUrl.ts` + `utils/repoCredentials.ts` 两个纯模块；差异只在布局 |
| 7 | 与 C 方案重叠返工 | C 若先上，A 的建仓子表单要迁进 destination editor | 组件边界按"可嵌入"设计（props 输入、事件输出，不依赖向导 store） |
