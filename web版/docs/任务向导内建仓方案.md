## 1. 目标与非目标

**目标**

1. 向导第一步支持「新建一座专属仓库」开关，开则内嵌完成 建仓 → 设密码 → 录凭据 → 初始化 → 连通测试；
2. 新建完成后自动把当前仓库切到新仓，任务直接落到新仓（`POST /api/repos/{id}/backup-tasks` 是 repo 作用域，必须切）；
3. 用户中断向导时，已建的仓库**可见、可撤销、可续用**，不产生"看不见的半成品"；
4. 全程零新增数据库列、零迁移、零后端改动。

**非目标**

1. 不强制 1:1（不加唯一索引、不拒绝「同仓第二任务」）；
2. 不改 `backup_tasks` / `jobs` / `repos` 表结构；
3. 不改任务 API 作用域（仍 `/api/repos/{repo_id}/backup-tasks`）。

## 2. 现状取证

### 2.1 创建路径现状：跨两个页面 6 步

| 步 | 动作 | 落点 |
|---|---|---|
| 1 | 仓库页「新建仓库」→ 填类型/地址/凭据 → 落库 | `pages/repo/index.vue:459-511`（`openCreate` / `runCreate`） |
| 2 | 设密码（行内按钮，密码文件缺失才出现） | `POST /api/repos/{id}/password`（E44） |
| 3 | 初始化（在"未初始化"结论上给入口，走 **rebuild**） | `POST /api/repos/{id}/rebuild` |
| 4 | 测试连接 | `POST /api/repos/{id}/test`（E43） |
| 5 | 切当前仓库 | `ui.setCurrentRepoId(id)`（`stores/ui.ts:85-92`） |
| 6 | 任务向导建任务 | `components/TaskWizard.vue` 五步 |

第 3 步之所以走 rebuild，是因为**全仓没有独立的 init 端点**：`grep '"init"'` 的唯一业务调用点在 rebuild 内部。

### 2.2 关键发现一：rebuild 不能承担「新建后初始化」

`rebuild_repo` 先判断本地后端，**远程后端直接 422**（`services/repo_lifecycle.py:266-280`），因为它的语义是「清空目录内容再 init」。而新建仓库最需要 init 的场景恰恰是 s3 / b2 / azure / sftp 这些**远程后端**（本地目录直接 `restic init` 也能建，但远程没有"清空"这回事）。

结论：**需要一条「只 init、不清空」的通道**，对远程后端同样安全可用——但**不必是新增端点**：

> ✅ **该通道已经存在**——`POST /api/jobs {type:"init"}`（`schemas/enums.py:19` 白名单内、`routers/jobs.py:52-112`），作业成功后自动做 `keys/` 身份中性化（`services/job_runner.py:552-566`）。它的语义正是「执行 `restic init`、不做任何清空」，因此**不受 rebuild 的本地后端限制**（那个 422 属于「清空目录」那一步，与 init 无关）。⇒ **后端零改动**，**绝不可复用 rebuild**。

### 2.3 关键发现二：向导第③步是只读 + 硬门禁

- 只读展示 `ui.currentRepoId` 的 url，无任何选择/新建入口（`TaskWizard.vue:856-871`）；
- 新建任务必须"测试通过"才能离开第③步：`step3Blocked = step === 3 && !isEdit && !testPassed`（`TaskWizard.vue:665`）；
- 镜像目的地候选来自 `listRepos()`，并按「url 非空 + `passfile_status=configured`」禁用（`:323-331`）。

推论：**未初始化的仓库无法通过第③步**（`test_repo` 走 `restic cat config`，未初始化必失败），所以"在向导内建仓"如果不带 init，用户会卡死在门禁上——这就是 init 必须内嵌的原因。

### 2.4 关键发现三：草稿不记仓库

`DRAFT_KEY = 'restic-web:wizard-draft:v1'` 的 `DraftEnvelope` 只有 `{step, form, savedAt}`（`TaskWizard.vue:157-163`）。若建仓发生在向导内而草稿不记仓库 id，用户刷新/重进会**重复建仓**（同一 id 409）或**留下孤儿仓库**。

## 3. 目标流程（用户旅程）

### 3.1 内嵌建仓的时序（前端编排，后端各步幂等）

```
① GET  /api/repos/_new_id                     预填 id（r<YYMMDD>-xxxxxx，可留空）
② POST /api/repos            {id?, name, url, host_tag}
③ POST /api/repos/{id}/password  {}           生成强随机密码，明文一次性回显（SecretReveal）
⑤ PUT  /api/config           cred.{id}.*      凭据多键写入
④ POST /api/jobs             {type:"init"}    异步作业；成功后自动 keys/ 身份中性化
⑥ POST /api/repos/{id}/test                   自动跑一次，ok 才算通过（复用第③步门禁）
⑦ ui.setCurrentRepoId(id) + draft.provisionedRepoId = id
   → 后续步骤照旧；保存时落到新仓
```

**顺序约束（硬性）**：

| 约束 | 原因 |
|---|---|
| ③ 必须先于 ④ | `restic init` 需要该仓库的口令文件 |
| ③ 必须先于 ⑤ | **严格语义**：无口令文件的仓库拒写 `cred.<repo_id>.*`（422 `VALIDATION_ERROR`，`data.path` 给期望路径），不降级回 default 密钥 |
| ④ 与 ⑤ 可互换，**推荐 ⑤ 先于 ④** | init 失败时凭据已录好，重试 init 无需重填 |

### 3.2 每步失败的可恢复性（幂等契约）

| 步 | 失败 | 处理 |
|---|---|---|
| ② | 409 id 重复 | 提示换 id，或「检测到你已建过该仓库 → 直接使用它」跳 ③ |
| ③ | 422 密码文件已存在 | 视为已完成（跳过），继续 ⑤ |
| ⑤ | 422 密钥不可用 | 文案：`该仓库还没有口令文件，请先在②③步设置仓库密码`（错误码 `VALIDATION_ERROR`，`data.path` 给期望路径）。**仅在凭据加密开关开启时成立**；开关关闭时敏感值以明文落库、不 422，文案须按两态分支 |
| ④ | 作业失败（已初始化 / 远端不可达 / 桶不存在） | 作业终态含 restic 退出码与末行；「已初始化」视为成功（幂等），其余映射可操作文案并保留已建仓库供重试 |
| ⑥ | 测试失败 | 按 `failure_kind` 分流（凭据错 / 网络 / 未初始化），给"重试 / 回仓库页处理"两个出口 |

### 4.2 两种分支的步骤编排

**设计原则：`step` 从「序数 1..5」改为「语义键 stepKey」**，键值不随分支变化、只新增一个键；**显示序号一律由序列下标派生**。这样开关切换时用户停留的逻辑步骤不移动、已填数据不错位、旧草稿可向后兼容。

| 分支 | 内部序列（stepKey） | 显示序号（= 下标 + 1） |
|---|---|---|
| **关**（默认，现状不变） | `[1, 3, 4, 5, 6]` | 1 基础信息 / 2 备份源 / 3 存储目标 / 4 调度 / 5 保留与首跑 |
| **开**（新建仓库） | `[1, 2, 3, 4, 5, 6]` | 1 基础信息 / **2 新建仓库** / 3 备份源 / 4 存储目标 / 5 调度 / 6 保留与首跑 |

| stepKey | 语义（i18n 键名沿用现有命名，**键名是历史命名、不代表序号**） | 出现在哪些分支 |
|---|---|---|
| 1 | 基础信息（+ 新增开关） | 两分支 |
| 2 | **新建仓库**（新增，`wizard.stepNewRepo`） | 仅「开」 |
| 3 | 备份源（原 `wizard.step2`） | 两分支 |
| 4 | 存储目标（原 `wizard.step3`，含测试门禁） | 两分支 |
| 5 | 调度（原 `wizard.step4`） | 两分支 |
| 6 | 保留与首跑（原 `wizard.step5`） | 两分支 |

**为什么保留 `3..6` 而不重新编号成 `2..5`**：

1. 旧草稿 `DraftEnvelope.step`（`:159-163`）存的是旧序数，映射表极简：`1→1`、`2→3`、`3→4`、`4→5`、`5→6`，一次可逆迁移即可，**不会把「第 2 步（备份源）」误认成「新建仓库」**；
2. 开关来回切换时，当前 stepKey 无需重算即可落在同一逻辑步；
3. 后续再插步只需往序列里加键，全站 `1..N` 硬编码一次性消失。

## 6. 边界与风险

### 6.1 风险 R1–R14

| # | 场景 | 风险 | 建议处置 |
|---|---|---|---|
| R1 | **流程中途把开关从开切到关**，且正停在「新建仓库」步 | 当前 stepKey 不在新序列里 → 空白页 / 越界 | 统一 `normalizeStep()`：切关时若 `step === KEY_NEW_REPO` → `nextKeyOf()`（＝备份源）；若已建仓则提示「已创建仓库 rXXX 将保留」并写 `provisionedRepoId` |
| R2 | 中途从关切到开 | 已填的源 / 调度数据不受影响（数据在 `form`，与步骤无关）；但「已跳过建仓」的语义需重述 | 切开时**不移动**当前位置；「新建仓库」步按需回访（步骤条可点） |
| R3 | 已建仓后关闭开关并保存任务 | 任务落到**新建的仓库**（`api/backupTasks.ts:32-42` 取 `currentRepoId`），而用户以为用的是原仓库 | 保存前二次确认 + 提供「回滚到原仓库」（`previousRepoId`），并明确提示任务归属 |
