## 0. 定位

### 0.1 一句话

今天要「一个任务一座独立仓库」，用户得跨两个页面走 6 步（仓库页建仓 → 设密码 → 初始化 → 测试 → 切当前仓库 → 任务向导建任务）；本方案把这 6 步压进**任务向导**，一次走完，且不引入任何新的数据模型约束。

> **v0.2 落点变更**：原写「压进第③步三态」，**以 §13 为准**——改为「第一步开关 + 独立第二步（新建仓库）+ 后续步骤整体后移一位」。业务时序与幂等契约不变。

### 0.2 与 C 方案的关系

| | A 方案（本文） | C 方案（暂缓存档） |
|---|---|---|
| 关系模型 | 不变（任务归属一个仓，一仓可多任务） | 反转（任务不归属仓，可配多目的地） |
| 数据迁移 | **零迁移** | 关联表 + 三段迁移 |
| 目的 | 降低「一任务一仓」的操作成本 | 改变「任务与仓的关系」语义 |
| 互斥性 | 不互斥：A 可先做，C 若将来上，A 的建仓子表单可直接复用为「目的地编组器」 | — |

结论：A 是低风险的前置改善，独立推进。**任务多仓库 C 方案已于 2026-11-01 owner 裁决彻底放弃并归档**，本表仅作历史对比，不再作为实施路线。

## 1. 目标与非目标

**目标**

1. 向导第③步支持「新建一座专属仓库」并就地完成 建仓 → 设密码 → 录凭据 → 初始化 → 连通测试；
2. 新建完成后自动把当前仓库切到新仓，任务直接落到新仓（`POST /api/repos/{id}/backup-tasks` 是 repo 作用域，必须切）；
3. 用户中断向导时，已建的仓库**可见、可撤销、可续用**，不产生"看不见的半成品"；
4. 全程零新增数据库列、零迁移。

**非目标**

1. 不强制 1:1（不加唯一索引、不拒绝「同仓第二任务」）；
2. 不改 `backup_tasks` / `jobs` / `repos` 表结构；
3. 不改任务 API 作用域（仍 `/api/repos/{repo_id}/backup-tasks`）；
4. 不解决凭据加密的多仓隔离缺口（§2.3 记录，另案）。

第 3 步之所以走 rebuild，是因为**全仓没有独立的 init 端点**：`grep '"init"'` 的唯一调用点在 `repos.py:1050`（rebuild 内部）。

### 2.2 关键发现一：rebuild 不能承担「新建后初始化」

`rebuild_repo` 先 `_repo_local_path(repo.url)` 判断本地后端，**远程后端直接 422**（`repos.py:995-1001`），因为它的语义是「清空目录内容再 init」。而新建仓库最需要 init 的场景恰恰是 s3 / b2 / azure / sftp 这些**远程后端**（本地目录直接 `restic init` 也能建，但远程没有"清空"这回事）。

结论（v0.2 修订）：**需要一条「只 init、不清空」的通道**，对远程后端同样安全可用——但这**不必是新增端点**：

> ✅ **v0.2 复核：该通道已经存在**——`POST /api/jobs {type:"init"}`（`schemas/enums.py:19` 白名单内、`routers/jobs.py:52-112`），作业成功后自动做 `keys/` 身份中性化（`services/job_runner.py:552-566`）。它的语义正是「执行 `restic init`、不做任何清空」，因此**不受 rebuild 的本地后端限制**（`repo_lifecycle.py:266-280` 的 422 属于「清空目录」那一步，与 init 无关）。⇒ **后端零改动**，原文「必须新增独立 init 端点」作废，详见 §4.1。

### 2.3 关键发现二：凭据加密是**全站单例**，密钥源固定为 default 仓库密码

> ⚠️ **v0.2 补正：先分清两个密码用途，本节只讲第二个**（原文标题容易被读成「整个仓库都用默认密码」，这是误读）。
>
> | 用途 | 密钥源 | 是否每仓独立 | 证据 |
> |---|---|---|---|
> | **restic 仓库本身**（init / backup / check / snapshot） | `<passfile_root>/<repo_id>/password` | ✅ **每仓一份** | `settings.py:167-179`（唯一实现点）；`services/restic.py:392` `env["RESTIC_PASSWORD_FILE"] = str(settings.passfile_path(repo_id))`；`tests/test_passfile.py:21-22` 断言 `passfile_path("repo-2") == /data/repos/repo-2/password` |
> | **凭据加密**（`cred.*` 配置值的 `enc:v2` 加解密） | `main.py` 里**唯一一个** `CredentialCrypto`，绑定 `DEFAULT_REPO_ID` | ❌ **全局单钥**（既有缺口） | `main.py:212`（HEAD）/ `:210`（基线）；`grep -rn 'CredentialCrypto(' backend/` 生产代码**仅此一处**（其余 4 处都在 `tests/test_credential_crypto.py`） |
>
> 两条链路**互不相干**：新建 repo-b 时，restic 用的是 `repo-b/password`（每仓独立、正常）；而 `cred.repo-b.*` 的加解密用的是 **default 的**密码文件派生出的密钥。本节其余内容全部只针对第二行。

`main.py:210` 只构造一个密码学实例（**基线提交 `82326b4` 的实测行号；当前 HEAD 这三行已下移至 `:212-214`**，符号名不变）：

```python
credential_crypto = CredentialCrypto(settings, repo_id=DEFAULT_REPO_ID)   # 固定 default
encryption = EncryptionState(credential_crypto)
config_repo = ConfigRepo(db, encryption=encryption)
```

`CredentialCrypto._derive_key()` 的密钥 = HKDF(**default 仓库密码文件**, info 混入 `repo_id`＝`"default"`)，`ConfigRepo._maybe_encrypt` 对所有敏感键共用这一实例（`config_repo.py:163-169`）。

> ⚠️ **v0.2 校正：机制 vs 装配**（上句原文写作「info 含 `"default"`」，容易读成「机制里把 info 写死成 default」，失真）
>
> - **机制早已就绪**：`crypto.py:51-57` 的 `_hkdf_info(repo_id)` 返回 `_HKDF_INFO_V1 + b"\x00" + repo_id.encode("utf-8")`——repo_id **确实**混入了 HKDF info；`encrypt`（`crypto.py:174-183`）与 `decrypt` 的 v2 分支（`crypto.py:195-213`）都走它。基线提交即如此，不是后来才改的。
> - **真正缺的是装配**：`main.py:210` 只建**一个**绑定 `DEFAULT_REPO_ID` 的实例并注入全局 `ConfigRepo`，因此所有 `cred.*` 共用 default 派生出的同一把密钥。
> - **对 §10-4 裁决的影响（代价差一个量级）**：按「机制缺失」理解会以为要重写派生算法；实际只需**按仓库各建实例**。但存量密文是用 info = `base + \x00 + "default"` 加密的（写侧恒 `enc:v2:`，`crypto.py:42`），一旦某仓改用 `repo_id=<该仓>` 派生，**旧密文立刻无法解密**（`CREDENTIAL_DECRYPT_FAILED`），必须伴一次性重加密迁移——可复用 `reencrypt`（`crypto.py:185-193`）与 `migrate_encryption`（`config_repo.py:171-190`）。这正好支撑 §10-4「另案」的判断。

`CredentialKeyUnavailableError` 的行号亦随代码演进漂移：**基线 `errors.py:173-184`，当前 HEAD `:223-234`**；§11 取证清单以基线为准，§12 核对表给出双坐标。

> **落地时发现的额外缺陷（顺带修复）**：`repo_lifecycle.rebuild` 原顺序是「清目录 → 写新口令文件 → restic init → 清旧 `enc:v2` 凭据」。B1 之后 `restic init` 取凭据要 `list_all()` 全表解密，而新口令文件已写、该仓旧密文已不可解 → 500。已把「清旧密文」提前到写口令文件之前（删键不需要解密），顺序契约同步更新在该方法 docstring。

>
> **对本方案的直接影响**：§3.2 的第 ④ 行「先设密码再录凭据」**从建议变为硬性顺序**——向导内嵌建仓必须保证「写口令文件」先于「录入 `cred.*`」。

由此得到两条与实施方案直接相关的结论：

1. **写 `cred.{新仓id}.*` 不依赖新仓密码文件**，只依赖 **default 仓库密码文件存在**。所以"建仓 → 设密码 → 录凭据"的严格顺序**不是**必须的；422 的唯一错误类是 `CredentialKeyUnavailableError(ValidationError)`（基线 `errors.py:173-184`，当前 HEAD `:223-234`；`ValidationError.status = ERROR_STATUS[VALIDATION_ERROR] = 422`，基线 `constants.py:119` / 当前 HEAD `:129`）。

   > ⚠️ **v0.2 校正：422 的前提是两个条件的合取，原文只写了一个**。`config.py:168-176` 的实际判定是 `encryption.enabled` **且** `patch` 含敏感键（`is_sensitive`，`config_repo.py:277-279`）**且** 密码文件不可用；即**凭据加密开关关闭时，敏感值以明文落库、不返回 422**（开关键 `security.cred_encryption`，启动期按持久化键校准，`main.py:365-366`）。因此 §3.2 第 ④ 行文案与 §8 风险 4 的措辞须覆盖「开关开 / 开关关」两态，不能只写「default 密码文件缺失」。
2. **多仓库凭据共享同一把密钥**，`enc:v2` 声称的"跨仓库密钥隔离"目前**并未生效**——原因是 `main.py:210` 只有**一个**绑定 `DEFAULT_REPO_ID` 的 `CredentialCrypto` 实例（**不是** info 被写死，v0.2 已校正见上）。`crypto.py:97-105` 的 docstring 也已写明「当前仅 default；R-023 多仓库时按仓库派生」，多仓库落地时没跟进装配。这是既有安全缺口，**不在本方案范围**，但必须在 §8 风险登记，避免被当成 A 方案引入的问题。

### 2.4 关键发现三：向导第③步是只读 + 硬门禁

- 只读展示 `ui.currentRepoId` 的 url，无任何选择/新建入口（`TaskWizard.vue:856-871`）；
- 新建任务必须"测试通过"才能离开第③步：`step3Blocked = step === 3 && !isEdit && !testPassed`（`TaskWizard.vue:665`）；
- 镜像目的地候选来自 `listRepos()`，并按「url 非空 + `passfile_status=configured`」禁用（`:323-331`）。

推论：**未初始化的仓库无法通过第③步**（`test_repo` 走 `restic cat config`，未初始化必失败），所以"在向导内建仓"如果不带 init，用户会卡死在门禁上——这就是第 3 步（init）必须内嵌的原因。

### 2.5 关键发现四：草稿不记仓库

`DRAFT_KEY = 'restic-web:wizard-draft:v1'` 的 `DraftEnvelope` 只有 `{step, form, savedAt}`（`TaskWizard.vue:157-163`）。若建仓发生在第③步而草稿不记仓库 id，用户刷新/重进会**重复建仓**（同一 id 409）或**留下孤儿仓库**。

## 3. 目标流程（用户旅程）

> ⚠️ **本节的落点形态已被 §13 取代（v0.2，2026-11-01）**：§3 把建仓做成**第③步内的三态选项**；§13 改为**第一步开关 + 独立第二步「新建仓库」+ 后续步骤整体后移**。二者的业务语义（建仓→密码→凭据→init→测试→切当前仓）完全一致，**差异只在落点与步骤编排**。实施以 §13 为准，本节保留作为**业务时序与幂等契约的参考**（§3.1 时序、§3.2 失败矩阵仍然有效，可直接被 §13 的第二步复用）。

第③步给三个选项，**默认选中"新建专属仓库"**：

| 选项 | 说明 |
|---|---|
| A. 新建专属仓库（默认） | 内嵌建仓子表单，走完即用 |
| B. 使用当前仓库 | 现状行为（只读展示 + 测试连接） |
| C. 复用其他已有仓库 | 从 `listRepos()` 选一个（等价于切换当前仓库），并提示「该仓已承载 N 个任务」 |

### 3.1 内嵌建仓的时序（前端编排，后端各步幂等）

```
① GET  /api/repos/_new_id                     预填 id（r<YYMMDD>-xxxxxx，可留空）
② POST /api/repos            {id?, name, url, host_tag}
③ POST /api/repos/{id}/password  {}           生成强随机密码，明文一次性回显（SecretReveal）
④ PUT  /api/config           cred.{id}.*      凭据多键写入（422 CREDENTIAL_KEY_UNAVAILABLE → 提示先配 default 密码）
⑤ POST /api/repos/{id}/init  （新增端点）      restic init + keys/ 身份中性化
⑥ POST /api/repos/{id}/test                   自动跑一次，ok 才算通过（复用第③步门禁）
⑦ ui.setCurrentRepoId(id) + draft.provisionedRepoId = id
   → 第④⑤步照旧；第⑤步提交时落到新仓
```

顺序约束说明（据 §2.3 修正）：③ 与 ④ 的先后**不是**安全约束，先设密码只是为了让"仓库自身可用"（init 需要密码文件，⑤ 依赖 ③）；④ 与 ⑤ 可互换，但建议 ④ 在 ⑤ 前——init 失败时凭据已录好，重试 init 无需重填。

### 3.2 每步失败的可恢复性（幂等契约）

| 步 | 失败 | 处理 |
|---|---|---|
| ② | 409 id 重复 | 提示换 id，或「检测到你已建过该仓库 → 直接使用它」跳 ③ |
| ③ | 422 密码文件已存在 | 视为已完成（跳过），继续 ④ |
| ④ | 422 密钥不可用 | 明确文案：`默认仓库密码文件缺失 —— 先到仓库页为 default 设置密码`（**v0.2 校正**：仅在**凭据加密开关开启**时成立；开关关闭时敏感值以明文落库、不 422，文案须按两态分支，见 §2.3 校正块） |
| ⑤ | 409 已初始化 | 视为成功（幂等），继续 ⑥ |
| ⑤ | 远端不可达 / 桶不存在 | 映射可操作文案（restic 退出码 + 最后一行），保留已建仓库供重试 |
| ⑥ | 测试失败 | 按 `failure_kind` 分流（凭据错 / 网络 / 未初始化），给"重试 / 回仓库页处理"两个出口 |

## 4. 后端改造

### 4.1 新增端点 `POST /api/repos/{repo_id}/init`（⚠️ **v0.2 降级为可选，推荐不新增**）

> **v0.2 复核结论**：本轮回到代码核实时发现 **init 已经有现成的异步通道**，本文写作时漏了它——
>
> | 事实 | 位置 |
> |---|---|
> | `init` 在任务类型白名单内 | `schemas/enums.py:19`（`INIT = "init"`） |
> | `POST /api/jobs {type:"init"}` 可直接提交，落 `jobs` 表、走 `JobRunner` | `routers/jobs.py:52-112` |
> | init 成功后**自动做 key 中性化**（与 §4.1「后置」要求同款） | `services/job_runner.py:552-566`（`status == "success" and job.type == "init"` → `neutralize_repo_key(...)`） |
> | **不受 rebuild 的「仅本地后端」限制**（那个 422 只属于「清空目录」语义） | `services/repo_lifecycle.py:266-280` |
>
> 因此「无独立 init 端点」≠「init 不可用」——**建仓后提交一个 `type=init` 作业即可**，后端**零改动**。本节的同步端点降级为**可选**，推荐**不新增**：少一个端点就少一套鉴权（红线 S4）、审计、错误码与超时语义的回归面，而向导本来就能等作业终态。
>
> 若 owner 仍要同步端点（例如希望前端拿到结构化 `already`/`key_neutralized` 而不必解析作业终态），下表保留作为设计参考，并须按 §4.2/§4.3 同步补齐抽取与审计常量。

**（以下为可选的同步端点设计）**

```
POST /api/repos/{repo_id}/init          （无请求体）
→ 200 {ok: true, already: bool, key_neutralized: bool}
```

语义与约束：

| 项 | 规则 |
|---|---|
| 前置 | 仓库存在（否则 404 `REPO_NOT_FOUND`）；`url` 非空（否则 422）；密码文件 `configured`（否则 422「请先设置仓库密码」） |
| 幂等 | 先 `restic cat config` 探测；已连通 → 200 `{already: true}` 直接返回（**不重复 init**） |
| 执行 | `restic.build("init")`（S2 白名单内已有 `init`，`constants.py:16`）+ `REPO_INIT_TIMEOUT_SECONDS`（120s） |
| 后置 | `neutralize_repo_key(...)`（`repos.py:1072-1078` 同款，失败只记日志不阻断） |
| 后端类型 | **不限制**——本地与远程后端均可（与 rebuild 的关键差异，见 §2.2） |
| 冲突 | 该仓库有 running/pending job → 409 `JOB_CONFLICT`（复用 rebuild 的检查，`repos.py:1003-1006`） |
| 审计 | 新增动作 `repo.init`（detail：`{already, key_neutralized}`，无凭据/无口令） |
| 缓存 | `invalidate_repo_status_cache()`（init 改变可连性） |

### 4.2 复用抽取

`rebuild_repo` 内 1039-1077 行的「init + keys 中性化」抽成模块级私有函数：

```python
async def _restic_init(request, repo_id: str, repo_url: str, password_file: Path, *,
                       log_prefix: str = "restic-init-") -> None
```

rebuild 与新端点共用；rebuild 的第 1 步（清空目录）保持私有，不进公共函数——**清空是 rebuild 独有的破坏性语义**，不能被 init 端点误用。

### 4.3 审计与错误码

| 项 | 内容 |
|---|---|
| 审计动作 | `AUDIT_REPO_INIT = "repo.init"`（新增常量）。**不进 S6 危险 20 项清单**（init 不删数据，与 `repo.rebuild` 同档：有审计但不在危险枚举） |
| 错误码 | 不新增；复用 `REPO_NOT_FOUND`(404) / `VALIDATION_ERROR`(422) / `JOB_CONFLICT`(409) / `RESTIC_FAILED`(500) |
| 文档同步 | 架构 §5.1 端点表加 E52（或 R-023 段内追加）+ §11 追溯矩阵；无需改 §5.0 错误码表 |

### 13.2 两种分支的步骤编排

**设计原则：`step` 从「序数 1..5」改为「语义键 stepKey」**，键值不随分支变化、只新增一个键；**显示序号一律由序列下标派生**。这样开关切换时用户停留的逻辑步骤不移动、已填数据不错位、旧草稿可向后兼容。

| 分支 | 内部序列（stepKey） | 显示序号（= 下标 + 1） |
|---|---|---|
| **关**（默认，现状不变） | `[1, 3, 4, 5, 6]` | 1 基础信息 / 2 备份源 / 3 存储目标 / 4 调度 / 5 保留与首跑 |

|---|---|---|
| 1 | 基础信息（+ 新增开关） | 两分支 |
| 2 | **新建仓库**（新增，`wizard.stepNewRepo`） | 仅「开」 |
| 3 | 备份源（原 `wizard.step2`） | 两分支 |

**为什么保留 `3..6` 而不重新编号成 `2..5`**：

1. 旧草稿 `DraftEnvelope.step`（`:159-163`）存的是旧序数，映射表极简：`1→1`、`2→3`、`3→4`、`4→5`、`5→6`，一次可逆迁移即可，**不会把「第 2 步（备份源）」误认成「新建仓库」**；
2. 开关来回切换时，当前 stepKey 无需重算即可落在同一逻辑步；
3. 后续再插步只需往序列里加键，全站 `1..N` 硬编码一次性消失。

### 13.5 边界与风险

| # | 场景 | 风险 | 建议处置 |
|---|---|---|---|
| R1 | **流程中途把开关从开切到关**，且正停在「新建仓库」步 | 当前 stepKey 不在新序列里 → 空白页 / 越界 | 统一 `normalizeStep()`：切关时若 `step === KEY_NEW_REPO` → `nextKeyOf()`（＝备份源）；若已建仓则提示「已创建仓库 rXXX 将保留」并写 `provisionedRepoId` |
| R2 | 中途从关切到开 | 已填的源 / 调度数据不受影响（数据在 `form`，与步骤无关）；但「已跳过建仓」的语义需重述 | 切开时**不移动**当前位置；「新建仓库」步按需回访（步骤条可点） |
