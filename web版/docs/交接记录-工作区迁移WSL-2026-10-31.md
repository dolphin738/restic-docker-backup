## 1. 两套工作区的关系（先搞清这个）

仓库现在有**两份工作副本**，都在同一台机器上：

| | Windows 侧 | WSL 侧（当前主用） |
| --- | --- | --- |
| 路径 | `D:\agent\AI Coding\restic-docker-backup` | `/home/AI-Coding/restic-docker-backup` |
| 世界 | Windows（`pwsh`，受 DSH 文件沙箱约束） | Linux（`bash`，WSL 自身即隔离边界） |
| 角色 | **备份侧 / 推送侧** | **开发侧 / 提交侧** |

WSL 副本的 `origin` 指向 Windows 副本（`/mnt/d/agent/AI Coding/restic-docker-backup`），
所以两侧同步走 git，不走文件拷贝。

### 同步方向

**默认：在 WSL 侧开发并提交，然后同步到 Windows 侧。**

```bash
# WSL 侧（开发完提交后）
git push origin main
```

```powershell
# Windows 侧（把 WSL 的提交拉进来）
cd 'D:\agent\AI Coding\restic-docker-backup'
git fetch origin && git reset --hard origin/main
```

> 反向场景：若某个改动只能在 Windows 侧做（例如必须 `pwsh` 或访问 Windows-only 工具），
> 在 Windows 侧提交后，WSL 侧执行 `git fetch origin && git reset --hard origin/main`。
> **两侧不要同时改同一个文件**——否则 `reset --hard` 会丢掉一侧的未提交改动。
> 每次同步前先确认目标侧工作树干净。

## 2. 推送（在 WSL 侧做）

`github`（github.com/dolphin738/restic-docker-backup）在 WSL 侧**尚未配置凭据**，
首次推送前需要一条：

```bash
gh auth login          # 浏览器 device flow
gh auth setup-git      # 让 git 复用 gh 的凭据
git push github main
```

没装 `gh` 时（Debian 官方源）：

```bash
(type -p wget >/dev/null || apt install -y wget) && \
  mkdir -p -m 755 /etc/apt/keyrings && \
  wget -qO- https://cli.github.com/packages/githubcli-archive-keyring.gpg \
    > /etc/apt/keyrings/githubcli-archive-keyring.gpg && \
  echo "deb [signed-by=/etc/apt/keyrings/githubcli-archive-keyring.gpg] \
https://cli.github.com/packages stable main" > /etc/apt/sources.list.d/github-cli.list && \
  apt update && apt install -y gh
```

**注意**：WSL 默认用户是 **root**，`~` = `/root`，git 全局配置落在 `/root/.gitconfig`。
凭据若用 `credential.helper store` 会**明文**写入 `/root/.git-credentials`——个人 VM 可接受，
共享机器请改用 `cache`（内存，15 分钟）或 `gh auth setup-git`。

**首次推送前务必核对**：当前 main **领先远端 111+ 个提交**，且这些提交只存在于本机两份副本上。
推送前先确认没有把不该公开的内容带上去（凭据、口令文件、`.env` 等已在 `.gitignore`，但仍建议
`git log --stat` 抽查一遍）。

### 候选 5 · **别重走这条死路**（已完成）

原计划「从 OpenAPI 生成 TS 类型取代手写」。**试过，不可行，已回滚**：

- 76 个同名类型改成 `S['X']` 别名后，`vue-tsc` 报 **82 个错误，其中 42 个 `possibly undefined`**
- 根因：**FastAPI 把带默认值的字段一律标为 optional**（`items?:`），而响应里它们必然存在 →
  生成类型比手写类型**更宽**
- `--properties-required-by-default` 救不了：会把请求体可选字段一并变必填（`force` 默认 false 是反例）
- **响应要必填、请求要可选，一个全局开关做不到**

现行方案：**类型仍手写，用两道门禁拦漂移**

| 门禁 | 拦什么 |
| --- | --- |
| `backend/tests/test_api_contract_sync.py` | `openapi.json` 与代码逐字一致；`schema.d.ts` 覆盖全部 schema 名 |
| `backend/tests/test_api_field_parity.py` | 前端同名类型**字段名集合**与后端 schema 一致 |

改后端 schema 后**必须**重新生成，否则门禁红：

```bash
# 在 web版/ 下，用 backend 的 venv
python scripts/gen-openapi.py
pnpm -C frontend gen:api
```

> owner 已批准 `openapi.json` + `schema.d.ts` 入库（生成产物豁免「≤400 行/次」约定）。

**三条贯穿四批的裁决：**

1. **确认门一律留在父页**（useRepoGates 持有开关与动作），子组件只 emit 请求开门。
   理由：门的渲染位置与生命周期若有变化，21 处门的编排就得重新验证；留在父页 = 零行为变化。
2. **共享状态以 prop 传入，不复制**：repoForm / credInput 是 reactive 对象，
   父子持同一份，v-model 双向照旧写回父页；保存/创建/测试等写路径留在父页。
   → 不存在「父子各持一份状态」的分叉。
3. **样式类随模板一起搬**（repo__*）：scoped 样式**不穿透子组件**，
   留在父页会静默失效（候选 6 已实证）。例外：.repo__note 与 .repo__init-progress
   在列表卡/维护卡也用，父页保留副本。

**诚实账：单文件降下来，仓库页总量是净增的**（四批合计约 +560 行）。
收益是「单文件可读」，不是「总行数减少」——拆分本身要付 props/emit 的声明成本。

## 5. 踩过的坑

1. **PowerShell 给 bash 传命令要用单引号**：双引号里 `$HOME`、`$?` 会被展开，反斜杠还会丢
   （`C:\Users\x` → `C:Usersx`，曾因此造出一个含 U+F03A 的怪目录）。
2. **WSL 侧写入后注意 CRLF**：Windows 侧 Python 默认写 CRLF，而仓库存 LF，会导致整文件重写。
   Linux 侧工具天然 LF，通常无此问题；跨侧编辑后建议 `git diff --stat` 看一眼。
3. **grep 自匹配**：门禁文件含正则字面量，`grep -l` 会把自己判成违规。已在 bash 与 pytest 两侧显式排除。
4. **别用手写 `"""` 状态机跳 docstring**：遇非常规引号会失步，曾导致某文件 63 行后**完全不被扫描**。
5. **`docs/` 指针校验只认带斜杠的路径式引用**；正文里的《文件名.md》是散文提名，不是链接。
6. **会话按工作区绝对路径隔离**：换工作区 = 空会话。所以状态写进 git（就是本件的用途），
   不要试图搬运 `D:\agent\.dsh\sessions\` 下的 jsonl。
