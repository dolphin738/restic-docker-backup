## 0. 一句话

「**哪些配置键由哪个密钥源保护**」这条知识被**手抄在 6 处**（1 处正确定义 + 5 份漂移副本，见 §2.1），
其中 2 处已实际发作（缺口 1/2）、2 处被「default 不可达」这个外部事实按住（§2.1 D/E）。
这是**一个缺失的模块**，不是六个独立 bug。

另外还有一条**与密钥归属无关、但更直接的数据丢失路径**（缺口 6）：`release` 端点缺守卫，
正常 UI 操作即可删掉 default 行并接通「墓碑到期 → 口令文件被回收 → 全局键永久解不开」的链条。

### 1.3 环境说明（重要，非仓库缺陷）

本机 DSH Windows 沙箱下，pytest 的 tmp 工厂用 `os.mkdir(mode=0o700)` 建目录（`_pytest/tmpdir.py:153,163`），

与仓库代码无关。切到完全权限后上述结果正常取得。若未来要在 Windows 上跑 CI，这会原样复现。

**另修一处门禁缺陷（本次实施中发现）**：`scripts/check_dockerignore.py` 打印 `✓`/`✗`（U+2713/U+2717），Windows 控制台默认 cp936 下抛 `UnicodeEncodeError` 直接崩溃，致 `bash scripts/verify_redlines.sh` 的 **G8 恒为假失败**（19 项里 1 项误报，会被后来者误判为回归）。最小修法：`main()` 开头对 `sys.stdout`/`sys.stderr` 调 `reconfigure(encoding="utf-8", errors="replace")`（`hasattr` 保护非 TTY 场景），**不改脚本语义与输出形态**。修后不设任何环境变量即 **19/19**——验收口径自此写死为「Windows 无环境变量 19/19、WSL 18/18（无 python 时 G8 按设计跳过）」。

### 1.4 二次核对：前一轮结论的更正与一条新发现（2026-11-02 追加）

前一轮口头结论里有 **1 处说错**，另有 **1 条更严重的缺口**当时没发现。均已实测：

#### 更正 ①：`migrate_encryption` **不是** `list_all()` 的调用方

前一轮把「启动期 `migrate_encryption`（`main.py:395`）」列为 `list_all()` 的调用方之一。**这是错的。**

`migrate_encryption` 走的是 `list_all_raw()`（`config_repo.py:204`），该入口**不解密**（`:119-122` docstring 明写「仅供加密迁移判定形态，勿用于业务」）。
所以「口令文件被换 → 启动期迁移静默跳过」这条现象**不是** `list_all()` 抛错造成的，而是 `migrate_encryption` 自己的两个 try 分支（`:212-218`、`:231-237`）在吞 `CredentialDecryptError`。

**影响**：缺口 2 的放大器清单少一项（该处本就不抛），缺口 3 的崩溃点仍成立（`cr.encrypt()` 在 `:228`，无 try）。**结论方向不变，论据需修正。**

#### 新发现：缺口 6 · `release` 端点可直删 default 行，并接通整条钥匙销毁链

**这是本次核对最重要的发现，且它把缺口 4 从「设计缺口」升级为「可直接触发的数据丢失路径」。**

`POST /api/archive/repos/{repo_id}/release`（`routers/repos_crud.py:308-339`）的守卫只有三条：
仓库存在（`:328`）、`confirm_id` 与 id 相同（`:331`）、无活跃作业（`repo_lifecycle.py:447`）。

**没有** `ensure_deletable`（对比同文件 `:209` 的 DELETE 路由有）、**没有** default 禁删、**没有**「必须已归档」校验。

实测（`app_client` 夹具，2026-11-02）：

| 步骤 | 结果 |
|---|---|
| 先经 E07 写入 `dump.password` | 200 |
| `POST /api/archive/repos/default/release {"confirm_id":"default"}` | **200** |
| `repos.exists("default")` | **False**（行已删） |
| 此时读 `dump.password` | 仍可读（口令文件还在） |
| 墓碑 | 已建，`released_at` 已置位 |
| 推进 365 天（删墓碑）+ 口令文件 mtime 超冷却期 → `reap_orphan_passfiles` | **`['default']` 被回收，口令文件消失** |
| 再读 `dump.password` | **`CredentialKeyUnavailableError`** |

即：**「归档页 → 释放 ID → 输入 default 确认」这一串正常 UI 动作，就能把 default 行删掉，并在墓碑到期后连带销毁全局键的密钥源。**
前端入口真实存在（`pages/archive/index.vue:673-679` 的 ConfirmGate，`keyword = repo_id`），不需要改库、不需要越权。

**另外两条实测**：

- **非归档仓库也能 release**：新建 `r9`（未归档）→ `release` 返回 200、行被删。语义上「释放**归档**仓库 ID」与实际行为不符。
- **有备份任务时抛未捕获的 `sqlite3.IntegrityError`**（`FOREIGN KEY constraint failed`）→ 走 `main.py:514` 兜底 → **500 服务器内部错误**，而不是 409/422。所以前一轮说的「外键是一道意外的保护」在**结果上成立、在体验上是 500**；且这道保护只在「有任务或作业行」时生效，干净仓库没有任何阻挡。

**为什么这条此前没被发现**：现有测试 `test_repo_lifecycle_release.py` / `test_repo_delete.py:420` 都只测「已归档的非 default 仓库」，从未覆盖 default 或未归档仓库。

## 2. 根因：一个不变量，六处手抄

### 2.1 全量盘点：1 处正确定义 + 5 份手抄副本（共 6 处）

`grep -n "cred\\.{" backend/app` 共命中 **6 处前缀重建**（另有 2 处 `startswith("cred.")` 判定 + 1 处属 A 自身，见后）。逐处定责：

| # | 位置 | 用途 | 只覆盖 `cred.<repo>.*`？ | 评价 |
|---|---|---|---|---|
| A | `services/crypto.py:244-257` `_repo_id_for_cred_key` | 键归属的**唯一定义** | 否（非 `cred.*` → default） | ✅ 正确，是 B–F 应当询问的源 |
| B | `routers/ops.py:901` 密钥轮换 | 收集需重加密的键 | 是 | 🔴 漏 5 个全局敏感键 |
| C | `services/repo_lifecycle.py:330` `_clear_encrypted_credentials`（rebuild 前） | 清残留密文 | 是 | 🔴 default 重建时漏全局键 |
| D | `services/repo_lifecycle.py:219` `_clear_credentials`（hard_delete / release / expire 三处调用：`:398/:452/:507`） | 清凭据键 | 是 | 🟡 形态同 B/C；**default 不可达**（见 §1.4 缺口 6），故暂未发作 |
| E | `services/retention.py:394` `expire_archived` 的**测试兜底分支** | 清凭据键 | 是 | 🟡 同 D；生产路径恒走编排器（`:387` 注释），但 `_lifecycle` 未注入时仍可达 |
| F | `services/repo_migration.py:56` 一次性迁移 | `cred.*` → `cred.default.*` | 是 | ✅ 目标就是 default，语义正确 |

另有 **3 处 `startswith("cred.")` 判定**（`config_transfer.py:200` 导出打包、`routers/ops.py:545` 导出计数、`services/crypto.py:252` A 自身）——它们判「是不是凭据键」，不判「归哪个密钥源」，**不属手抄**。

还有 **3 处按仓库过滤的前缀**（`services/env_sync.py:121`、`services/config_transfer.py:315`、`routers/backup_tasks.py:366`）

A 是正确定义，B–E 是它的手抄副本，各自漂移。**B、C 已实际发作（缺口 1/2）；D、E 被「default 不可达」这个外部事实按住——一旦可达路径变化（如 §1.4 缺口 6 被修成别的形态），它们会跟着发作。**

### 2.2 全局敏感键的完整清单

`db/repositories/config_repo.py:34-41` `SENSITIVE_EXACT_KEYS`（共 5 个）：

`dump.password`、`notify.healthchecks_url`、`notify.webhook.url`、`notify.mail.password`、`metrics.token`

`crypto.py:249` 的注释写作「`notify.*`」**不精确**——实际只有上面 3 个 `notify.*` 是敏感的，其余 `notify.*`（如 `notify.on_success`、`notify.skipped_threshold`）走明文。

### 2.3 为什么「全局键落到 default」本身是对的

`crypto.py:244-257` 的规则不是偷懒：全局键**不属于任何仓库**，但加密必须有密钥源。落 `DEFAULT_REPO_ID` 是唯一可用选择——除非另造一个「全局密钥源」。

**问题不在「落 default」，在「这个落法没有被任何调用点知道」。**

## 3. 缺口清单（按严重度）

### 🔴 缺口 1 · 轮换 default 口令，全局敏感键永久不可解

- **锚点**：`routers/ops.py:894-920`
- **机制**：轮换流程是「用旧密钥解出密文 → 写新口令文件 → 用新密钥重写」。收集条件（`:901`）只匹配 `cred.default.*`，5 个全局键被跳过。
- **为何无兜底**：`config_repo.py:227-237` 的 `migrate_encryption` 只处理「明文→加密」与「`enc:v1:`→`enc:v2:`」两个分支；已是 `enc:v2:` 但密钥不对的密文**两个分支都不进**，直接跳过。**没有任何启动期告警。**
- **用户可见后果**：快照导出 500（`dump.py:116` 读 `dump.password`）、通知渠道配置读不出（告警全哑）、metrics 令牌鉴权失效。
- **恢复路径**：逐个经 E07 覆写——但用户**不知道要这么做**，因为轮换界面显示「完成」。

### 🔴 缺口 2 · 残留密文把单仓库故障放大成全站故障

- **锚点**：`db/repositories/config_repo.py:114-117`（`list_all` 全表逐行解密）
- **两个入口都会留下残密文**：
  - `routers/repos_status.py:105-144` **force 覆盖口令文件**：写完文件即返回，没有清理调用（对比 `repo_lifecycle.py:567-572` 的 rebuild 分支，注释明写「留到 init 之后会 500」）。
  - `repo_lifecycle.py:325-338` `_clear_encrypted_credentials`：只清 `cred.<repo_id>.*`，对 default 执行 rebuild 时**全局键密文照样残留**。
- **放大器**：`list_all()` 的调用方包括 `env_sync.load_credentials`（`job_runner.py:1404-1406`，**每个备份任务的必经之路**）、`GET /config`（`config.py:107`）、配置导出（`ops.py:530`）、单任务导出（`backup_tasks.py:369`）。
- **实测坐实**：测试 ② 的失败点就是 `list_all()` 本身，不是某个键。
- **注意**：这条**与 default 无关**，任何仓库都会中招。

### 🔴 缺口 3 · 口令文件缺失 + 有明文残留 → 启动崩溃循环

- **锚点**：`main.py:394-397` 裸调 `migrate_encryption(encrypt=True)`；`config_repo.py:227-229` 的 `cr.encrypt()` 无 try。
- **为何是循环**：`main.py:374-378` 对「口令文件缺失」只 `logger.warning`，**不阻止启动**；于是每次重启都在同一处抛异常。
- **触发条件**：口令文件丢失 + 库里还有明文敏感键（加密开关曾关闭期间写入的存量形态）。

### 🟡 缺口 4 · 孤儿口令文件回收会误删 default 的钥匙

- **锚点**：`services/retention.py:415-426` + `utils/passfile.py:139-165`
- **判据**：口令文件存在，且 repo_id **不在** `known_ids`（在用 + 归档 + 墓碑），且 mtime 超冷却期 → 删除。
- **级联链**：

  ```
  default 行损坏/消失 → default 不在 known_ids → 其口令文件被判「孤儿」
  → 冷却期（RETENTION_REPO_PASSFILE_DAYS，默认 30）一过 → 自动删除
  → 全局键的密钥源永久消失
  ```

- **最危险的窗口**：行先没、文件后删，中间隔着 30 天。此时系统只是「某个仓库不见了」，真钥匙还在盘上、还能救。窗口一过就救不回来。
- **前提**：`repos` 表的 default 行只由迁移 `0002_multi_backup_tasks.sql:14` 一次性插入，全仓**没有启动期重建逻辑**（`INSERT INTO repos` 仅 `create()` 一处，不会自动补）。

### 🟡 缺口 5 · `RESTIC_PASSWORD_FILE` 全局覆盖让隔离收益归零

- **锚点**：`settings.py:155-179`
- **现状**：设了这个 env，所有仓库共用同一口令文件 → 所有仓库密钥材料相同（只有 HKDF info 里的 repo_id 不同）。
- **删除侧保护是到位的**：`remove_passfile`（`utils/passfile.py:97-100`）与 `reap_orphan_passfiles`（`:148-150`）都整体跳过。**这个设计正确，不要动。**
- **但隔离收益消失**：一个文件泄露 = 全部仓库密钥材料泄露；一个文件丢失 = 全部仓库不可读 + 全部凭据不可解。且会放大缺口 1–4。

### 🔴 缺口 6 · `release` 端点可直删 default 行，并接通整条钥匙销毁链

> **本节为 2026-11-02 二次核对的新发现**（详见 §1.4）。它是缺口 4 的**可触发路径**，严重度高于缺口 4 本身。

- **锚点**：`routers/repos_crud.py:308-339`（`POST /api/archive/repos/{repo_id}/release`）
- **守卫只有三条**：仓库存在（`:328`）、`confirm_id` 与 id 相同（`:331`）、无活跃作业（`repo_lifecycle.py:447`）。
- **缺三条守卫**：
  - **没有** `ensure_deletable`——对比同文件 `:209` 的 DELETE 路由有；
  - **没有** default 禁删——`repo_repo.py:371` 的守卫只在 `ensure_deletable` 里，此路径不经过；
  - **没有**「必须已归档」校验——实测未归档仓库也能 release 成功。
- **完整触发链（实测逐步验证）**：

  ```
  归档页 →「释放 ID」→ 输入 default 确认
    → POST /api/archive/repos/default/release  →  200
    → repos.exists("default") == False        （行已删）
    → 墓碑建立、released_at 置位              （此时口令文件仍在，钥匙还能救）
    → 365 天后墓碑到期被删 → default 不在 known_ids
    → reap_orphan_passfiles 回收 ['default']  →  口令文件消失
    → 全局键（dump.password / notify.* / metrics.token）永久解不开
  ```

- **前端入口真实存在**：`pages/archive/index.vue:673-679`（ConfirmGate，`keyword = repo_id`）。**不需要改库、不需要越权。**
- **有任务时的实际表现**：抛未捕获的 `sqlite3.IntegrityError`（`FOREIGN KEY constraint failed`）→ `main.py:514` 兜底 → **500**，不是 409/422。外键在结果上挡住了删行，但**只在有任务或作业行时**生效；干净仓库没有任何阻挡。
- **为何此前未被发现**：现有测试（`test_repo_lifecycle_release.py`、`test_repo_delete.py:420`）只覆盖「已归档的非 default 仓库」，default 与未归档仓库从未被测。

## 4. 方案 A（第 1 批）：把键归属收成单一出口

### 4.1 目标

让「键 → 密钥源」与「密钥源 → 键集合」这一对映射**只有一处定义**，四个调用点全部改为问它。
这样缺口 1/2 的一部分与缺口 4 从「补丁堵住」变成「结构上不可能发生」。

### 4.2 接口（最小形态）

在 `services/crypto.py` 内新增（或独立小模块），四个方法：

| 方法                                                                       | 回答的问题                   | 现在的分散实现在                       |
| ------------------------------------------------------------------------ | ----------------------- | ------------------------------ |
| `owner_of(key) -> repo_id`                                               | 这个键由哪个密钥源保护             | `_repo_id_for_cred_key`（A，已正确） |
| `keys_of(repo_id, keys) -> set[str]`【**双参**：crypto 不读库（红线 A1），全量键由调用方传入】 | 该密钥源保护哪些键（**含全局键**）     | B、C（都漏了）                       |
| `must_be_owned(repo_id) -> bool`                                         | 该密钥源必须永久视为「有主」          | D（漏了 default）                  |
| `is_sensitive(key) -> bool`                                              | 该键是否属敏感集（需加密存储）            | 原在 `config_repo.py:34-41`，已搬入 crypto 保持单一定义点 |

### 4.3 改动面（第 1 批，5 个文件）

| 文件 | 改什么 |
|---|---|
| `services/crypto.py` | 新增上述判定；`_repo_id_for_cred_key` 保留为 `owner_of` 的实现（不重复） |
| `routers/ops.py:899-920` | 收集范围由前缀字面量改为 `keys_of(payload.repo_id, keys)`（全量键取 `list_all_raw()` 的行，crypto 不读库） |
| `services/repo_lifecycle.py:325-338` | 同上 |
| `services/retention.py:420-423` | `known_ids` 无条件并入 `DEFAULT_REPO_ID`（或调 `must_be_owned`） |

外加缺口 3 的一处：`main.py:394-397` 或 `config_repo.py:227-229` 加降级 try + 告警计数。

> ⚠️ **改造禁区**：`services/env_sync.py:121`、`services/config_transfer.py:315`、`routers/backup_tasks.py:366` 三处**刻意**只按 `cred.<repo>.*` 过滤（子进程注入 / 按仓导入 / 单任务导出）——它们问的是「这个仓库的凭据有哪些」，**不是**「这个密钥源保护哪些键」。若把它们也改成 `keys_of(repo_id, keys)`，会把 `dump.password` 注进子进程环境（S3 红线）或打进任务导出包。**实施时必须逐处判断语义，不得机械替换。**

外加缺口 6 的路由守卫（§4.7，独立于本表，见该节）。

### 4.7 缺口 6 的独立修复（已定为第 0 批，见 §8.1）

## 5. 方案 B（第 3 批，B-full，已定案）：读取侧按仓库收窄 + 降级语义

### 5.1 内容

1. `ConfigRepo` 增加「按密钥源分组读取」入口，`list_all()` 不再无条件全表解密；
2. 某密钥源失效时，其保护的键**降级为 `has_value=false` + 一个可读的失效标记**，而不是让整表抛异常；
3. 启动期把失效密钥源汇总成**一条显式告警**（而不是逐键静默跳过）。

### 5.2 收益

一次性消灭缺口 1/2/3/4 的**全部**后果，包括「一个仓库坏掉拖垮全站」这条与 default 无关的放大器。
这也是唯一能让「密码文件丢失」从「全站全损」降级为「局部可恢复损失」的改法。

### 5.3 代价

动加密主路径与所有 `list_all` 调用方的语义（含 `load_credentials`、两条导出）。
需要独立验收，周期以天计。**不建议与方案 A 混在一批。**

> 本节取代 v0.2 的「待裁决」表。**D1–D6 全部定案（含 D6=(c)）**，**最终目标 = 方案 A + 方案 B-full**。

| # | 裁决项 | **裁决** | 说明 |
|---|---|---|---|
| D1 | 修到哪一层 | **A + B-full**（两阶段，A 先 B 后） | 二者关的是不同缺口，不是二选一（见 §7.1）。`(b)` 不单列——`(a)` 的 §4.3 已含缺口 3 的降级 try，`A == b` |
| D2 | 三条红测试如何入库 | **(a) 与修复同批提交** | 不标 `xfail`——红测试在修复前保持失败是正确的可执行断言 |

### 7.1 为什么 A 与 B 必须都做（覆盖矩阵）

| 缺口 | 方案 A | 方案 B-full |
|---|---|---|
| 1 轮换 default 漏全局键 | ✅ **阻止丢失** | ❌ 照丢，只让其余键不再瘫痪 |
| 2 残密文 → `list_all` 全表炸 | ⚠️ 仅清理侧（且 force 路径原本不调清理） | ✅ **关放大器** |
| 3 启动期硬崩 | ✅ 降级 try | ❌ **写侧问题，B 碰不到** |
| 4 孤儿回收误删 default 钥匙 | ✅ `must_be_owned` | ⚠️ 顺带被 A 覆盖，B 不主责 |
| 5 全局覆盖隔离归零 | ❌（D4=否，不修） | ❌ |
| 6 release 直删 default 行 | ❌ | ❌ **由 D5 的路由守卫独立修** |

两条关键不对称（决定了顺序）：

- **B 关不掉缺口 1**：B 治的是「读不出来会不会炸」，不是「钥匙会不会丢」。轮换后密文仍用旧密钥加密，B 最多把它降级成 `has_value=false`——用户照样要重录。**止血，不防伤。**
- **B 的正确实现依赖 A 的产物**：B 要做「按密钥源分组读取」，前提是知道「哪些键归哪个密钥源」，那正是 A 的 `keys_of()`。没有 A，B 只能再手抄一遍前缀——**用 B 治 A 的病却先得 A 的病**。

### 7.2 原文档的漏项：缺口 2 的「清理侧」只覆盖一半

方案 A 改的是 `_clear_encrypted_credentials`（`repo_lifecycle.py:325-338`）。但缺口 2 有**两个独立入口**：

| 入口 | 现状 | A 能否覆盖 |
|---|---|---|
| rebuild（`repo_lifecycle.py:567-572`） | 先清后写，**本来就对** | ✅ 增强其边界即可 |
| **force 覆盖口令文件**（`repos_status.py:124-144`） | `write_passfile` 后**只有审计与返回，零清理调用** | ❌ **改清理函数的边界，治不了「不调用它」的地方** |

故 force 路径必须**新增一次清理调用**（用 `keys_of(repo_id, keys)` 驱动），列入第 2 批。原 §4.4 那句「✅ 但只关清理侧」表述含糊，已在此更正。

### 7.3 D6 的核实结论：为什么 (b) 无效

2026-11-02 探针实测 release default 后的即时状态：

```
RELEASE 200
AFTER  cred.default.*:   False   ← 仓库级凭据当场被删
AFTER  dump.password:    True    ← 全局键还在
PASSFILE_STILL_THERE:    True    ← 钥匙还在盘上
GLOBAL_DECRYPT_OK:       True    ← 全局键此刻仍能解密
```

推论：

- 行能重建（一条 `INSERT`），但 **`cred.default.*` 已被删**，云存储凭据必须用户重录——重建行 ≠ 恢复凭据；
- 真正的破坏是**时序炸弹**：现在一切正常，365 天后墓碑到期、口令文件被判孤儿回收，**全局键才炸**，且那时已不可逆。

因此 D6 要防的不是「怎么恢复」，而是**别让炸弹上弦**。三个选项：

| 选项 | 收益 | 代价 | 判断 |
|---|---|---|---|
| (c) 入口硬断言，default 禁止 release | 炸弹根本不上弦；一行代码；与「default 不可删」既有不变量一致 | 无 | ✅ **建议采纳** |
| (a) 靠备份恢复 | 零成本 | 用户不知要备份，且路径**无任何警告** | ❌ 掩盖问题 |
| (b) 重建 default 行脚本 | 能修「行没了」 | 修不了「凭据被删」「口令文件会过期被回收」 | ❌ 治标且无效 |

**补充（运维事实）**：即使守住 release，「default 行丢失」仍无自动重建（`INSERT INTO repos` 仅 `create()` 一处）。故缺口 4 的 `known_ids` 无条件并入 `DEFAULT_REPO_ID` **仍要做**——它是**第二道保险**，与 D5 的入口断言互补，不是替代。
