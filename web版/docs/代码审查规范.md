## 1. 目的与原则

代码审查的目标是**正确性、安全、可维护性、性能**四件事，不是风格偏好。风格问题交给 lint（**当前实际可用：后端 `ruff check`、前端 `vue-tsc --noEmit`；eslint 与 vitest 尚未接入，CI 亦未落地——详见 §7 过渡期说明**），审查人只花精力在机器查不出来的问题上。

四条基本原则：

1. **一次审查给完整反馈**——不挤牙膏式分多轮抛意见；发现什么全部一次说清。
2. **每条意见说清 Why**——指出问题、解释后果、给出建议，三要素齐备；不写"这里不好"这类无信息量的评论。
3. **具体到行为后果**——"这会导致 SQL 注入"而不是"有安全问题"；"容器重启后 skipped 计数会丢失"而不是"逻辑有误"。
4. **好的代码要点名表扬**——审查不只挑错，遇到干净的模式（如纯函数化的 OutputParser）也要明确肯定，反馈才有校准价值。

> **与 AGENTS.md 的关系**：本文件是红线与流程的**唯一权威版本**；项目根目录 `AGENTS.md` 是面向 AI 编码代理的写码侧**编号索引**（红线正文只在本文件 §3.1，AGENTS.md 每条给出编号 + 一句话 + 可自查的 grep 线索）。规则变更时**先改本文件，再同步 AGENTS.md 的编号与线索**，禁止只改其一——**编号对不上即视为同步失败**。
>
> AGENTS.md 当前收录：S1/A2、S2、S3、S4+S5+S8（合并为一条「鉴权与首启门」）、S6、S7、A1、A3、A5、A4+A6（合并为一条）。**S4/S5/S8 与部分子项历史上曾整体漏进镜像**，已由 v1.1 补齐；新增规则须确认是否需要进 AGENTS.md。

## 3. 审查标准

### 3.1 🔴 Blocker 清单

#### A. 安全类（本项目的生命线，零容忍）

| # | 检查项 | 依据 |
|---|---|---|
| S1 | **路径越界**：任何用户输入的路径必须经 `PathMapper.validate`（规范化 + 前缀白名单 `/host`、`/sources`、`/restore`），越界抛 `PathValidationError` → 400。绕过 PathMapper 直接 `open()/os.stat/subprocess` 处理用户路径 = Blocker | 架构 D7、方案 §6 注入防护 |
| S2 | **restic 参数注入**：restic argv 只能由 `ResticCmd.build` 白名单拼装，不允许自由字符串透传，不允许 `shell=True` | §7.1 |
| S3 | **凭据泄漏**：仓库密码/后端凭据不得出现在任何 API 响应（只回 `has_value` + `source`）、日志、SSE 事件、审计 detail、异常消息中；session 明文 token 只存在于 cookie（DB 只存 SHA-256） | §8、§4.2/4.3 |
| S4 | **鉴权覆盖**：新增端点必须落在中间件链保护下（免鉴权端点仅限 E04 health 与 auth/bootstrap 相关）；SSE 端点与普通 API 同一 `require_session`，**禁止**引入 query token 鉴权 | 架构 D5、§8 |
| S5 | **CSRF/Origin**：写方法（POST/PUT/DELETE）的 Origin 校验不得因新增路由方式（如裸 APIRoute、WebSocket 替代方案）而被绕过 | §8 |
| S6 | **审计绕过**：危险操作（forget --prune / unlock / 原位恢复 / cache.clear / config.update / login.failed / restore.run）必须写审计；`audit_logs` 代码面只允许 INSERT 与 SELECT——出现 UPDATE/DELETE 路径 = Blocker | §4.6、§7.6 |
| S7 | **恢复覆盖语义**：P1 阶段任何 PR 不得引入"覆盖现有文件"的能力或参数（`--overwrite` 仅限时间戳子目录场景按 §6.3 使用）；原位恢复在 CompareService（P2）落地前不得接任何路由 | 架构 D4、PRD G3 |
| S8 | **首启门**：bootstrap 未完成时压制全站的逻辑不得被新路由/新中间件顺序破坏；随机密码明文只能一次性返回，不得进日志 | PRD US-A1 |

#### B. 架构红线类（唯一实现点纪律）

| # | 检查项 | 依据 |
|---|---|---|
| A1 | **DB 访问只在 `repositories/`**：路由层、服务层不得直接 import aiosqlite 或拼 SQL。**豁免（见下方「A1/A2 豁免机制」）**：`app/auth/` 独立 auth 模块、`routers/health.py` 的探针 SQL | 架构 D7、架构 §1.1（三层 + 独立 auth 模块） |
| A2 | **路径映射只在 `PathMapper`**：`/host`、`/sources` 前缀字符串不得硬编码在业务代码里；容器形态路径只存在于存储与 restic argv，出 API 一律带 `display_*` / `display_path` 派生字段。**豁免**：`app/constants.py`（白名单唯一出处）与 `app/exclusions.py`（模式派生所需，见下方说明） | §5.1 E08–E11 定案、D7 |
| A3 | **内置排除集唯一来源是 `ExclusionRules`**：前端或后端其他位置复制内置排除集清单 = Blocker（D8：单一事实来源）；UI 只读展示走 E32 | D8 |
| A4 | **SSE 持久底座是日志文件**：进度/事件不得改为只走内存队列（丢失断点续传与重启回放能力）；心跳 15s、`X-Accel-Buffering: no` 约定不得移除 | 架构 D6、E15 |
| A5 | **SQLite 工程约定**：全部写经 `Database.write` 单连接串行；不得引入第二个写连接或连接池；WAL + busy_timeout=5000 + foreign_keys=ON 初始化不得移除 | 架构 D2、§7.7 |
| A6 | **解析零 IO**：`OutputParser` 保持纯函数（行→结构），IO 副作用不得混入解析层（破坏 fixture 回归能力） | §7.2 |

#### C. 正确性与并发类

##### A1/A2 豁免机制（2026-10-11 裁决）

A1 与 A2 的原始措辞与**已合入 `main` 的 P1 代码**存在冲突，严格照字面执行会导致 reviewer 打回已交付代码。本节为裁决结果，把设计意图写清楚，**零代码改动**。

**A1 豁免 —— 独立 auth 模块与健康探针**

架构 §1.1 的原设计即「三层后端（路由-服务-仓储）**+ 独立 auth 模块**」：auth 自成表边界（`sessions` / `admin_account`），不经过 `repositories/`，是**刻意设计而非历史遗留**。已合入的下列直接 SQL 因此合规：

| 位置 | 用途 | 判定 |
|---|---|---|
| `app/auth/session.py` | sessions 表的 INSERT / SELECT / UPDATE / DELETE | ✅ 合规（auth 模块表边界） |
| `app/auth/bootstrap.py` | `admin_account` 的 SELECT / INSERT | ✅ 合规 |
| `app/routers/health.py` | 探针 `SELECT 1` | ✅ 合规（不触业务数据） |
| `app/services/job_runner.py` | 直接 UPDATE jobs 的 `snapshot_id` | ⚠️ **不在豁免范围**——见收口要求 |

- **豁免范围仅限 `app/auth/` 与健康探针**，不扩大到其他业务服务；
- **收口要求**：`job_runner.py` 对 jobs 表的写入应收敛到 `job_repo.py`（🟡 Suggestion，非 🔴；收敛后 A1 恢复完整适用）；
- **新增代码不得援引此豁免**——新业务模块一律走 `repositories/`。

**A2 豁免 —— 前缀字面量的两个合法出处**

| 位置 | 为何合法 |
|---|---|
| `app/constants.py` | 前缀白名单的**唯一出处**（`RESTORE_ALLOWED_PREFIXES` 等），本就该定义字面量 |
| `app/exclusions.py` | `ExclusionRules` 按模式派生排除集，`HOST_PREFIX = "/host"` / `SOURCES_PREFIX = "/sources"` 是**模式派生的输入**，不构成「绕过 PathMapper 做路径转换」 |

A2 的**实质红线是「路径转换只能发生在 PathMapper」**，而非「字符串不得出现」。上述两处不构成转换，属豁免范围；**其余位置硬编码前缀 = Blocker**。

| # | 检查项 |
|---|---|
| C1 | **任务互斥**：同仓库 running/pending 互斥判定正确；手动冲突 409、scheduled 冲突记 cancelled + audit 不排队——两条路径不得混淆（§6.4） |
| C2 | **状态机合法性**：jobs 状态转换只允许 §5 定义的方向；异常路径必须收敛到 `failed`，不允许任务停在 running 悬空 |
| C3 | **asyncio 竞态**：`_repo_lock` 的 acquire/release 配对；cancel 与正常终态的竞态（cancel 时任务已自行结束）有处理；`asyncio.create_task` 持有引用防 GC |
| C4 | **事件循环阻塞**：CPU 密集（`--json` 逐行解析）与阻塞 IO（os.stat 批量比对）必须在 `to_thread`，不得裸跑在协程里 |
| C5 | **容器重启恢复**：改动 JobRunner/shutdown 路径时，`recover_on_startup`（running+pending → interrupted、补跑判定、AUTO_UNLOCK）语义不得破坏（§6.5 P1 裁决） |
| C6 | **错误响应契约**：错误码与 HTTP 状态映射以 `errors.py` 为唯一映射点；不得在路由里裸 `raise HTTPException` 返回未登记的 code |
| C7 | **破坏 API 契约**：已定案端点（E01–E32）的请求/响应字段删除或改名需走文档修订，PR 内直接破坏 = Blocker |

### 3.2 🟡 Suggestion 清单

- **测试缺口**：新逻辑没有对应测试。特别关注——解析器改动 fixture 先行；状态机转换表驱动；API 集成测试用 dependency_overrides mock restic 子进程；前端 composable 用 mock EventSource。
- **错误处理**：吞异常（裸 `except: pass`）、异常后状态不回滚（DB 写了 pending 但任务没起）、`E31 dry-run` 类"非 0 退出要 200 + error 字段明示原因"的约定未遵守。
- **性能**：snapshots/文件树未分页或游标；进度落库无节流（<1s 间隔，写放大 R5）；前端大列表未用虚拟滚动（n-data-table `virtual-scroll` / `useVirtualList`）；循环内 await N 次单查可合并。
- **i18n**：硬编码文案（作者自查漏网时审查补位）。
- **可读性**：命名与领域术语不一致（如把"展示路径"写成"原始路径"）、一层函数同时干两件事、魔法数字（超时/阈值应进 settings/constants）。
- **依赖**：新增依赖需在 PR 说明选型理由并锁定版本（后端 `uv.lock`、前端 `pnpm-lock.yaml`）；禁止引入与既有选型重叠的库（如再引一个 ORM）。
  > **现状提示**：后端当前**尚无 `uv.lock`**、Dockerfile 用 `pip install --no-cache-dir .`；前端由 **pnpm** 管理（`frontend/pnpm-lock.yaml` + `pnpm-workspace.yaml`，`nodeLinker: hoisted`）。补 `uv.lock` 并改 Dockerfile 为 `uv sync --frozen` 属待办（🟡），归档前请勿宣称依赖已完全锁定。
- **错误码登记（反向检查）**：C6 只管「不得返回未登记 code」，还需正向同步——**新增 `constants.py` 的 `ERROR_STATUS` 条目时，必须同 PR 更新架构文档 §5.0 的错误码表**。当前 `ERROR_STATUS` 有 20 条，架构 §5.0 仅列 14 条（缺 `RESTIC_FAILED` / `POLICY_WRITE_CLOSED` / `READONLY_KEY` / `PASSWORD_WRONG` / `CSRF_ORIGIN` / `BOOTSTRAP_REQUIRED`），待补（🟡）。

## 4. 审查流程

### 4.1 分支与提交约定

```
main ── 保护分支，仅经 Owner 审查后合并，CI/本地检查全绿 + 审查通过才可 merge
  └─ dev ── 集成分支，日常提交汇集于此
       └─ feat/<topic> 或 fix/<topic> ── 特性分支，按特性拆 commit（Conventional Commits）
```

> **与仓库实况对齐（2026-10-11 复核）**：本仓库目前实际只有 `main` 与 `dev` 两个分支，无 `feat/*` 分支、无 PR 记录，P1 交付走的是 `dev → main` 直接合并（如 `a5d2d8c`）。上图的 `feat/*` 与 PR 是**目标形态**，尚未启用；启用前 §4.4 的「PR ≤400 行」按**单次合入 `dev` 的 diff**度量。

- 发布由 git tag 触发（双版本 `restic-web:<应用版本>-restic<restic版本>`），审查人确认 tag 前变更已经过完整审查；
- 本地 commit 不自动 push；推送由负责人统一执行。

### 4.2 三段式工作流（engineer → QA → owner）

本项目采用三段提交工作流，审查机制嵌入其中：

| 阶段 | 职责 | 审查动作 |
|---|---|---|
| ① Engineer 实现 | 按文档实现 + 自测，提交特性分支 | 作者完成 §2 自查清单后发起审查 |
| ② QA 独立验证 | 独立跑测试、复现验证，**核对自述与 git status/diff 一致**，确认测试真实覆盖缺陷场景（trust but verify） | 出具验证报告：通过/缺陷清单 |
| ③ Owner 审查合并 | 按 §3 标准逐条审查，Blocker 清零后由团队负责人（`restic-web-dev <dev@local>`，与 git 身份一致）合并入 `dev`/`main` | 最终合并裁决 |

> **「拆分提交」的归属澄清**：拆分应在**实现侧完成**——Engineer 实现时就按特性把改动组织好，Owner 负责**审查并决定是否合并/push**，不负责事后替实现者拆分。历史版本「由 Owner 按 Conventional Commits 拆分提交」的表述与「代理不自行提交」冲突（AI 只产出改动清单，无法表达 commit 边界，实际会退化为单 commit 塞入），v1.1 已更正。

### 4.3 审查执行步骤（审查人视角）

1. **先看全局**：PR 描述 → diff 统计 → 改动是否触碰 §3.1 红线区域（auth/、restic.py、PathMapper、repositories/、中间件、迁移 SQL）。触碰红线的 PR 优先级最高、逐行审。
2. **再钻细节**：逐文件按 🔴→🟡→💭 顺序记录意见，一次给全。
3. **验证测试**：测试是否真的覆盖了本次改动的行为（不是只看数量）；解析器 PR 必须看到新 fixture。
4. **给出结论**：`Approve` / `Request Changes`（有 🔴 或未协商的 🟡）/ `Comment`（仅 💭）。
5. **复核**：作者修改后审查人确认所有 🔴 已解决、🟡 已处置（修复或记 issue），不重复开新意见。

### 4.4 PR 尺寸与时限约定

- **建议单次合入 ≤ 400 行 diff**（豁免口径：仅 `tests/**` 与 `tests/fixtures/**` 路径不计；**单个非测试文件 >400 行本身即触发拆分**，防止新建 `test_helpers.py` 夹带）；超大变更拆分或先出设计摘要再出代码；
- **🔴 须在同一会话内闭环**；常规变更首轮 48h 内完成——本仓库为单维护者（`restic-web-dev`）+ AI 代理协作，原「🔴 24h / 常规 48h」时限在无 PR 流程下不可执行，跨会话遗留的未处置 🔴 视为阻塞项；
- 意见分歧由 Owner 裁决；裁决结果若涉及架构决策变更，须同步回写架构文档（如 §1.3 决策表）再合并。

## 5. 审查评论格式模板

```
🔴 **安全：路径越界风险**
sources.py 第 N 行：用户传入的 path 未过 PathMapper.validate 直接拼进 restic ls 参数。

**Why:** 传入 `path=../../etc` 可浏览白名单外目录，突破 /host 前缀隔离（方案 §6 注入防护）。
```

## 7. 与 CI 的分工边界

| 机器把关（CI 门禁） | 人工把关（本规范） |
|---|---|
| ruff / eslint / vue-tsc 静态检查 | 安全设计正确性（S1–S8） |
| pytest（fixture 回归 / 状态机 / 迁移幂等 / API 集成） | 架构红线纪律（A1–A6） |
| vitest（composable / ConfirmGate / api 层） | 测试是否覆盖真实缺陷场景 |
| 镜像构建 | API 契约演进、审查裁决、合并决策 |

CI 绿 ≠ 可以合并：CI 只证明"机器能查的都过了"，§3.1 的红线必须人工确认。

> **过渡期说明（2026-10-11 复核）**：仓库**尚未落地 CI 配置**（架构文档 §10.2 已定义流水线，`.github/workflows` 待创建），**且前端尚未接入 eslint 与 vitest**（`frontend/package.json` 无 `lint` script、无 `eslint`/`vitest` 依赖，无任何 `*.spec.ts`）。CI 与前端 lint/单测就绪前，左列检查由**作者本地执行、QA 在验证阶段复核**：
>
> ```bash
> # 后端（backend/，uv；本机 uv 不在 PATH 时用 .venv/Scripts/python -m ...）
> uv run ruff check app tests
> uv run pytest
>
> # 前端（frontend/，**用 pnpm，非 npm** —— 仓库前端依赖由 pnpm 管理，锁文件为 pnpm-lock.yaml）
> pnpm run typecheck     # vue-tsc --noEmit
> pnpm run build         # vue-tsc --noEmit && vite build
> ```
>
> **不要执行** `npm run lint`（script 不存在）、`npx vitest run`（依赖未安装）、`eslint .`（未接入）——这三条是本规范历史版本失实之处，已于 v1.1 更正。CI 与前端 lint/单测落地后，本节自动恢复为纯机器门禁，届时再把 eslint / vitest 写回本表左列。
