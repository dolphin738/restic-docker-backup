# 暂缓存档：密钥托管架构

> 版本：v1.0（2026-11-04）｜状态：**暂缓（暂不实施）**——评估已完成，但结论**未最终否决**：当前判定为「provider 抽象收益不足」，代之以零代码方案
> 适用范围：`enc:v2:` 密钥源（`<passfile_root>/<repo_id>/password`）的托管方式评估。
> 暂缓原因：评估后判定 **provider 抽象层当前收益不足**；同一收益可由 `passfile_root` 迁出 `/data` 零代码达成。本文件保留全部评估过程与实测数据，防止将来重复调研。
> **重启条件**：① `/data` 仍会被单独拷走或异地同步；② 需要接入外部 KMS；③ 出现多环境/多形态密钥源需求。任一成立即重新评估。
>
> **本文不是现行契约**：文中的 provider 清单、Protocol 设计均为**暂不实施的方案**，实施前必须重新评估（尤其须先确认 `/data` 是否仍会单独拷走）。

## 1. 问题

`crypto.py` 把仓库密码文件硬编码成 `enc:v2:` 的**唯一密钥源**：

| 事实 | 出处 |
| --- | --- |
| `enc:v2:<base64(nonce / ciphertext / tag)>` | `backend/app/services/crypto.py:10` |
| 密钥取自 `path.read_bytes()` | `backend/app/services/crypto.py:166-179` |
| `data_dir=/data`、`passfile_root=/data/repos`、`db_path=/data/restic.db` | `backend/app/settings.py:38,50,95` |
| 敏感键范围 `SENSITIVE_PREFIXES = ("cred.",)` + 精确键 | `backend/app/services/crypto.py:52-65` |

**密钥与锁同盘**：`enc:v2:` 的密钥源与 `restic.db` 同在 `/data`。整包拷走 `/data` 即同时拿走锁与钥匙。

项目已有「分开保管」纪律，但**只管 restic 仓库口令**：`docs/云端仓库安全基线.md:115,492`、`docs/全站数据备份与恢复设计方案.md:475`。该纪律对 `enc:v2:` 密钥源**形同虚设**——应用必须自动读它跑定时任务，不可能离线。

## 2. 密钥托管的实质意义（先钉死目标，否则会误判）

### 2.1 目标不是「不落盘」

评估初期曾以「让密钥不落盘」为目标，**该目标在 compose 部署下不可能达成**（见 §4.1）。若以此为目标，结论必然是「做什么都没用」。

真实目标是：**让 `/data` 被拷走时，里面没有钥匙。**

### 2.2 能做到的三件事

| 收益 | 说明 | 强度 |
| --- | --- | --- |
| **切断「一次拷贝同时拿走锁和钥匙」** | 现状 `passfile_root` 默认 `/data/repos`，与 `restic.db` 同卷；备份一次 `/data` = 锁 + 钥匙一起走 | **唯一实质收益** |
| 口令可换，不必重加密全部数据 | 换密钥源文件即可 | 弱（本项目换密钥需求低） |
| 消除「密钥由应用自管」的收入面 | 把「谁提供密钥」变成部署决策 | 仅在接 KMS 时有意义 |

### 2.3 做不到的两件事

| 做不到 | 原因 |
| --- | --- |
| 防整盘泄露 | compose 下 secret 就是宿主机文件（§3.1 实测）；swarm 下 manager 的 Raft 日志是否留副本**未实测** |
| 防容器内进程 | 口令最终必须进入读写它的进程；能执行命令者照样可取 |

### 2.4 因此判断成立的前提

只有一种情况密钥托管有价值：**`/data` 会被单独拷走或异地同步**。

| 场景 | 价值 |
| --- | --- |
| `/data` 单独备份 / rsync 到 NAS | **有**（且这正是《全站数据备份与恢复设计方案》覆盖的场景） |
| 整机镜像 / 整盘窃取 | **无** |
| 单机自用、无异地同步 | **接近无** |

## 3. 部署形态：两种形态的密钥通道不同

项目有两种部署形态（`backend/app/services/deploy_mode.py`，`DEPLOY_MODE=docker|host|auto`，`constants.py:65-71`）：

| | Docker | Host |
| --- | --- | --- |
| 浏览根 | `/sources` | `/` |
| 安全边界 | 挂载隔离 | deny 前缀（`/proc` `/sys` `/dev` `/run` + `repo_root` + `data_dir` + `passfile_root`） |
| 是否有容器运行时 | 有 | **无**（裸进程直跑） |

**关键结论**：Docker Secrets 与 K8s Secret 都依赖容器/编排层，**host 形态完全不可用**。因此任何 seal 方案若只写 Docker Secrets，host 部署的用户会用不了。

### 3.1 各通道跨形态可用性

| 通道 | Docker | Host | 备注 |
| --- | --- | --- | --- |
| Docker Secrets | ⚠️ 可用但**落盘** | ❌ | 见 §4.1 实测 |
| K8s Secret | ✅ 挂载 | ❌ | 依赖编排 |
| **`0600` 文件** | ✅ | ✅ | **唯一两种形态都成立的载体** |
| env | ⚠️ `/proc/<pid>/environ` 可读 | ⚠️ 同 | 子进程全部继承 |

这也解释了为什么默认实现必须是文件型：项目已在用——`backend/app/utils/passfile.py:77` `os.chmod(tmp, 0o600)`，从不区分 deploy_mode。

## 4. 关键实测（决定了后续全部判断）

### 4.1 Docker Secrets 在 compose 下**仍然落盘**

实测环境：WSL2 Debian，Docker Compose v5.6.0，`alpine:3.20` 容器。

```
D:\ on /run/secrets/via_secret type 9p (ro,noatime,aname=drvfs;path=D:\;...)
-rwxrwxrwx 1 root root 14 via_secret
VIA_ENV=mypassword123          <- /proc/1/environ 明文可读
```

**结论**：compose 模式的 secret 经 9p bind mount 指回**宿主机源文件**，不是 tmpfs。因此「用 Docker Secrets 就不落盘」这个预期**在本项目的 compose 部署下不成立**。

| 来源 | 是否落盘 | 说明 |
| --- | --- | --- |
| Docker **swarm** 的 `secrets:` | 内存（容器内 tmpfs） | 必须 swarm 模式 |
| **compose** 的 `secrets:` | **落盘** | 实测：源文件就在宿主机 |
| env 写死在 compose | **落盘** | compose 文件本身明文 |
| `*_FILE` 指向宿主机文件 | **落盘** | 与 compose secret 本质相同 |

### 4.2 env 在被 fork 的子进程里全部继承

`exec_rclone`（`backend/app/services/rclone.py:91-96`）不传 `env=` → 继承父进程环境；`restic.py:389-422` 显式 `env = dict(os.environ)` 后追加白名单。因此 env 形式的密钥会一路传给 restic / rclone 子进程。

### 4.3 LibSecret / gnome-keyring 在本项目两种环境下均不可用

| 环境 | dbus-daemon | gnome-keyring | secret-tool | libsecret.so | `org.freedesktop.secrets` |
| --- | --- | --- | --- | --- | --- |
| Alpine 3.24 容器 | ❌ | ❌ | ❌ | ❌ | ❌ |
| WSL Debian（host 代表） | ✅ | ❌ | ❌ | ❌ | ❌ |

Duplicati 的 `LibSecretLinuxProvider.cs` 硬性依赖该服务：`:39` `DefaultServiceName = "org.freedesktop.secrets"`、`:57` 可用性探测、`:140-141` `CreateAsync` + **`UnlockAsync()`**、`:132` 非 Linux 抛 `PlatformNotSupportedException`；`LibSecret/README.md` 明确要求 session bus 上有运行中的 Secret Service。

## 5. 评估过的 provider 清单（暂不实施，仅供参考）

```
SecretProvider (Protocol)
+-- FileProvider      (默认)   <- 读 0600 文件；跨形态、零依赖、无需解锁
+-- EnvProvider       (兜底)   <- 带「安全性较弱」告警
+-- DockerSecretsProvider      <- 仅 docker 形态
+-- KMS 接入点        (预留)   <- 仅接口定义，无实现
```

### 5.1 被明确排除的三个

| Provider | 排除理由 |
| --- | --- |
| **Windows 凭据管理器** | 本项目部署形态不支持 Windows：`backend/app/constants.py:75` `MOUNTINFO_PATH = "/proc/self/mountinfo"` 是 Linux 专属；`AGENTS.md:45` 与 `docs/部署指南.md:724` 均记录 Windows 下 restic/rclone 全部子进程操作 500。Windows 在本项目是**开发机**（`AGENTS.md:136`），非运行环境 |
| **LibSecretProvider** | 见 §4.3，两种环境均无 Secret Service；且 `UnlockAsync()` 需人工解锁，与无人值守冲突 |
| **PassProvider**（Unix `pass`） | 依托第三方 CLI（`UnixPassProvider.cs:43` `Key => "pass"`、`:192-200` `Process.Start` + `ArgumentList.Add("show")`），非 OS 密钥库；需用户装 `pass`+`gpg`，无 gpg-agent 缓存时会被 passphrase 卡住；与 FileProvider 收益重叠 |

## 6. Protocol vs 完整插件体系的区别

| 维度 | 定义 Protocol | 完整插件体系 |
| --- | --- | --- |
| 形态 | 一个抽象基类 + 若干实现，选择逻辑在代码里 | 动态加载外部模块，用户可自行扩展 |
| 工作量 | 80–150 行（1–2 天） | 2–4 周 + 持续维护 |
| 谁能加 provider | 项目开发者 | 任何用户 |
| 加一个要做什么 | 提 PR | 自己编译插件 |
| 失败模式 | 简单（构造时选一个） | 动态加载、版本兼容、降级语义 |
| 适用产品 | 单一组织的服务器工具 | 有插件生态的通用平台 |

Duplicati 选择插件体系的实证成本：`DynamicLoader/SecretProviderLoader.cs`（动态加载 DLL）、`SecretProviderModules.cs`（模块注册）、12 个 provider 各带 `Key`/`DisplayName`/`ICommandLineArgumentMapper`、4 个命令行参数（`--secret-provider` / `--secret-provider-cache` / `--secret-provider-pattern` / `--disable-default-secret-provider`）、`Server/Program.cs:1176-1270` 四级降级链、3 个独立测试工程、专用 CI（`.github/workflows/secretprovidertests.yml`）。

**判断**：本项目是自托管服务，provider 集合由项目自己决定（仅 3–4 个），无第三方生态需求 → 插件体系明确不适用。

## 7. 对照 Duplicati 的可复用结论

Duplicati 的 `enc-v1:` 与本项目 `enc:v2:` 同构（`EncryptedFieldHelper.cs:82` `HEADER_PREFIX = "enc-v1:"`、`:87` `SETTINGS_ENCRYPTION_KEY`、`:116/:139` 密钥缺失/不匹配专用异常、`:76/:163` 密钥黑名单）。其最有价值的三条经验：

1. **库已加密时绝不重新生成密钥**（`Server/Program.cs:1219` 注释）——否则新密钥解不开旧数据；
2. **`--require-db-encryption-key` 强制开关**（`:1254`）——把「可以裸跑」变成「可以选择不允许裸跑」；
3. **密钥轮换它自己也没做**（`WebserverCore/Services/RemoteControllerHandler.cs:93` `// TODO`）。

## 8. 当前结论：暂不实施 provider 抽象

**理由**：密钥托管的实质收益只有一条——**切断「一次拷贝同时拿走锁和钥匙」**。而这条收益可由零代码方案达成：

`settings.passfile_root`（`backend/app/settings.py:50`，环境变量 `PASSFILE_ROOT`）**已经是可配置项**。把它迁出 `/data`（例如挂到另一个卷），备份 `/data` 时自然不含密钥，**无需 provider 抽象、无新故障模式、无代码改动**。

| 场景 | provider 抽象的额外价值 |
| --- | --- |
| `/data` 单独备份/异地同步 | **无**（`passfile_root` 迁出已覆盖） |
| 整盘/整机泄露 | **无**（compose 下 secret 也落盘，见 §4.1） |
| 容器内进程被控 | **无**（口令最终必须进进程） |
| 将来接 KMS | 有（但届时有需求再加 Protocol 也不迟） |

## 9. 替代方案（零代码，建议实施）

| 方案 | 成本 | 收益 |
| --- | --- | --- |
| **`passfile_root` 迁出 `/data`** | 零代码（改 compose + 文档） | 切断「锁与钥匙同卷」 |
| 文档写明「`/data` 整包 = 锁 + 钥匙」 | 零 | 让运维知情 |
| 密钥缺失/不匹配时明确报错 | 小 | 避免静默降级 |

## 10. 口令通道对比：env vs `*_FILE` vs `RCLONE_PASSWORD_COMMAND`

### 10.1 env 与 `*_FILE`

| 维度 | env | `*_FILE` |
| --- | --- | --- |
| 泄露面 | `/proc/<pid>/environ` 明文；`docker inspect` 可见；**子进程全部继承** | 只暴露给主动读它的代码；子进程不继承 |
| 误打进日志 | 极易（打印整个环境时） | 较难 |
| 是否落盘 | 取决于来源；写死在 compose 里即明文落盘 | 是，必然落盘 |
| 改口令 | 必须重建容器 | 改文件即可，重启进程生效 |
| 权限控制 | 由 Docker 层管理 | 可用 `0600` 精确控制 |
| 实现复杂度 | 零（`os.environ`） | 低（读文件 + 去尾部换行） |
| 与 Secrets/K8s 兼容 | 需先导出 | **原生兼容**（两者都挂文件） |

**结论**：`*_FILE` 更优，三项理由——① `exec_rclone` / `restic` 都会 fork 子进程，env 会一路带下去，`*_FILE` 不会；② Docker Secrets / K8s Secret / systemd `LoadCredential` 全都挂文件；③ 改密钥不必重建容器。

**但必须承认**：只要还是 compose 部署，密码**必然在宿主机落一份**。这不是 `*_FILE` 的缺陷，而是 compose 的局限。真正的内存态需要 swarm 或外部 KMS。

### 10.2 `RCLONE_PASSWORD_COMMAND`（rclone 场景的首选）

env 唯一胜出的场景是**工具只认 env 变量名**。rclone 提供 `--password-command` / `RCLONE_PASSWORD_COMMAND`：给它一个**能输出口令的命令**，读文件、读 secrets、查 KMS 都行。

因此可插拔性**下放给运维脚本**，不必写进代码：

```
运维提供脚本（内容：cat /run/secrets/xxx  或从密码管理器取）
        |
        v
RCLONE_PASSWORD_COMMAND=<脚本路径>
        |
        v
restic 继承 env -> fork rclone serve restic --stdio -> 子进程读到 -> 解密 conf
```

实测依据见 #2（已关闭票之外的独立实测）：加密 conf 后 `init` / `backup` / `snapshots` 三条链路全通；**口令完全缺失**时会尝试交互读取、挂到 60 秒超时并报 `context deadline exceeded`（误导性错误），**口令错误**则快速失败且报错准确——因此前置校验应判断「是否配置了口令」，而非「口令是否正确」。

## 11. 待验证（若将来重启本议题）

1. Docker secrets 在 **swarm 模式**下是否真为 tmpfs；manager 的 Raft 日志中是否留存副本。
