## 0. 结论先行

**既有「配置迁移」（批次 E，`services/config_transfer.py` + `routers/ops.py` 的 `POST /api/config/export|import`）不能满足本需求**，必须新增独立通道并由其取代。三条硬理由：

1. **它明确不搬仓库密码文件**（`docs/配置迁移导入导出说明-2026-10-22.md:43`）。而本项目的 **restic 仓库密码就存在该文件里**——`services/restic.py:392` 把 `RESTIC_PASSWORD_FILE` 指向 `settings.passfile_path(repo_id)`；且该文件同时是 `enc:v2:` 凭据的**密钥源**（`services/crypto.py:145-179` 用密码文件内容经 HKDF-SHA256 派生密钥）。少了它，新机既打不开 restic 仓库，也解不开库里的加密凭据——**不是「配置不全」，是「恢复不了」**。
2. 它只搬 `behavior.* / notify.* / cred.*` 三族配置键，`timezone`、`log.level`、`db.busy_timeout_ms`、`schedule.*`、`dump.*`、`retention.*`、`metrics.token`、`security.cred_encryption` 等**全部不进包**（`config_transfer.py:65-66`）。
3. 它的导入是 **merge 语义**（仓按 id、任务按 `(repo_id, name)` 匹配，默认跳过冲突），并把任务 `id/tag` 剔除。全站恢复是**整机替换**语义，且**必须保留任务 id**——restic 快照上打的是 `task-<id>` tag（`task_repo.py:302-305`），换 id 会让 `forget --tag` 的集合算错、历史快照变孤儿。

**范围**：本功能只备份 **本 Web 应用自身的配置与设置类数据**，**明确排除 restic 产生的备份数据**（仓库、快照、索引、缓存）。

## 1. 数据范围

### 1.1 结论

纳入 = `/data/restic.db` 中**五张表的逻辑内容** + `<passfile_root>/<repo_id>/password` **全部文件** + （可选）`rclone.conf` + 其形态表 + （条件性）**rclone conf 加密口令** `<passfile_root>/rclone.pass`。排除 = 全部 restic 仓库/快照/缓存/源目录，以及全部运行期与历史数据。

**不备份 SQLite 物理文件**：只搬逻辑行。理由——① 物理文件会连带 `jobs`/`audit_logs`/`sessions` 与 `-wal/-shm` 一起走；② 目标机的 schema 版本由本机迁移器决定，跨版本靠列映射（§2.4），不靠二进制兼容。

### 1.3 明确排除清单

| 排除项 | 位置 | 理由 |
|---|---|---|

### 1.4 `repo_tombstones` 通俗说明（D2 的依据）

**一句话：它是「死亡证明」——记录「这个仓库曾经存在过、已经没了」，但不含任何能把它救回来的东西**（不存密码、不存凭据、不存数据）。

> 类比：你家有个车库（restic 仓库）。不想要了，先**封起来**（= `repos.deleted_at` 置位，叫「归档」，30 天内可一键解封）。封存到期后车库拆掉、**车也一起没了**（密码文件 + 凭据被清）。车库没了，账本上仍留一行：「B2026 号车库，2026-10-01 建，2026-11-05 拆，当时停了 12 辆车」——**这一行就是墓碑**。它只让你知道「这儿曾经有过什么」，不能把车找回来。

表结构见 `0009_repo_archive.sql:30-39`：`repo_id/name/type/url_display/archived_at/snapshot_count/data_destroyed/released_at`——全是元数据，无密钥。

**不纳入的三条理由**：① 无恢复价值（不含密码/凭据/数据）；② 会制造假信息（新机没见过这个仓库却被记成「已销毁」，污染归档页）；③ 包内已有真信息——`repos.deleted_at` 已纳入（§1.2-2），墓碑是它的下游衍生物。

> 出处：`0009_repo_archive.sql:4`「**记录会过期，数据永不自动删**」——墓碑属于「记录」，不属于「数据」。

### 1.5 「无活跃作业」的定义（D3 的依据）

**结论：`jobs` 表里不存在 `status` 为 `running` 或 `pending` 的行。** 定义在 `constants.py:26`（`ACTIVE_JOB_STATUSES = ("running", "pending")`），判据接口 `JobRepo.list_active(repo_id=None)`（`job_repo.py:68-85`，`None` = 不限仓库）。

通俗讲：**当前没有正在跑或正排着队的 restic 操作**——backup / restore / forget / check / unlock / init / dump / prune / repair / recover / copy。

**为什么必须卡**：

| 导入动作 | 若此刻有 backup 在跑 |
|---|---|
| 覆写 `<passfile_root>/<repo>/password` | 子进程的 `RESTIC_PASSWORD_FILE` 指向它，密码中途换掉 → 该次备份收尾 `Fatal: wrong password`，已传数据块成孤儿 |
| `DELETE FROM jobs` + `DELETE FROM backup_tasks` | 作业行被删但子进程还活着 → 写终态找不到行，SSE 推不动，日志变无主孤儿 |

`pending` 也算活跃：调度器随时会把它拉起来，同样被撞。

**代价**：用户须先等作业结束或到任务页取消。故 `inspect` 报告（§4.2）要**列出当前活跃作业**（任务名 + 类型 + 开始时间）并给「去任务页取消」入口。

### 1.6 关键陷阱（实现必须处理）

1. **`source='env'` 不能原样搬**：源机由 `AWS_*` / `RESTIC_REPOSITORY` / `LOG_LEVEL` 覆盖的键在库里是 `source='env'`（`env_sync.py:47-71`）。新机若无该 env，启动期 `sync_env_overrides` 会**删除**这些键（`env_sync.py:191-195`）→ 静默丢配置。**导入一律归一为 `source='ui'`**，`repos.url_source/host_tag_source` 同理，并在报告中列出被归一的键。
2. **凭据密文不跨机搬**：`enc:v2:` 由旧机密码文件派生。**解密后的载荷内**一律存**明文**（载荷本身经 §2.2 的 AES-256-GCM 加密），导入时按目标机 `ConfigRepo` 的写侧加密重新落库（`config_repo.py:239-245`）。
3. **任务 id 必须保留**（与 `config_transfer.task_values_from_pack` 的剔除策略相反）：`task-<id>` 是 restic 快照 tag（`task_repo.py:302-305`）。
4. **导出不完整的包最危险**：任一在用仓库的密码文件缺失/不可读 → **拒绝导出**（fail-closed，§3.3）。
5. **rclone conf 加密态必须与口令同进同出**（v1.5 新增）：conf 可能处于 rclone 自身加密态（判定 `services/rclone.py::conf_encrypted`，零子进程）。**只搬 conf 不搬口令** → 目标机所有 `rclone:` 远端不可达且**导入不报错**（启动自检发现 conf 已加密但 `rclone.pass` 缺失，只记 `RCLONE_CONF_LOCKED` 文案）——这是本方案里唯一「导入成功、事后静默不可用」的路径，故 §1.2-8 与 #6 强绑定。反之，目标机**原本加密**而包内 conf 是明文：写回后 conf 变明文、而 `RCLONE_PASSWORD_COMMAND` 仍指向旧口令文件 → `rclone` 会因「口令给了但 conf 未加密」而行为不明（无对应分支，代码不覆盖）。**导入必须在 §4.3 第 6 步硬校验两侧加密态一致**（不一致即拒），这是 Q2 的一部分，不是可选加固。
6. **`RESTIC_PASSWORD_FILE` 全局覆盖**：`settings.passfile_path()` 会把所有仓库指向同一个文件（`settings.py:156-179`）。包内按 `repo_id` 记录逻辑键 + 内容 + sha256，**与路径解耦**；导入写到目标机自己的 `passfile_path(repo_id)`；目标机也设了覆盖时写到该路径并提示「全局共用模式」。

## 2. 文件格式

### 2.1 结论

单文件 JSON：**最小明文头 + 一个 AES-256-GCM 加密载荷**。不做压缩、不做「明文段 + 加密段」双层——全站包头部以下**全部内容**都敏感（含仓库密码、admin 哈希、全部凭据、rclone conf）。头部用 **AAD 绑定**，篡改 `version` 即 GCM 校验失败。

### 2.2 外层结构

```jsonc
{
  "format":      "restic-web-site-backup",   // 与旧配置迁移包 "restic-web-config-export" 区分
  "version":     1,                          // 包格式版本（结构变更才 +1）
  "created_at":  "2026-11-04T02:11:07Z",
  "encryption": {
    "algo": "PBKDF2-HMAC-SHA256",
    "iterations": 600000,                    // 与 config_transfer._PBKDF2_ITERATIONS 同值
    "salt": "<b64 16B>",
    "cipher": "AES-256-GCM",
    "aad":  "<canonical-json-of-header-minus-aad>"
  },
  "payload": "<b64(nonce[12] || ciphertext||tag)>"
}
```

- **不压缩**：内容 KB 级（若干仓库 + 任务 + 配置 + 每仓 ~32 字节密码文件 + 一个 conf），gzip 无收益，反多一层解析面。若未来纳入审计归档，升 `version=2` 再引入。
- **加密强制**：不提供「无口令导出」。包内含 restic 仓库密码 = 整个备份数据的万能钥匙。口令下限 `config_transfer.PASSWORD_MIN_LENGTH = 10`（`config_transfer.py:63`）。

### 2.4 版本与跨版本兼容策略

结论：**两个版本号分离**——`version`（包结构）与 `schema_version`（DB 结构）。导入接受集合而非严格相等（沿用 `config_transfer._SUPPORTED_PACK_VERSIONS` 的「集合而非相等」口径；该常量当前为 `frozenset({1, 2})`（`config_transfer.py:48`），v1.4 引的 `:46-48` 是上下文行区间。**注意本方案的 `version` 独立于该常量**：`_SUPPORTED_PACK_VERSIONS` 管的是旧配置迁移包的 `version`，全站包用自己的 `_SUPPORTED_VERSIONS = frozenset({1})`，两者不共享）。

当前 `schema_version` 目标值 = **10**（迁移 `0001`–`0010`，`PRAGMA user_version = 10` 见 `0010_drop_dead_task_columns.sql:21`）。

| 情形 | 处理 |
|---|---|
| `format` 不符 | 422 `SITE_PACK_INVALID`；若 `format == "restic-web-config-export"` → 提示「这是旧版配置迁移文件，本功能不支持；请在原机用本功能重新导出全站备份包」（**D6：不兼容旧包**） |
| `version` 不在 `{1}` | 422 `SITE_PACK_INVALID`，message 带「请升级应用」/「请用新版导出」 |
| `schema_version > 当前` | 422 `SITE_SCHEMA_UNSUPPORTED`（**前置拒绝**：不解密、不写入） |
| `schema_version < 当前` | 允许，走**列映射表**：多余列丢弃并记 warning，缺失列取 `task_repo._SEED_DEFAULTS` / NULL（**模块级常量**，非类属性，`task_repo.py:43`；v1.4 误记为 `TaskRepo._SEED_DEFAULTS`）；`warnings` 进导入报告 |
| 载荷缺字段 / 类型非法 | 422 `SITE_PACK_INVALID`（结构严格校验，不猜） |

`app_version` 与 `source.deploy_env` 仅供诊断展示，不参与任何校验或恢复。

## 3. 导出

### 3.1 结论

`POST /api/site-backup/export` → 一次性返回文件流。一致性靠 **`BEGIN IMMEDIATE` 只读快照（纯 SQL、毫秒级）** + **事务外读密码文件与 rclone.conf**；**不需要停任务**（`jobs` 不进包、运行期列被剔除，§3.4）。

### 3.2 接口

```python
class SiteExportRequest(_Base):
    password: str = Field(min_length=10, max_length=256)
    include_rclone_conf: bool = True       # D1：默认勾上；UI 明写「含网盘授权令牌」

# POST /api/site-backup/export  → application/json 附件
# Content-Disposition: attachment; filename="restic-web-site-2026-11-04.json"
```

### 3.3 一致性与完整性

1. **DB 侧**：在一个 `Database.transaction()`（`BEGIN IMMEDIATE`，`database.py::Database.transaction`）内顺序 `fetch_all` **五张表**（config / repos / backup_tasks / admin_account / rclone_credential_forms）+ 取 `user_version` → 全量进内存 dict；事务内**不发任何非 SQL await**（A5 事务纪律）。
   > v1.4 写「六张表」把 `user_version` 算进了表——它是 `PRAGMA user_version` 标量（`database.py::Database.user_version`），不是表，本版更正措辞。
2. **文件侧**：事务结束后读 `<passfile_root>/*/password`、`resolve_conf_path(settings)`，**以及（conf 为加密态时）`<passfile_root>/rclone.pass`**。跨资源无原子性 → 在 `passfiles[].mtime_ns/sha256`、`rclone.conf_sha256`、`rclone.pass.sha256` 留证据，供导入后诊断。
3. **前置完整性检查（fail-closed）**：

```python
async def assert_passfiles_complete(settings, repos) -> None:
    missing = [r["id"] for r in repos if r["deleted_at"] is None
               and not settings.passfile_path(r["id"]).is_file()]
    if missing:
        raise SitePassfileIncompleteError(missing)   # 422 SITE_PASSFILE_INCOMPLETE
```

4. **降级键**：`ConfigRepo.list_all()` 返回 `degraded=True` 的行（密钥源失效）→ 写进 `warnings`，沿用 `config_transfer.py:218-222` 的 v2 `degraded` 思路。第 3 条已拒绝密码文件缺失，正常不出现。
5. **rclone conf 缺失**：`include_rclone_conf=True` 而 `resolve_conf_path()` 指向的文件不存在 → **不报错**，`included=false` + `warnings` 记「源机未配置 rclone.conf（可能未用 rclone 后端）」；`forms` 仍照搬。**conf 存在但不可读** → 前置 422，不静默产出残缺包。
6. **conf 加密态但口令缺失 → fail-closed**（v1.5，Q2 的必要配套）：`conf_encrypted(conf_path)` 为真而 `<passfile_root>/rclone.pass` 不存在或不可读 → **拒绝导出**（422 `SITE_PASSFILE_INCOMPLETE`，message 指明「源机 rclone conf 已加密但配置口令不可读，导出的包在新机不可用」）。理由与第 3 条同构：一个打不开 conf 的包 = 所有 `rclone:` 远端在目标机不可用，而导出侧是唯一能发现这件事的地方。**conf 为明文态时 `rclone.pass` 不采集**（`pass.included=false`），目标机也不会被写入多余口令。
6. **不阻塞活跃作业**：`jobs` 不进包、`last_run_at` 剔除（§3.4），导出与备份并发无害。

### 3.4 生成与下载


## 4. 导入

### 4.1 结论

三段式：**`inspect`（只读预检，零写入）→ `import`（单事务替换 + 文件回滚点）→ 热生效**。默认且唯一的落地语义是 `replace`；失败永不留下半成品。

### 4.2 接口

```python
class SiteInspectRequest(_Base):
    pack: dict
    password: str

class SiteImportRequest(SiteInspectRequest):
    mode: Literal["replace"]      # 只有一种；显式声明，防误调
    acknowledge: str              # 必须等于 pack["created_at"]（服务端二次确认，配合前端 ConfirmGate）

class SiteInspectReport(_Base):
    pack:     PackSummary
    target:   TargetSummary    # repos / tasks / config_keys / active_jobs / restic_available /
                               # passfile_writable / rclone_conf_writable / rollback_keep_count
    blockers: list[str]

class SiteImportReport(_Base):
    applied: dict[str, int]              # repos / tasks / config / passfiles / rclone_conf / forms / rclone_pass
    normalized_env_keys: list[str]
    warnings: list[str]
    rollback_dir: str                   # 本次回滚点相对路径（文件名，容器形态路径不出 API）
    logged_out: bool = True             # sessions 已清空，前端须跳登录页
```

### 4.3 文件校验顺序（每一步失败都不写任何东西）

| 序 | 检查 | 失败响应 |
|---|---|---|
| 1 | JSON 可解析、`format` 匹配 | 422 `SITE_PACK_INVALID` |
| 2 | `version ∈ {1}` | 422 `SITE_PACK_INVALID` |
| 3 | AAD 重算一致 + GCM 解密（错口令/篡改一律 GCM 失败） | 401 `PASSWORD_WRONG`（「口令错误或文件被篡改」） |
| 4 | 载荷结构 schema 校验（键集/类型） | 422 `SITE_PACK_INVALID` |
| 5 | `schema_version ≤ 当前 user_version` | 422 `SITE_SCHEMA_UNSUPPORTED` |
| 6 | 目标能力与**加密态一致性**：① `passfile_root` 可写（临时文件试写）；② rclone conf 父目录存在且可写（仅 `included=true` 时）；③ restic 二进制可执行；④ **`rclone.conf_encrypted` 必须等于目标机 `conf_encrypted(resolve_conf_path(settings))`**（v1.5，Q2 配套）——包内密文而目标机明文态、或包内明文而目标机加密态，一律拒绝 | 422，`blockers` 明示（④ 的 message：「包内 rclone conf 为<加密/明文>态，与目标机<明文/加密>态不一致，导入会使全部网盘远端不可用；请先在目标机调整 conf 加密态或更换包」） |
| 7 | **无活跃作业**：`job_repo.list_active()` 为空 | **409 `JOB_CONFLICT`**（D3 强制） |
| 8 | 目标已有数据 → 需 `mode=replace` + `acknowledge` | 409 `SITE_TARGET_NOT_EMPTY` |

### 4.4 覆盖策略（为什么只有 replace）

- **合并无法定义**：两台机器的 `admin_account`（单行 `id=1`）、`repos.default`、`config` 同名键都会撞；「哪边的时区算数」没有客观答案。
- **`replace` = 先清后插，全程单事务**。清表顺序受 `PRAGMA foreign_keys=ON` 约束（`database.py:105`）：
  1. `DELETE FROM jobs` —— **必须删**：`jobs.repo_id REFERENCES repos(id)` 且列 `NOT NULL`、无 `ON DELETE` 级联（`0003_multi_repos.sql:15`），不删 jobs 就删不掉 repos；
  2. `DELETE FROM backup_tasks` → `DELETE FROM repos` → `DELETE FROM config` → `DELETE FROM sessions` →（`included=true` 时）`DELETE FROM rclone_credential_forms`；
  3. `UPDATE admin_account`（单行覆写）；
  4. `INSERT repos` → `INSERT backup_tasks`（显式 id + `tag='task-<id>'`）→ `INSERT config`（预加密后的存储形态）→ `INSERT rclone_credential_forms`。

> **副作用明示**：replace 会清空目标机的 `jobs` 执行历史（不导出、也不保留）。`inspect` 报告的 `target` 摘要必须显示 jobs 行数，让用户确认前看见。

```python
# app/db/repositories/site_repo.py —— 新增仓储（A1：DB 访问只在 repositories）
async def replace_all(self, tx: Tx, state: dict) -> dict[str, int]:
    for sql in ("DELETE FROM jobs", "DELETE FROM backup_tasks", "DELETE FROM repos",
                "DELETE FROM config", "DELETE FROM sessions"):
        await tx.execute(sql)
    if state["rclone"]["included"]:
        await tx.execute("DELETE FROM rclone_credential_forms")
    for r in state["repos"]:            # 列名白名单校验，同 task_repo._assert_columns 口径（模块级函数，task_repo.py:308）
        await tx.execute("INSERT INTO repos "
            "(id,name,url,host_tag,url_source,host_tag_source,created_at,deleted_at) "
            "VALUES (?,?,?,?,?,?,?,?)", (...))
    for t in state["tasks"]:
        await tx.execute(f"INSERT INTO backup_tasks ({cols}) VALUES ({ph})", (...))
    for c in state["config"]:           # 存储形态已在事务外算好（明文/密文）
        await tx.execute("INSERT INTO config (key,value,source,updated_at) VALUES (?,?,?,?)", (...))
    await tx.execute("UPDATE admin_account SET password_hash=?, must_change=?, bootstrap_shown=1, "
        "bootstrap_password_hash=NULL, failed_attempts=0, lock_level=0, locked_until=NULL, "
        "updated_at=? WHERE id=1", (...))
    return {"repos": ..., "tasks": ..., "config": ...}
```

> **加密为什么在事务外做**：`ConfigRepo._maybe_encrypt` 需读密码文件（文件 IO），事务内不得有非 SQL await（`database.py:9-11`）。做法：新增 `ConfigRepo.encode_for_storage(key, value) -> str | None`（`_maybe_encrypt` 的公开薄封装），导入在事务外对每个敏感键预加密，事务内只落 SQL——**加密实现仍是唯一一份**。

### 4.5 失败回滚（跨「文件 + DB」两资源）

导入顺序刻意 **先文件、后 DB**：文件内容单一、体积极小，回滚代价最低；DB 有事务天然原子。

```
0  前置检查（§4.3 1–8）                              —— 失败：零写入
1  全量解密 + 结构校验（纯内存）                      —— 失败：零写入
2  事务外预加密 config 敏感值                          —— 失败：零写入
3  回滚点（D4：保留最近 3 份，可调）
   ├ 复制现有 <passfile_root>/**/password
   ├ 复制现有 rclone.conf（仅 included=true 且目标存在时）
   ├ 复制现有 <passfile_root>/rclone.pass（v1.5：仅目标机 conf 为加密态时）
   └ 写 /data/site-restore/<ts>/state.json = {"phase":"prepared"}
                                                    —— 失败：中止（旧文件未动）
4  原子写新密码文件（utils/passfile.write_passfile：0600 + os.replace）
   + 原子写新 rclone.conf（**按包内 conf_b64 原样字节写回**：加密态就是 rclone
     加密态、明文态就是明文，**不做解密/重加密转换**——加密态切换是用户
     在 rclone 配置页的显式动作（`/api/rclone/conf-encryption/*`），本方案只搬运。落盘 0600 与 rclone.conf 自身在 0600 的
     既有语义一致；混淆密码 / OAuth token / 密文都在文件里，权限不可省）
   + 原子写新 rclone.pass（0600 + 同目录 mkstemp + os.replace，**无尾随换行**，
     与 rclone_crypto._write_pass 的写法逐字对齐；仅包内 pass.included=true 时）
                                                    —— 失败：从第 3 步恢复 → 500，DB 未动
5  Database.transaction() → SiteRepo.replace_all(tx, state)
                                                    —— 失败：事务 rollback（DB 未变）
                                                             → 从第 3 步恢复文件 → 500
6  成功：state.json 改 "committed" → 热生效（§4.6）→ 审计 site.import → 返回报告
   按 settings.site_restore_keep_count（默认 3）裁掉更早的回滚点目录
```

**D4 的「3 份」具体是什么**：`/data/site-restore/<时间戳>/` 目录，里面只有两类文件——

```
/data/site-restore/2026-11-04T021107Z/
  ├─ passfiles/default/password            ← 每个仓库一个，32 字节左右
  ├─ passfiles/<其他 repo_id>/password
  ├─ rclone.conf                          ← （可选）几 KB～十几 KB
  ├─ rclone.pass                          ← （可选，v1.5）32 字节口令明文
  └─ state.json                           ← {"phase":"prepared"|"committed", ...}
```

体积估算：10 个仓库 × 32 B × 3 份 ≈ **960 B**，rclone.pass 再 +96 B；加上 conf 每份十几 KB → 3 份仍**几十 KB 量级**。只保留最近 3 个时间戳目录，第 4 个自动删除。**份数是 `settings` 可调阈值**（`site_restore_keep_count = 3`，默认值写 `constants.py`；不裸写在业务逻辑里，遵守 AGENTS.md「可调阈值不得裸写数值」），`<=0` = 不保留（不推荐）。

**崩溃窗口**：仅在第 4 步之后、第 5 步提交之前——盘上是「新密码文件（含新 rclone.pass）+ 旧 DB」，旧 DB 的 `enc:v2:` 密文按旧密钥解不开、且 conf 的加密态已随新包切换。三个文件（password / rclone.conf / rclone.pass）必须**在同一个第 4 步内成组切换**：任一个先落盘都会制造混合态（例如新口令 + 旧 conf = `RCLONE_CONF_LOCKED`）。兜底：`state.json` 写 `phase=prepared`；启动期在 lifespan 检测到未完成状态时**告警并指路** `/data/site-restore/<ts>/`，由人工决定「继续导入」还是「回滚文件」（不自动执行，避免二次破坏）。

### 4.6 导入后如何生效

| 变更项 | 生效方式 |
|---|---|
| `repos / backup_tasks / config / admin_account` | 立即（DB 已替换） |
| 调度器（cron / 时区 / 抖动） | `await app.state.scheduler.reload()`（同 `routers/config.py:187-193` 用法） |
| 日志级别 | `apply_log_level(await config_repo.get_value(LOG_LEVEL_KEY))` |
| SQLite 锁等待 | `db.apply_busy_timeout(int(...))` |
| restic 子进程时区 | `restic.set_timezone(await config_repo.get_value(TIMEZONE_KEY))` |
| 状态/快照缓存 | `invalidate_repo_status_cache()` + `invalidate_snapshot_catalog()` |
| **会话** | `sessions` 表已清空 → **当前请求结束后即 401**，前端须跳登录页（响应体先返回，再跳转） |
| **rclone.conf** | 文件已按包内字节覆写；`rclone` 子进程每次启动重读 conf，**无需重启**；报告提示「网盘授权已随包迁移」 |
| **rclone 加密口令 / `RCLONE_PASSWORD_COMMAND`**（v1.5） | 文件已写回后**必须在进程内重建 env**：`rclone_crypto._set_password_command_env()`（纯 `os.environ[...] = password_command_for(pass_path)`，无隐藏状态）、包内 `pass.included=false` 时调 `_clear_password_command_env()`。**只写文件不重建 env 会静默失效**——原 env 是启动期由 `main.py` 的启动自检算好的，指向的是旧口令文件路径与旧口令；复用该函数而非重算命令串，避免第二份口令命令构造实现 |
| 部署项（`DEPLOY_MODE`/`SOURCES_ROOT`/`PORT`…） | 不在包内，不生效 |
| ~~TLS~~ | **已废弃**：内置 TLS 于 2026-11-04 删除，`main.py` 的 `def main()` 恒纯 HTTP，无重启生效项 |

> 结论：**本方案无需重启容器**；只需前端在成功后跳登录页。
>
> **v1.5 修正**：v1.4 的「rclone.conf 行 → 无需重启」在 **conf 加密态**下**依据不成立**——`RCLONE_PASSWORD_COMMAND` 只在 `main.py` 的启动自检里赋值（且仅当 `rclone config encryption check` 返回 0 时才赋），导入改变加密态或口令后该 env 不会自己更新。结论「无需重启」仍然成立，但**依据改为「进程内重建 env + 子进程每次重读 conf」**，且重建是**必做项**而非优化项。

## 5. 安全

### 5.1 结论

沿用仓库既有四道纪律：**鉴权挂 `require_session` + `require_bootstrap_done`、写方法过 Origin 校验、审计留痕只记计数、凭据零泄漏（S3/S4/S5/S6）**。新增两个危险审计动作，须同步 `docs/代码审查规范.md` §3.1 S6 清单与 `AGENTS.md` 红线 5 索引（**v1.5 更正：S6 现为 27 项**，`docs/代码审查规范.md:66` 与 `AGENTS.md` 红线 5 均为 27；v1.4 写的「24 项」是 v1.17 之前的计数）。

### 5.2 执行权限

```python
_PROTECTED = [Depends(require_session), Depends(require_bootstrap_done)]
# 三个端点全部挂 _PROTECTED；写方法（全是 POST）由 CSRFOriginMiddleware 做同源校验
# （class CSRFOriginMiddleware 定义于 main.py:108，dispatch 在 :111-118，中间件注册在 :463；v1.4 引 :107-117 起点差 1 行且未标注册点）
```

- **未完成首启门不得导入**：否则可绕过 `must_change` 直接接管实例（S4/S5）。
- **导入即「整站接管」**：清空 `sessions` 是刻意的——旧机所有会话作废；前端须提示「导入后需重新登录」。
- **不接受 GET 触发的导出**：导出无副作用但产物是万能钥匙，必须 POST + Origin 校验 + 审计。

### 5.5 威胁提示（必须写进 UI 与部署文档）

> **本包是强制加密的**：除 `format / version / created_at / encryption` 四个头字段外，全部内容经 **PBKDF2-HMAC-SHA256（600k 迭代）派生密钥 + AES-256-GCM** 加密，且头部作 AAD 绑定（§2.1–§2.2）。**不提供「无口令导出」**；口令下限 10 位。
>
> 真正的威胁模型是「**包 + 导出口令**」同时到手：那一刻 = restic 仓库密码 + 全部云凭据 + rclone 网盘授权 + 管理员口令哈希全部泄露 ≈ 仓库钥匙泄露。**单拿到包、没有口令**，只是拿到一段不可读密文（GCM 无后门）；**单丢了口令**，包即作废，只能回旧机重新导出。
>
> **v1.5 追加（Q2）：包内多了一层口令。** 源机 conf 处于 rclone 自身加密态时，包内 `rclone.pass` 携带 32 位 **conf 解密口令**（§1.2-8）。它与导出口令处在**不同的层**、但同样在包内：拿到包 + 导出口令 → 解出载荷 → 得到 conf 密文 + conf 口令 → 解出该机器的 rclone conf → **所有 `rclone:` 远端的 OAuth token / obscured 密码**。故 Q2 不改变威胁模型的上限（本来 conf 就在包内、本来就是等价凭据，见 §1.2-6），只是把「conf 加密」这一层在备份链上抹平——**它保护的是宿主磁盘上的 conf，不是包**。UI 与部署指南须明写这半句，避免用户以为「conf 已加密所以包里的是安全的」。
>
> **操作纪律（须写进 UI 与部署指南）**：① 包与口令**分开保管**（口令进密码管理器，包进离线介质），不要一起留在浏览器下载目录；② 包本身仍按敏感物对待，不贴聊天/工单/公开仓库；③ 口令遗忘无任何找回途径。
