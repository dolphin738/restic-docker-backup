## 0. TL;DR

1. **云端看到的是「一堆密文对象 + 一个明文密钥文件」**。备份内容、文件名、目录树、快照元数据全部加密；仓库口令不落盘。唯一明文的仓库文件是 `keys/<id>`。
2. **`keys/<id>` 里能消除的只有身份标注**（`username` / `hostname`）；`salt / N / r / p` 必须明文（口令派生的数学约束，见 §2.2），`created` 是必要记录。本项目已在 init 后自动把身份换成中性值 `svc-backup@repo`（§4）。
3. **唯一真正的防线是仓库口令强度**。拿到 `keys/<id>` 就能离线暴破，其余加固措施都不能替代高熵口令。
4. **云端最致命的实际风险不是「偷看」而是「删除/毁坏」**。restic 不防存储侧删除：凭据泄漏后攻击者可直接抹对象。对策是 IAM 最小权限 + 版本控制/Object Lock（§3.3），**不是**撤掉 `DeleteObject`（撤了 prune 就废）。
5. 对「连仓库指纹都不想暴露」的极端场景，可选 rclone `crypt` 叠加（§3.5），代价是多一层故障点。
6. 诚实的边界：数据体量、对象数量、备份节奏、客户端出口 IP **无法隐藏**（§7）。
7. **口令与 `keys/` 缺一即不可恢复**——口令不是万能钥匙（master key 不由口令派生）。只要还活着一份 key + 它的口令，就能 `key add` 重建任意份；两者都丢则**无任何后台恢复路径**（§2.3）。
8. **不用进容器也能看密钥身份**：仓库页「仓库状态」卡底部新增「密钥身份」小节（只读，§5），直接显示已中性化 / 暴露 / 混合 / 无法读取。

## 1. 威胁模型：谁能看到什么

### 1.1 可见面（云商 / 能读存储的人）

| 可见对象 | 具体内容 | 本项目是否可控 |
|---|---|---|
| 对象清单 | 以 SHA-256 命名的密文文件（`data/` `index/` `snapshots/` `locks/` `config`） | 否（restic 格式决定） |
| 对象大小 / 数量 / 增量 | 可推断备份体量、文件数级、变更频率 | 否（`crypt` 可部分缓解） |
| 时间模式 | 上传时刻、访问频率 → 备份排期 | 否 |
| `keys/<id>` 明文 | `created`、`username`、`hostname`、`kdf/N/r/p/salt` | **部分可控**：身份已中性化（§4） |
| 客户端出口 IP | 备份源所在网络 | 需代理/VPN |
| 计费与访问日志 | 云商侧审计，可被调取 | 否 |

### 1.2 不可见面

| 内容 | 原因 |
|---|---|
| 备份的文件内容 | 离开客户端前已 AES-256-CTR + Poly1305-AES 加密 |
| 文件名 / 目录结构 | 存在于加密的 tree/snapshot 中 |
| 快照元数据（时间、标签、路径） | 加密存储 |
| 仓库口令 | 不落盘（只用于派生，见 §2） |
| master key | `keys/<id>` 的 `data` 字段是**密文**，用「口令派生的密钥」二次包裹 |

### 1.3 两个常见误解

| 误解 | 事实 |
|---|---|
| 「开 S3 SSE 就安全了」 | SSE 的密钥在**云商手里**，对云商不是秘密。它只防「物理介质被偷」。端到端保密只能靠客户端加密（restic 已内置）。 |
| 「再自己加密一遍数据更安全」 | restic 已是端到端加密，对同一威胁模型叠加密钥不增加安全性。要叠就叠在「隐藏仓库形态」上（`crypt`，§3.5）。 |

## 2. restic 的明文面：`keys/<id>`

### 2.1 实测结构

restic 0.18.0 初始化后，`keys/` 下唯一文件是**单行 JSON 明文**（镜像内 restic 0.19.1 字段一致）：

```json
{"created":"2026-10-23T22:06:48.605162206+08:00","username":"root","hostname":"Wien-laptop",
 "kdf":"scrypt","N":32768,"r":8,"p":7,
 "salt":"wqQxWP2dG0Gvabklwlz5mfHpx7JjfPW94eOzMxXkSGia+5VDKsfiAn4m7FIvFmySOi35qrrPYWodTqD/9Sh1tA==",
 "data":"FhwYFnayocm2B03OUsdt79RT6pdF9CSuBUVx4YlFztkJZOxjELWslM9jPXldrrP05vfPe4/4yyBaqiE2+..."}
```

| 字段 | 明文？ | 性质 |
|---|---|---|
| `created` | ✅ 明文 | 建 key 时间（含时区）。**必要记录**，无法消除 |
| `username` / `hostname` | ✅ 明文 | 身份标注。**可消除**（本项目已中性化） |
| `kdf` / `N` / `r` / `p` / `salt` | ✅ 明文 | 口令派生参数。**必须明文**（§2.2） |
| `data` | ❌ 密文 | master key 的密文包裹（口令派生密钥加密） |

### 2.2 为什么 `salt/N/r/p` 不能加密

开库链路是一条**单向依赖链**：

```
读 keys/<id>
  → 用【输入的口令】+【文件里的 salt/N/r/p】经 scrypt 派生临时密钥
    → 用临时密钥解密 data 字段，得到 master key
      → 用 master key 解密 config / index / data / snapshots / locks
```

派生过程需要 `salt/N/r/p` 作为**输入**。若它们也被加密，就没人能启动派生，等于把钥匙锁进自己都打不开的盒子。这是所有「口令派生密钥」方案（restic / borg / age）的共性约束，不是实现缺陷。

**推论**：`keys/<id>` 只能做「身份标注中性化」，做不到「整个文件加密」。要连 KDF 参数都不让存储侧看到，唯一正路是**存储层加密**（§3.4）。

### 2.3 丢失与恢复边界：key 文件能「重建」吗

**结论：能重建，但充要条件是「至少还活着一份 key 文件 **且** 记得它的口令」。** 两者是并列必要条件，缺一即不可恢复。

最容易搞错的一点：**口令不是万能钥匙**。master key 是 `restic init` 时**随机生成**的，唯一存放处就是 key 文件的 `data` 字段——它**不由口令派生**（口令只负责包裹它，见 §2.2 依赖链）。所以：

| 手里剩下的东西 | 能开库 | 能重建 key 文件 |
|---|---|---|
| 一份 key + 它的口令 | ✅ | ✅（`key add` 可再造任意份） |
| 多份 key，缺其中一份 | ✅（用其它那把） | ✅ |
| 记得口令，但 `keys/` 全没了 | ❌ | ❌ |
| `keys/` 全在，但忘了口令 | ❌ | ❌ |

**「重建」≠「还原」**：`key add` 造出的新文件是**新 salt**，字节、文件名、ID 都与原来的不同，但解出的 master key 相同、功能完全等价。想还原成一模一样的字节既做不到也没必要。

```bash
# 用任一还活着的口令，为「丢失的那把」重建一份（口令不变，用户无感）
restic -r <repo> --password-file <当前可用口令> key add --new-password-file <想恢复的那个口令文件>
```

**恢复既有 key 文件时的硬约束**：拷贝回去必须保持**原文件名**。因为 **key ID = key 文件内容的 SHA-256**（restic 用文件名作为 ID 校验）——实测把同一份内容存成另一个合法 64 位 hex 名，restic 不认；存成非 hex 名同样不认。原文件名能开、改名即失效，见 §8 探针。

**实践含义（两条，方向相反）**：

1. `keys/` 随仓库存放、多份 key 互为备份，日常**真正容易丢的是口令**——口令必须离线保管（密码管理器/纸质封存），与仓库分开。
2. 反过来，若手工同步/迁移仓库时只拷了 `data/` 而漏掉 `keys/`，**即使口令正确也读不出任何数据**（§6 检查项）。

**备份 key 文件的时间点**：应在**中性化之后**（§4）。中性化之前备份，等于把 `root@真实机器名` 又带回备份介质，身份清理白做一次。备份位置若与仓库同一处，暴露面不增加（它和仓库里的那份是同一份密文包裹）；放离线介质则更稳。

> 实证（restic 0.18.0，`.e2e/probe-key-rebuild.sh`）：删一份 key 后另一口令照常开库；`key add` 复用原口令重建后快照齐全且新 ID ≠ 原 ID；`keys/` 全删后两个口令都失败、`repair index` 报 `wrong password or no key found`；把事先备份的 key 按原名放回即完全恢复。

## 3. 加固分层（按收益排序）

### 3.1 L1：仓库口令强度（第一优先，不可替代）

拿到 `keys/<id>` 即可**离线**暴破口令（scrypt 只是抬高单次成本）。默认参数 `N=32768, r=8`，`p` 由 restic 初始化时按机器性能校准（本机实测 `p=7`），已较强，但口令熵低仍是最大风险。

| 要求 | 判据 |
|---|---|
| 长度/熵 | ≥ 20 位随机字符（密码管理器生成），或 diceware 6–7 词 |
| 唯一性 | 不与任何其他系统复用；不进 Wiki/工单/聊天记录 |
| 存放 | 只存本项目密码文件（挂载给容器，宿主机权限 600）；不进日志/API/SSE/审计（红线 S3） |
| 轮换 | 疑似泄漏或定期轮换，走《部署指南》§7.2（轮换后旧口令立即作废） |

### 3.2 L2：`keys/` 身份中性化（**本项目已自动化**）

init 后自动把唯一 key 的身份从「真实机器/账号」换成 `svc-backup@repo`，口令不变、用户无感。实现与覆盖边界见 §4。

> 价值边界：这只消除「哪台机器、哪个账号」的推断，**不改变**「可离线暴破口令」这一事实。它是低成本的纵深一层，不是防线本体。

### 3.3 L3：云凭据最小权限 + 防删除

**为什么这条比「防偷看」更实际**：restic 从设计上就不防存储侧删除（设计文档明言无法防御）。AK/SK 一旦泄漏，攻击者可以删对象或 `forget --prune`，代价远高于「偷看密文」。

**S3 最小权限策略示例**（只授单桶单前缀）：

```json
{
  "Version": "2012-10-17",
  "Statement": [
    { "Sid": "ListPrefix", "Effect": "Allow", "Action": ["s3:ListBucket"],
      "Resource": "arn:aws:s3:::my-backup-bucket",
      "Condition": { "StringLike": { "s3:prefix": ["restic/*"] } } },
    { "Sid": "ObjectRW", "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject", "s3:DeleteObject"],
      "Resource": "arn:aws:s3:::my-backup-bucket/restic/*" },
    { "Sid": "Location", "Effect": "Allow", "Action": ["s3:GetBucketLocation"],
      "Resource": "arn:aws:s3:::my-backup-bucket" }
  ]
}
```

> **必须保留 `s3:DeleteObject`**：restic `prune` 靠删对象回收空间。想要「凭据泄漏也抹不掉历史」，正确手段是**版本控制 / Object Lock**，而不是撤权限——撤权限等于放弃 prune。

**其它后端对应口径**：

| 后端 | 最小权限做法 | 防删除手段 |
|---|---|---|
| Backblaze B2 | Application Key 限定单 bucket，capabilities 仅 `listFiles/readFiles/writeFiles/deleteFiles` | Bucket Object Lock（建桶时开） |
| Azure Blob | 容器级 SAS 或限定范围的凭据（读/写/列/删） | Blob 版本控制 + 软删除 + 不可变策略 |
| GCS | 服务账号只授该 bucket 的 `objectAdmin`（或更细） | Object Versioning + Retention Policy |
| rclone（网盘） | 独立账号/独立应用授权，只授目标目录 | 网盘侧版本历史（多为有限期） |

**Object Lock 与 prune 的冲突（必须提前决策）**：

| 模式 | 效果 | 与 restic prune 的关系 |
|---|---|---|
| Compliance（合规） | 保留期内**任何人**都删不掉（含 root） | prune 会失败；只能等保留期自然过期后回收 → 需让保留期 ≥ 备份保留策略 |
| Governance（治理） | 有特权的账号可绕过 | 可与 prune 共存，但「有权限者可绕过」= 泄漏的高权凭据仍能删 |
| Versioning + MFA Delete | 删除只产生删除标记，彻底清除需 MFA | 与 prune 共存较好；代价是存储成本上升 |

**推荐**：`Versioning + MFA Delete`，或 `Governance` 模式；只有强合规要求才用 `Compliance` 并接受「prune 不回收空间」。

### 3.4 L4：存储层加密（消除 KDF 参数明文顾虑）

把仓库放在加密卷上：本地盘用 LUKS / BitLocker / NAS 加密共享；这样 `keys/<id>` 的 `salt/N/r/p` 即使明文也无人可见。

> 注意区分：**对象存储的服务端加密（SSE）不等于这一层**——钥匙在云商手里（§1.3）。L4 只对「你能控制加密密钥的介质」有效（自管磁盘、自管 NAS、加密容器）。

### 3.5 L5（可选）：rclone `crypt` 叠加——隐藏「这是 restic 仓库」

在 restic 与云端之间插一层 rclone `crypt` remote：云端只看到乱码文件名 + 定长加密块，连「对象名是 SHA-256、这是 restic 仓库」都看不出来。

```ini
# rclone.conf：crypt 套在 s3 之上
[cloud]
type = s3
provider = AWS
# ... AK/SK ...

[vault]
type = crypt
remote = cloud:my-backup-bucket/restic-enc
password = <rclone 加密口令（另一份，独立保管）>
password2 = <salt（可选）>
filename_encryption = standard
directory_name_encryption = true
```

restic 侧仓库地址变为 `rclone:vault:`（本项目走 `rclone:` 后端即天然支持）。

| 收益 | 代价 |
|---|---|
| 隐藏仓库指纹、文件名、精确大小 | 多一层加解密与故障点（`check`/`repair` 依赖 crypt 层正常） |
| 云端无法针对 restic 做定向攻击 | **多一个必须备份的口令**（rclone crypt 口令丢失 = 数据永久不可读，比 restic 口令更致命） |

### 3.6 L6：侧信道（只能接受）

数据体量、对象数量、备份时间模式、客户端出口 IP —— restic 不隐藏，`crypt` 也只部分缓解。若这些本身是机密，需要：固定排期/填充流量（成本高）、代理出口、或换用更强匿名的传输方案。

## 4. 本项目实现：init 后密钥中性化

### 4.1 两个生效入口（当前实现的事实边界）

| # | 入口 | 代码位置 | 触发时机 | 覆盖的用户场景 |
|---|---|---|---|---|
| 1 | `POST /api/repos/{repo_id}/rebuild` | `backend/app/routers/repos.py`（`rebuild_repo`，init 成功后同步调用；2026-10-23 核查锚点 ≈ L858） | 重建仓库（清空→写新密码文件→`restic init`→中性化） | 仓库页「重建」；本地 FS 后端 |
| 2 | 作业类型 `init`（`POST /api/jobs` 显式提交，或 `AUTO_INIT` 自动提交） | `backend/app/services/job_runner.py:512`（`_run` 终态 `success` 且 `job.type == "init"` 时调用） | 作业跑完 `restic init` 成功后 | 首次初始化 / 远端仓库建库 / `AUTO_INIT=1` 启动自举 |

两个入口都调用**同一个函数** `neutralize_repo_key()`，参数形态一致（`restic` 实例 + `repo_id` + `env` + `password_file`），因此行为、幂等性、失败语义完全相同。

### 4.2 执行序列

```
restic init（原流程，成功后）
  └─ neutralize_repo_key()
       ① key list --json          → 读现有 key（判定是否唯一 / 是否已中性）
       ② key add --user svc-backup --host repo --new-password-file <现有密码文件>
       ③ key list --json          → 按中性 userName/hostName 定位新 key
       ④ --key-hint <新id> key remove <旧id>
```

四点实现纪律：

| 要点 | 原因 |
|---|---|
| `--new-password-file` 指向**现有密码文件** | 新 key 与旧 key 同口令 → 中性化对用户完全透明（原密码照常开库） |
| ④ 必须带 `--key-hint <新id>` | 新旧 key 同口令时，restic 先解出哪个不确定；若先解旧 key，则「当前 key」= 旧 key，`key remove` 会报 `refusing to remove key currently used`。真机 0.18.0 已实证 |
| 只处理**唯一 key** | 多 key 说明有其它工具/他人接入，擅自删除会破坏别人的访问 |
| 命令全部经 `ResticCmd.build` 白名单拼装 | 不经 shell；`--user/--host` 过 `_assert_safe_value` 防 flag 注入，`--key-hint` 过 `_assert_key_id` 校验（红线 S2） |

### 4.3 幂等与失败矩阵

`neutralize_repo_key()` 的返回语义：`True` = 实际完成中性化；`False` = 跳过或失败，**原因只记日志、绝不抛异常**。

| 情形 | 行为 | 仓库影响 |
|---|---|---|
| 已中性（user/host 均为中性值） | 只读一次 `key list` 即返回，不加不删 | 无（幂等，可重复安全调用） |
| 多个 key | 跳过 | 无（旧 key 全部保留） |
| `key add` 失败 | 停止，返回 `False` | 无（仅有旧 key，仓库可用） |
| `key add` 成功但定位不到新 key | 返回 `False` | 旧 key 保留；新 key 已存在（后续手工清理） |
| `key remove` 失败 | 返回 `False` | 仓库可用；出现「中性 key + 旧 key」两条（旧身份仍暴露，需手工删） |

**设计原则**：中性化是**加固步骤**，不能把已成功的 init 反转成失败。两个调用点都做了这层保护（`job_runner` 额外用 `contextlib.suppress(Exception)` 包裹，`CancelledError` 属 `BaseException`，不会被吞）。

### 4.4 覆盖边界与「新增 init 路径」接入指引

> 现状一句话：**只覆盖上面两个 init 入口（`rebuild` 与 `job type=init`）**。若未来新增任何执行 `restic init` 的路径，直接复用 `neutralize_repo_key()` 即可——不要在别处重写一遍 KEY 逻辑。

**(a) 判据（什么样新代码必须接）**

凡是「创建了一个新仓库」的代码路径，都必须在其 `restic init` 成功之后调用一次。检测手法（结果应为 2 处，新增后逐一确认下游有调用）：

```bash
# 在 web版/ 下执行；init 的 argv 拼装点（无 rg 时用 grep -rn 'build("init"' backend/app）
rg -n 'build\(\s*"init"|build\(job\.type|job_type == "init"' backend/app
```

**(b) 接入三要素（少一个就会出错）**

| 参数 | 来源 | 缺失后果 |
|---|---|---|
| `restic` | `app.state.restic`（路由）或 `self._restic`（JobRunner） | 无实例则无法拼装 |
| `env` | `restic.build_env(repo_url=..., repo_id=..., env_extras=...)` 的返回值 | 必须含 `RESTIC_PASSWORD_FILE`/`RESTIC_REPOSITORY`，否则操作打错仓库 |
| `password_file` | `passfile_path(settings, repo_id)` | **必须指向新建仓库时所用的那个口令文件**；指向别的文件会造出「不同口令的第二个 key」——用户用原口令开库可能失败（取决于哪个 key 先被尝试） |

**(c) 调用模板（照抄即可）**

```python
from app.services.repo_keys import neutralize_repo_key

await neutralize_repo_key(
    restic,                      # ResticCmd 实例
    repo_id=repo_id,
    env=env,                     # 已含 RESTIC_REPOSITORY / RESTIC_PASSWORD_FILE
    password_file=password_file, # 与 init 使用同一个口令文件
)
# 返回值可忽略：True=已中性化，False=跳过/失败（已记日志，不抛异常）
# 若不想让任何异常影响主流程，外层再套 contextlib.suppress(Exception)
```

**(d) 三个易踩的坑**

1. **口令文件必须一致**：这是最容易出错的地方。`key add` 用的 `--new-password-file` 若不是 init 时的口令文件，仓库会出现两个不同口令的 key，用户「原密码打不开」或「有时能打开」。
2. **不要在「仓库已初始化」的探测路径上调用**：中性化只该发生在**本次 init 成功之后**。在 `cat config` 探测成功/失败分支上误调，会把「已存在仓库」也改身份（多 key 场景虽会跳过，但语义已错）。
3. **不要因为返回 `False` 就重试或报错**：`False` 是「跳过/失败已记录」，不是「仓库坏了」。盲目重试会在多 key 场景反复 `key add`。

**(e) 护栏**

| 资产 | 作用 |
|---|---|
| `backend/tests/test_repo_keys.py` | 12 例：argv 拼装（`--user/--host/--key-hint` 位置、非法 id 拒绝）、`key list --json` 解析容错、五条中性化路径（成功/已中性/多 key/add 失败/remove 失败） |
| 真机验证口径 | 用真实 restic 跑「init → key add → key list → `--key-hint` remove → `cat config`」，确认身份变为 `svc-backup@repo` 且仓库仍可打开（restic 0.18.0 已跑通；镜像为 0.19.1） |

### 4.5 手工 CLI 等价操作（容器内应急/老仓库补做）

```bash
# 口令走文件，不进 argv；RESTIC_REPOSITORY 已由环境提供
restic key list
# *a1b2c3d4  root  host1  2026-10-23 21:00:00

restic key add --user svc-backup --host repo \
  --new-password-file "$RESTIC_PASSWORD_FILE"
#  saved new key as <e5f6a7b8...>

restic --key-hint e5f6a7b8 key remove a1b2c3d4   # --key-hint 必需，见 §4.2
restic key list                                   # 确认只剩 svc-backup@repo
```

> 最后一个 key 删不掉：`key remove` 拒绝删「当前正在使用的 key」。仓库只剩一个 key 时，它必然就是当前 key → 实际效果等同「不能删最后一个」。所以永远是「先 add，再 remove」。

## 5. 只读密钥可见性（已实现）

> 状态：**已落地**（v1.1）。仓库页「仓库状态」卡底部新增「密钥身份」小节，数据源
> `GET /api/repos/{repo_id}/keys`；加/删 key 仍不在范围内（写操作涉及「删错 key 就永久
> 失去访问」，需单独评审 + 二次确认）。
> 目的：让用户确认「中性化是否真的生效」「是否有历史遗留的真实身份 key」，不需要 CLI。

### 5.1 端点契约

> 编号：**E47**（《架构设计文档》§5.1 为契约的规范出处，本节给运维视角的可读版）。

```
GET /api/repos/{repo_id}/keys
依赖：require_session + require_bootstrap_done（与 /repos/{repo_id}/status 同口径）
只读：无写方法；加/删 key 不在本期范围
```

响应示例：

```json
{
  "repo_id": "default",
  "overall": "neutralized",
  "keys": [
    {
      "id": "70b65d8e",
      "id_full": "70b65d8efa88a4fc336d08c408eb672c4e3a8d3f2a966ff95988a63718086bfb",
      "user": "svc-backup",
      "host": "repo",
      "created": "2026-10-23 22:06:48",
      "created_tz": "UTC",
      "current": true,
      "neutral": true
    }
  ],
  "probe_error": null
}
```

### 5.2 具体能看到什么

**字段级（5 个来自 `restic key list --json` 实测字段 + 1 个服务端时区标注）**

| 响应字段 | 来源 | 界面用途 |
|---|---|---|
| `repo_id` | 路径参数 | 多仓库区分 |
| `overall` | 服务端判定 | 顶部结论：`neutralized` / `mixed` / `exposing` / `unknown` |
| `keys[].id` | `id` 前 8 位 | 列表主标识（与 `restic key list` 表格列一致） |
| `keys[].id_full` | `id`（64 位 hex） | 复制按钮 / CLI 排障（`key remove` 可直接用） |
| `keys[].user` | `userName` | 身份判定、暴露预警 |
| `keys[].host` | `hostName` | 同上 |
| `keys[].created` | `created` | 建库/接入时间线（判断哪个是历史遗留） |
| `keys[].created_tz` | `settings.tz`（服务端标注） | restic 的 `created` 是**按子进程时区渲染的无时区字符串**（本项目注入 `TZ`，默认 `UTC`）；不带该标注就会与用户本地时间差出偏移且无从判断。原样展示，**不做换算**（红线 C8：时间语义单一真源） |
| `keys[].current` | `current` | 「当前」徽章（restic 保证唯一） |
| `keys[].neutral` | 服务端判定（`user == svc-backup && host == repo`，与 `repo_keys.NEUTRAL_KEY_*` 同源常量） | 绿色「已中性化」/ 橙色「暴露真实身份」 |
| `probe_error` | `key list` 失败原因（截断） | 失败态可见，不显示空白 |

`overall` 判定：`neutralized`（全部 key 均为中性身份）/ `exposing`（存在非中性 key）/ `mixed`（中性 + 非中性并存，通常是「旧 key 未删」或其它工具接入）/ `unknown`（`key list` 失败，此时 `keys` 为空、`probe_error` 非空）。

**界面级**（仓库页 → 状态卡 → 「密钥身份」小节）

已中性化：

```
密钥身份                    ● 已中性化
  70b65d8e   svc-backup @ repo      2026-10-23 22:06:48   [当前]
   该仓库的密钥身份不暴露真实机器名与账号（云端仅见此中性标注）
```

未中性化（历史仓库 / 旧版本创建）：

```
密钥身份                    ⚠ 1 个密钥暴露真实身份
  a1b2c3d4   root @ Wien-laptop     2026-10-23 21:00:00   [当前]
   该身份随 keys/<id> 明文存放于仓库，云端可见 → 建议重建仓库或执行 key 中性化
```

多 key（其它工具接入）：

```
密钥身份                    ⚠ 混合（2 个密钥）
  70b65d8e   svc-backup @ repo      2026-10-23 22:06:48   [当前]
  e5f6a7b8   alice @ build-host     2026-10-25 09:12:03
   中性化只处理唯一 key；多 key 仓库跳过（避免破坏其它工具的访问）
```

探测失败（仓库锁残留 / 网络不可达 / 口令文件缺失）：

```
密钥身份                    ? 无法读取
  restic key list 失败：<原因摘要>
```

**版式**：本小节在状态卡内与左侧「连接态 / 容量」**左右并排**（横向，不上下堆叠），两栏之间**只用 40px 间距分组，不画分隔线**（用户 2026-10-23 指令：分隔线去掉）。三条必须同时成立的约束（都来自真实排版翻车）：

1. **两栏都按内容收缩**（左栏不 `flex-grow` 撑满）：左栏一旦撑满，右栏会被推到卡片最右侧、中间留一大片空白（用户 2026-10-23 截图反馈）。
2. **告警通栏在分栏下方**：`last_error` / 口令文件缺失 / 锁残留三条告警是**全卡级**信号，不参与分栏；留在左栏会被压成内容宽度、文字挤成多行。
3. **两栏垂直居中对齐**：左栏通常只有一行标签，右栏是三行块；顶对齐会让左栏吊在顶部、下方空出一截。

右栏上限 50%（超长 `host` 不致挤没左栏）；视口 ≤640px 回落为上下堆叠（间距 12px），`align-items` 复位为 `stretch`（否则 column 方向下 `center` 变成水平居中）。

判据是几何事实而非文案，由 `.e2e/p16-key-split.cjs` 逐档断言：两栏间距 = 40px、两栏中心线偏差 ≤ 2px（居中）、**两档 `border-left` 与 `border-top` 均为 0px（确无分隔线）**、告警宽 = 分栏宽（通栏）、两档零横向溢出。

### 5.3 不会看到什么（安全边界）

| 内容 | 为什么看不到 |
|---|---|
| `data` 字段（master key 密文） | 不解析、不回传（只取 `id/userName/hostName/created/current`） |
| `salt / N / r / p` | 不回传：这些是暴破难度参数，对用户无操作价值，少给一份指纹 |
| 仓库口令 | 不在 restic 输出中，接口更不可能返回 |
| 直接加/删 key 的能力 | 本期只读。写操作涉及「删错 key 就永久失去访问」，需单独评审 + 二次确认 |

其它纪律：

- `key id` **不是机密**：它就是 `keys/` 文件名，能读存储的人本来就能看到，因此可正常展示（便于 CLI 排查）。
- **不写审计**：只读端点与 `/status` 同口径，不为每次读取写审计行（会淹没真正的写操作记录）。若将来引入访问审计，只记「条数 + 是否中性」，**不记**真实 `user@host`——避免把身份泄露从云端转移进本地日志。
- **不走 E30 状态缓存**：`/status` 有 TTL 缓存（容量/stats 代价高），`key list` 是轻量实时探测，且「是否已中性化」是安全判定，缓存会误导。独立、无缓存。

## 6. 部署检查清单

| 阶段 | 检查项 | 判据 |
|---|---|---|
| 建库前 | 仓库口令强度 | ≥ 20 位随机或 diceware 6–7 词；密码管理器生成；不复用 |
| 建库前 | 密码文件权限 | 宿主机上仅容器运行用户可读（`600`）；所在目录不对其他用户开放 |
| 建库前 | 口令离线保管 | 口令另存于密码管理器/离线介质，与仓库**不在同一处**；口令丢失 = 数据永久不可读（§2.3） |
| 建库前 | 仓库位置 | 敏感场景置于加密卷（LUKS/BitLocker/加密 NAS）；对象存储场景见下 |
| 建库后 | 密钥身份 | `restic key list` 仅 1 条，User/Host = `svc-backup` / `repo` |
| 建库后 | 云凭据范围 | 只授目标 bucket/prefix 的 List/Get/Put/Delete；无其它桶权限 |
| 建库后 | 防删除 | 版本控制 + MFA Delete，或 Object Lock（Governance；Compliance 需接受 prune 不回收） |
| 建库后 | 公共访问 | 关闭匿名/公共读；开启访问日志（事后取证） |
| 定期 | 口令轮换 | 按《部署指南》§7.2 执行；轮换后确认其它工具已同步 |
| 定期 | 身份复核 | `key list` 无新增未知身份；有则确认来源（新机器/新工具） |
| 定期 | 配置复核 | IAM 策略、对象锁、版本控制未被静默改动 |
| 定期 | 恢复演练 | 用离线口令 + 仓库副本实开一次 `restic snapshots`；只验证「备份任务成功」不算验证（成功 ≠ 可恢复） |
| 定期 | 仓库完整性 | 迁移/同步仓库后确认 `keys/` 目录在位（漏拷 `keys/` = 口令正确也读不出，§2.3） |
| 事故 | 凭据泄漏 | 立即吊销 AK/SK → 查对象删除记录 → 从版本历史/Object Lock 恢复 → 轮换仓库口令 |
| 事故 | 口令或 `keys/` 丢失 | 按 §2.3 矩阵判定：两者缺一即**不可恢复**，唯一出路是事先的离线口令（与中性化后的 key 文件副本）；此时**不要**执行「重建仓库」——那是 `restic init`，会连同历史数据一起丢弃 |

## 7. 明确「防不住」的

| 风险 | 现状 | 缓解 |
|---|---|---|
| 离线暴破口令 | 拿到 `keys/<id>` 即可离线尝试，scrypt 只抬高单次成本 | **只能靠口令熵**（L1） |
| 存储侧删除/损坏 | restic 明确不防御 | 版本控制 / Object Lock / 异地副本（镜像仓库） |
| 数据体量、对象数、备份节奏 | 对象大小与数量天然可见 | `crypt` 部分缓解；否则接受 |
| 客户端出口 IP | 云端可见连接来源 | 代理/VPN |
| 高权凭据泄漏后绕过 Governance Lock | Governance 模式允许有权限者绕过 | 用 Compliance（代价：不能 prune）或 MFA Delete |
| **口令或 `keys/` 全丢** | restic **没有**任何后台恢复路径：`repair index` 也要先开库，同样报 `wrong password or no key found` | **只能预防**：口令离线保管 + 中性化后备份 key 文件（§2.3、§6）。事后无解 |
| 本地宿主机被攻破 | `rclone.conf`（OAuth token 明文）、密码文件、DB 都在宿主机 | 宿主加固、文件权限、最小挂载；不在本文范围 |
