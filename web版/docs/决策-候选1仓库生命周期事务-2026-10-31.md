# 决策：候选 1 · 仓库生命周期事务

## 1. 结论先行

新增 `services/repo_lifecycle.py`（`RepoLifecycleService`），把 `delete_repo` / `release_archived_repo` / `rebuild_repo` / `restore_archived_repo` 四段跨介质多步序列收成一个深模块；`retention.cleanup_archives` 的归档到期分支一并接管。路由只做入参映射与响应映射。

**风险模型不是「靠事务回滚」，而是「顺序 + 幂等」**——磁盘清空、删日志、删密码文件都不可逆，补偿补不回来。真正让系统收敛的是：**把删行挪到最后**，使任何中途失败都能整请求重发并收敛。

## 3. 目标形态

```python
# services/repo_lifecycle.py
class RepoLifecycleService:
    def __init__(self, *, db, repos: ReposRepo, config: ConfigRepo, jobs: JobRepo,
                 audit: AuditRepo, settings: Settings, restic: ResticCmd,
                 crypto, status_cache, catalog, logger=None): ...

    async def archive(self, repo_id: str) -> None
    async def restore(self, repo_id: str) -> None
    async def hard_delete(self, repo_id: str, *, purge_disk: bool) -> DeleteReport
    async def release(self, repo_id: str) -> DeleteReport
    async def rebuild(self, repo_id: str, *, password: str | None) -> RebuildReport
    async def expire_archived(self, repo_id: str) -> None   # retention 专用，无 HTTP 语义
```

`DeleteReport` 字段：`removed_logs: int` / `cleared_credentials: int` / `purged_disk: bool`（与原审计 detail 同形，前端无感）。

**锁**：`self._locks: dict[str, asyncio.Lock]`，`_lock(repo_id)` 惰性建锁（照 `JobRunner._repo_lock` 的形状，但键是 **repo_id** 不是 url）。单进程是硬约束（`main.py:191` 注释：`--workers>1` 在 Windows 会废掉子进程；`rclone_config.py:367` 注释：「应用为 asyncio 单进程」），故内存锁合法。

## 4. 精确步骤序

### 4.1 `hard_delete(*, purge_disk)`（批次 ①）

```
async with self._lock(repo_id):
  1. repo = repos.get(repo_id)                      # 锁内重取；None → RepoNotFoundError
  2. await repos.ensure_deletable(repo_id)          # 锁内复查（三门守卫）
  3. await jobs.list_active(repo_id) → 非空即 JobConflictError
  4. audit.record(AUDIT_REPO_LIFECYCLE_BEGIN,
                  detail={op:"delete", purge_disk, name})            # 意图留痕
  5. log_paths = await jobs.terminal_log_paths(repo_id)             # 只查，不删
  6. purged = await self._purge_disk(repo)          # 仅 purge_disk 分支；失败 422 零损失
  7. cleared = await self._clear_credentials(repo_id)
  8. async with db.transaction() as tx:             # 3 条 SQL，毫秒级
       repos.insert_tombstone_tx(tx, ...)           # INSERT OR REPLACE
       repos.drop_row_tx(tx, repo_id)               # DELETE jobs(终态) + DELETE repos
  9. await asyncio.to_thread(_unlink_logs_sync, log_paths)
 10. audit.record(repo.delete | repo.purge, detail={计数字段})       # 失败吞掉 + ERROR 日志
 11. status_cache.invalidate(); catalog.invalidate()
```

**关键性质**：崩在 6~8 之间 → 行仍在 → 用户重发，第 2 步守卫重新通过、第 6/7 步幂等跳过已完成部分，收敛。崩在 9 之后 → 只缺一条收尾审计 + 可能留下孤儿日志文件（由 `_purge_old_logs_sync` 的 mtime 扫描收掉，最迟一个 `logs_days`）。

**外键是最后一道安全网**：`jobs.repo_id` 外键无级联动作。若在步骤 5 与 8 之间插入了活跃作业，`DELETE FROM repos` 会因外键约束失败 → 事务回滚 → 行仍在，可重试。**不要给该外键加级联。**

### 4.2 `release()` / `expire_archived()`（批次 ②）

同形，去掉磁盘步骤：

```
lock → get → (release 需 confirm_id 校验，留在路由) → begin 审计
  → log_paths → 清凭据 → [expire 另加：remove_passfile]
  → tx{ 墓碑(released_at / data_destroyed=0) + drop_row }
  → 删日志文件 → 收尾审计 → 失效缓存
```

`retention.cleanup_archives` 第一档改为：`for repo in list_archived(): ... await lifecycle.expire_archived(repo.id)`。retention 只负责「何时」（保留期判定），不负责「怎么删」。

### 4.3 `rebuild(*, password)`（批次 ③）

保持现有顺序，把「清空先于覆盖密码」**从注释提升为编排器里的显式顺序契约**：

```
锁 → get → 本地 FS 校验(local_path None → 422) → list_active 非空 → 409
  → begin 审计 → _is_fs_root 硬拒 → [exists 且非目录 → 422] → _clear_dir_contents
  → _write_passfile(新密码) → restic.consume("init")
  → neutralize_repo_key（失败只记日志，不阻塞）
  → 清 enc:v2 凭据 → 收尾审计 → 失效缓存
```

失败态语义（写进 docstring）：清空失败 = **零损失**（什么都没动）；清空成功后密码/init 失败 = 旧数据已按确认销毁，状态自洽（空库待 re-init），可重入。

## 5. `Database.transaction()` 的契约（批次 0）

```python
@asynccontextmanager
async def transaction(self) -> AsyncIterator[Tx]:
    if self._in_transaction:
        raise RuntimeError("不支持嵌套事务")
    await self.conn.execute("BEGIN IMMEDIATE")
    self._in_transaction = True
    try:
        yield Tx(self.conn)
    except BaseException:
        await self.conn.rollback(); raise
    else:
        await self.conn.commit()
    finally:
        self._in_transaction = False
```

**两条硬约束**：

1. **事务内禁止 `await` 到 IO/子进程**。A5 单写连接 = 全局写排他，事务时长必须以毫秒计。
2. **`write()` 在事务内直接抛 `RuntimeError`**，强制走 `tx.execute()`。理由：`write()` 是「执行 + 立即 commit」，事务中调它会把事务**静默腰斩**——后续 `ROLLBACK` 变空操作且不报错。这种 bug 能跑通、测试拦不住、只在线上删仓库时炸。

仓储写方法统一接受可选 `tx: Tx | None = None`：给 `tx` 走 `tx.execute`，不给走 `self._db.write`。**仓储层仍是唯一 SQL 出口（A7 不破）。**

## 7. 审计

`detail` 只含 `op`（`archive`/`restore`/`delete`/`purge`/`release`/`rebuild`/`expire`）+ 非敏感计数（S3：绝不回显凭据、密码、URL 里的口令段）。

> `repo.lifecycle.begin` / `repo.lifecycle.failed` 是生命周期动作的**过程留痕**（每步进展与失败），危险的是 `repo.delete` / `repo.purge` / `repo.id_release` 本身，**不计入 23 项清单**。

## 10. 已接受的风险（owner 已确认）

1. **purge 成功、删行失败**：仓库仍在列表里，但盘上数据已空，点进去打不开。优于现状（行没了 + 凭据残留 + 无审计）——有审计、可重试、用户能自己再点一次。
2. **崩溃在事务后、删文件前**：孤儿日志文件活不过下一个 `logs_days`（`_purge_old_logs_sync` 按 mtime 扫，不依赖 jobs 行）。代价：日志比预期多留一个维护周期。
3. **审计明细可能缺收尾条**（决策 9）。

**未关闭的窗口（本次不解决，登记在案）**：backup 提交与 delete 之间仍有「`ensure_deletable` 通过 → backup 抢到任务 → delete 继续」的缝，锁只保护生命周期侧。真正关闭需 JobRunner 与编排器共用锁域，属 R-023 多仓库范围。**但外键会在 `DELETE FROM repos` 处兜住，不会产生悬空 jobs 行。**
