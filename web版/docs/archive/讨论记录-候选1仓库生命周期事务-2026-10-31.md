## 0. 事实基线（已核实，不用再查）

`routers/repos.py` 里三个生命周期函数，每个都是**跨介质多步序列，没有任何事务边界**：

### `delete_repo`（:502）— hard / purge 分支 6 步

```
1. 磁盘：_purge_repo_disk()        ← 清空目录内容 + 删密码文件（不可逆）
2. DB  ：repos_repo.hard_delete()  ← 删 repos 行（+ 终态作业级联）
3. 磁盘：_unlink_logs_sync()       ← 删孤儿日志文件
4. DB  ：config_repo.delete() ×N   ← 逐条删 cred.{repo_id}.* 凭据键（循环，非事务）
5. DB  ：audit.record()            ← 审计（append-only）
6. 内存：invalidate_*() ×2         ← 缓存失效
```

| 步骤 | 介质 | 能否回滚 |
| --- | --- | --- |
| 1 磁盘清空 | 文件系统 | ❌ |
| 2 删行 | SQLite | ✅ |
| 3 删日志 | 文件系统 | ❌ |
| 4 删凭据 | SQLite | ✅ |
| 5 审计 | SQLite | ❌（append-only，S6） |
| 6 缓存 | 内存 | ✅ |

**现有防护**：三门守卫（`ensure_deletable`）**先于一切副作用**；`_purge_repo_disk` 被
特意排在校验之后。这是当前唯一的一致性保证。

**暴露面**：2→3 或 3→4 之间崩（进程重启 / 磁盘满 / 权限变）→ 行已删、日志残留、凭据残留，
且**没有审计记录**（第 5 步没跑到）→ 事故无痕。

### `release_archived_repo`（:662）— 4 步

```
1. DB  ：repos_repo.release_id()   ← 删 repos 行 + 返回待删日志
2. 磁盘：_unlink_logs_sync()       ← 删日志
3. DB  ：config_repo.delete() ×N   ← 删凭据键
4. DB  ：audit.record()
```
同样的「DB 先行、磁盘/后续步骤无保护」形状。

### `rebuild_repo`（:1433）— 3 步，**已有一次审查修复**

```
1. 磁盘：_clear_dir_contents()     ← 清空仓库目录（不可逆）
2. 磁盘：_write_passfile()         ← 写新密码文件
3. 子进程：restic init             ← 重新初始化
```
> 注释载明：原顺序是「先写密码再清空」，审查 🔴 修复（2026-10-22）调序为**清空先于覆盖密码**——
> 因为清空失败（EBUSY/权限）时若密码已覆盖，盘上快照永久不可读，「自救」变「自毁」。
>
> **这是本仓库处理此类问题的既有先例，值得作为 Q2 的参考。**

## ❓ Q1 — 事务边界划到哪一层

SQLite 能包住 2/4/5，包不住 1/3（文件系统）。所以「什么算一个事务」必须先定。

- **(A) 只包 DB 步骤**：把 `hard_delete` + 凭据删除 + 审计收进一个 `Database.write` 事务；
  磁盘操作留在事务外，按 Q2 的补偿处理。改动小，但跨介质不一致仍可能存在。
- **(B) 编排层统一收口（推荐）**：新增一个生命周期编排器（如 `RepoLifecycleService`），
  由它串起「磁盘 → DB → 日志 → 凭据 → 审计 → 缓存」，并持有**每一已完成步骤的补偿动作**；
  DB 部分内部再走单个事务。接口只有「我要删除这个仓库（含哪些选项）」。
- **(C) 维持现状，只补审计兜底**：不动结构，仅保证任何失败都留审计。最省，但不解决不一致。

➡️ **(B)**。理由：候选 1 的抱怨正是「不变量和步骤不住在一起」。(A) 只解决一半；
(C) 等于承认现状。(B) 与已完成的候选 2 同构——把散在路由里的多步序列收成一个深模块。

## ❓ Q2 — 中途失败怎么补偿

- **(A) 尽力补偿**：失败时按已完成步骤逆序执行补偿（删了的凭据重建不了就跳过、日志已删不管），
  最后仍抛错让用户重试。
- **(B) 先记后做（推荐）**：动手**之前**先写一条「意图」审计（或落一张 `repo_ops` 待办），
  每完成一步更新状态；崩溃后启动/下次请求可发现未完成的 op 并继续或回退。
- **(C) 什么都不做，仅抛错**：依赖用户重试 + 人工核对。

➡️ **(B)** 但**受 S6 约束**——审计只允许 INSERT/SELECT（唯一受控 DELETE 是 `purge_older_than`），
所以「更新状态」不能 UPDATE 审计表。可行做法：每次进展 **INSERT 一条新审计**（如
`repo.delete.begin` / `repo.delete.disk_done` / `repo.delete.committed` / `repo.delete.failed`），
靠 append-only 序列表达进度，不破坏 S6。

⚠️ 这一点需要你确认：是否接受「用多条 INSERT 表达状态机」这个表达法（会新增 4~5 个 `AUDIT_*`
常量，需同步 §3.1 危险清单与架构文档 §5.0）。若不接受，退回 (A)。

## ❓ Q3 — 幂等与重试语义

- **(A) 每步幂等，整体可重试**：把「删凭据键」「删日志」做成幂等（已删则跳过），
  整体失败后用户可安全重发。
- **(B) 一次性，失败即终态**：失败后不允许重发，要求人工介入。

➡️ **(A)**。理由：这三个端点都是**不可逆危险操作**（`repo.delete`/`repo.purge`/`repo.id_release`
已在 S6 危险清单），用户在失败后最可能的动作就是「再点一次」；不幂等会让重试变成二次破坏。
且 (A) 的实现成本低——现有 `config_repo.delete` 与 `unlink(missing_ok=True)` 语义已接近幂等，
主要缺的是「行已删」的判定分支。

## ❓ Q4 — 编排器放哪、叫什么

- **(A) `app/services/repo_lifecycle.py`（推荐）**：纯服务层，不碰 HTTP；路由只做入参校验与响应映射。
- **(B) 留在 `routers/repos.py` 内**：不新增文件，但 repos.py 已 1769 行（候选 3 的抱怨）。
- **(C) `app/db/repositories/` 内**：不合适——它要编排磁盘与子进程，不是仓储层职责。

➡️ **(A)**。与候选 2 的接缝同构（机制进 services，路由只编排）。
命名建议 `RepoLifecycleService`，方法形如 `archive()` / `hard_delete()` / `purge()` / `rebuild()`。

> 需同步：`docs/架构设计文档.md` §3 目录树与 §7（新增 services 模块）——候选 2 落地时已做过同类登记。

## ❓ Q5 — 迁移分批（≤400 行/次硬约束）

- **(A) 先 `delete_repo` 的 hard/purge 分支**（证据最硬、6 步最脆），再 `release_archived_repo`，
  再 `rebuild_repo`，最后 `delete_tombstone`。

# 第二轮（Q1–Q5 定完后才问，先不答）

1. 编排器是否需要**锁**（同一 repo_id 的并发删除/重建如何互斥）？现有 `JobRunner` 有
   `_repo_lock`，但是作业级的；生命周期操作要不要复用它还是另起一把？
2. 「意图审计」的常量命名与 §3.1 危险清单的归属：新增的 `repo.delete.*` 进度动作是否**入**
   23 项危险清单？（我倾向：**不入**——它们是过程留痕，危险的是 `repo.delete`/`repo.purge` 本身）
3. `purge_disk` 分支里 `_purge_repo_disk` 已返回 `bool`（是否真删了）。失败时是当作
   「数据仍在、行也别删」还是「数据尽力了、行照删」？——这直接决定补偿方向。
4. 是否需要为这些端点补**并发/崩溃注入测试**（`asyncio.gather` 双并发 + 中途异常）？
   `AGENTS.md` 已要求 `JobRunner.submit` 有双并发测试，这里是否同标准？
5. 审计在事务内的位置：审计 INSERT 与业务写是同事务（一起回滚）还是独立提交
   （业务回滚但审计保留「我试过」的痕迹）？——**S6 append-only 倾向后者**，需你确认。
