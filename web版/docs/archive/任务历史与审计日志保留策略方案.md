# 任务历史与审计日志保留策略方案

## 1. 结论先行（TL;DR）

| 数据流 | 是否无限累积 | 现有清理 | 建议 |
|---|---|---|---|
| **任务历史**（`jobs` 行 + `/data/jobs/*.log`） | 否 | ✅ 已有：每日 03:40 `maintenance-retention`，`retention.jobs_days` 默认 90 天，只删终态行 | 补一个**手动「立即清理」入口** + 清理前可预览；其余保持 |
| **审计日志**（`audit_logs`） | **是** | ❌ 无。代码面只有 INSERT / SELECT，不存在 UPDATE / DELETE 路径 | **新增保留策略**：先「归档导出 + 按天滚动清理」，默认保留 365 天；**不给**通用删除 API |

关键判断：两条流的清理诉求**性质不同**——任务历史是运维数据（可丢、有对账价值有限），审计日志是合规证据（不可随意丢、但需要可辩护的保留边界）。用同一套「到期即删」会把审计拖进不合规区，用同一套「永久保留」会把 SQLite 文件拖进无界增长。故分开设计。

### 2.3 增长量级估算（用于定保留周期，不是实测）

写入审计的 41 类动作全部是**离散事件**（登录、配置变更、任务生命周期、危险操作），没有轮询级噪声；`login.failed` 有指数退避 + 独立限流兜底。粗估：

- 轻量站点：≤50 条/日 → 3 年 ≈ 5.5 万行
- 常规站点（每日若干备份 + 交互）：100–300 条/日 → 3 年 ≈ 11–33 万行
- 单行按 `detail` 截断上限 2000 字符估上限 ≈ 2 KB，实测多数行远小于此（几百字节）

按 300 条/日 × 500 B ≈ **55 MB/年**。即：3 年量级在百 MB 级——**不是紧急问题，但是无界的**，且与 `/data/restic.db` 同库（备份元数据也在此），库文件变大将连带影响备份/导出/容器卷体积与 `VACUUM` 成本。

## 3. 保留策略设计

### 3.1 任务历史（改动小，主要是补入口）

| 维度 | 设计 |
|---|---|
| 保留周期 | 维持 `retention.jobs_days=90` 默认；**不改默认值**（用户可见的历史窗口已稳定） |
| 归档 | 不做（日志文件已随行清理；如需留证走审计流，任务历史不承担合规职责） |
| 自动清理 | 维持现有每日任务；**补一条**：清理前把将要删除的条数/字节数写入 `retention.cleanup` 审计 detail（已有，保持不变） |
| 手动入口 | **新增设置页「立即清理」按钮**（复用 `RetentionService.cleanup_once()`，带 `ConfirmGate`），返回本次清理报告并 toast。理由：用户改小 `retention.jobs_days` 后想立刻生效，现在只能等次日 03:40 |
| 选择性删除 | **不做单条删除**——jobs 行与 `/data/jobs/<id>.log`、SSE 游标 `last_event_id` 相互耦合，单删易留孤儿且破坏「历史连续」语义 |

### 3.2 审计日志（核心新增）

设计原则：**先可导出，再可清理；能被证明的清理才是合规的清理。**

| 维度 | 设计 | 说明 |
|---|---|---|
| **① 归档导出** | 新增 `GET /api/audit/export`（`since`/`until`/`action`/`result` 同查询参数，返回 NDJSON 或 JSON 数组，流式） | 先有导出才有资格谈清理；导出只读、不改表 |
| **② 滚动归档** | 每日维护在**删除前**把「即将超出保留期的整段」写入 `/data/audit/archive/audit-<yyyy>.jsonl`（追加，不覆盖），记 `audit.archive` 埋点 | 实现注释里承诺的「整段滚动导出后截断」，落到代码 |
| **③ 自动清理** | 新增 `retention.audit_days`（**默认 365**，与 `retention.jobs_days` 同读取口径；`<=0` = 不启用 = 永不清理） | 与 jobs 同构，fail-safe 一致 |
| **④ 清理口径** | 只删 `ts < now - audit_days` 的行；**分批**（如每轮 5000 行）走 `Database.write` 串行；删前必须已归档成功（归档失败 → 跳过本轮删除并告警） | 红线 A1（SQL 只在 repo）/ A5（写串行）/ C8（时间工具） |
| **⑤ 埋点** | 每次清理记 `audit.cleanup`（条数、时间区间、归档文件路径、字节数） | 清理这件事本身必须可审计——否则「谁删了审计」无从追责 |
| **⑥ 手动删除入口** | **不提供通用删除/清空 API 与 UI 按钮**。提供的是「立即执行保留策略」（按当前 `retention.audit_days` 跑一轮 ②+③），不是自由删除 | 与 S6 append-only 红线一致：给策略执行入口，不给任意删除能力 |
| **⑦ 保护动作** | `login.failed`、`*.delete`、`key.rotate`、`repo.rebuild` 等安全敏感动作**不受保留期清理**（或按更长下限，如与 `audit_days` 取大者 ×3） | 安全事件需要更长追溯窗口；避免「清理策略削弱取证能力」 |

### 3.3 推荐方案与取舍

**推荐：B（归档 + 365 天滚动清理 + 敏感动作豁免）**

| 方案 | 做法 | 优点 | 代价 / 风险 | 评价 |
|---|---|---|---|---|
| **A 维持现状（永久保留）** | 不动 | 零改动、零合规风险、取证能力最强 | 库无界增长；`/data` 卷与备份体积逐年抬升；`VACUUM`/导出变慢 | 短期可接受，长期不可接受 |
| **B 归档 + 按天清理（推荐）** | ②+③+④+⑤+⑦ | 有界；有可辩护的保留边界；归档保住取证；与 jobs retention 同构，心智负担低 | 需新增导出/归档/清理三段实现 + 迁移配置键；归档文件本身也要有保留边界（否则换个地方无界） | **推荐** |
| **C 按条数上限（环形截断）** | 只保留最近 N 条（如 10 万） | 实现最简单，体积绝对可控 | 「最近 N 条」的边界不可预测（突发 `login.failed` 会冲掉正常审计），**无法向审计方解释保留了多久** | 不推荐：可辩护性差 |
| **D 分表/外置（审计独立库或文件日志）** | 审计移出主库 | 主库瘦身、清理不影响业务库 | 破坏「单一 SQLite 文件」的部署假设；跨库查询与导出复杂；迁移面大 | 收益不抵成本，暂缓 |

**取舍要点**：B 的核心代价是「多一套归档文件也要设边界」。建议归档文件自身按**年份切分**并复用同一 `retention.audit_days` 的下限（例如归档保留 3 × `audit_days`，或明确写入部署文档由管理员外送冷存），否则只是把无界从一个地方搬到另一个地方。

### 3.4 对审计合规性的影响

| 影响面 | 说明 |
|---|---|
| **正向** | 明确保留期（365 天）+ 归档 = 「有定义的保留策略」本身比「永久但无管理」更容易通过审计问询；清理动作本身留痕（`audit.cleanup`），可证明「删了什么、什么时候、按什么规则」 |
| **风险 1：追溯窗口缩短** | 365 天以外的事件只能查归档文件（离线）。需同步更新 Web版PRD §12 与审计页文案（现在写的是「仅支持整段归档滚动」，应改为可操作的导出入口） |
| **风险 2：默认值的合规含义** | 若行业/客户要求 ≥1 年或 ≥3 年，365 天是下限。建议把默认值暴露到设置页并写清「改小会缩短取证窗口」，由管理员按合规要求决定 |
| **风险 3：归档文件完整性** | 归档是明文 JSONL，落 `/data` 卷；若 `/data` 本身被排除出宿主机备份（部署指南要求），归档也会丢 → 文档需提示外送冷存 |
| **不变的部分** | 审计仍 append-only：**不新增 UPDATE，不新增任意 DELETE**；新增的 DELETE 只出现在「按保留期滚动」这一条受控路径上，且经 `AuditRepo` 单一出口 |
