4. **dry_run_pending 门禁三处闭环且契约一致**（d6bf5ca/7eff049/a6a305e）：服务端 E36「无 error 且未截断」才清 0 + X6 首次成功备份清 0（绕过 UI 也解除）+ 前端 F1 截断时禁用「确认并立即首跑」，三层语义完全对齐，前端注释显式引用服务端契约；
5. **调度器工程质量高**（93f9674）：先记账后执行防崩溃重复触发、jitter 上限防护（配置写爆兜底 3600s）、reload 全量重建并清理遗留触发器、坏 cron 降级仅手动并记 WARNING、启动顺序 start→reload→catchup 有专门用例锁死；N3 裁决「prune 只判定不执行」有 `test_due_for_prune_never_submits_forget` 反向断言；

### 🟡 Suggestion（应修复或记 issue）

- **S-1 stale 预览窗口（TaskWizard.vue）**：编辑流下用户在 E36 预览成功**之后**再改 sources/excludes，`dryRunResult` 不随表单变化失效，`onSaveAndRun` 仍可基于旧预览直接提交新源集合。服务端 `update` 会重置 `dry_run_pending=1`，但 `createJob` 不受该标记拦截（只拦仪表盘 Start），X6 在首跑成功后清 0——即「预览的是 A 集合、首跑的是 B 集合」的窗口存在。风险低（预览后即改即跑），但组件里已有 `sourcesChanged` computed，建议 `onSaveAndRun` 加一道 `if (sourcesChanged.value) → 要求重新预览`（或 watch 使 `dryRunResult` 失效），三层门禁的口径就完全闭合了。
- **S-2 路由调用调度器私有方法**：`backup_tasks.py` 的 `_to_card` 直接调 `scheduler._due_for_prune(task)`。跨模块调下划线方法破坏封装（调度器重构改名会静默炸路由），建议 `SchedulerService` 公开为 `due_for_prune`（docstring 已自称「唯一调用点」，正是应该转正的信号）。
- **S-3 TaskWizard 关键门禁无前端单测**：`dryRunOk`（F1 修复点）是业务拦截核心，当前 vitest 19 例未覆盖向导（现有惯例：useJobStream/VirtualTree 等关键逻辑均有 spec）。不阻塞本批（AGENTS 未强制），建议记 issue 补齐。
- **S-4 `TaskRepo.update` 列名 f-string 插值**：`f"{key} = ?"` 的列名来自 values dict 的 key，当前唯一调用方 `TaskService.normalize` 输出固定键集，安全；但仓储层自身无列名白名单，未来新调用方误传即成注入面。与 `PolicyRepo` 既有模式一致（非本批新增债），建议后续统一加列名断言（`set(payload) <= set(_COLUMNS)` 一行即可）。
