## 0. 与「现状已支持多目的地」的区别（先破一个误解）

当前 `backup_tasks.mirror_repo_ids`（0006，C4）确实让一个任务能写多个仓库，但它与本文目标不是同一件事：

| 维度 | 现状 `mirror_repo_ids` | 本文目标 |
|---|---|---|
| 关系本质 | 任务**归属**一个主仓（URL 路径 + `X-Repo-Id`），镜像只是附属目的地 | 任务不归属任何仓；「目的地集合」是任务的一等属性 |
| 增删目的地 | 仅向导第③步多选，要求目标仓 url 与密码已配置 | 任务详情内随时增删，可含「当场新建仓库」 |
| 每仓状态 | 无独立状态（只有一个 `mirror_note` 文本） | 每仓独立的 last_result / 快照数 / 错误原因 |
| 保留策略 | **只对主仓跑 forget；镜像仓从不清理**（下文 §9.2 实证） | 逐仓 forget，最终一致 |
| 引用保护 | 只查 `backup_tasks.repo_id`（`repo_repo.py:194-216`），镜像引用不查 | 查 `task_repos` 全部引用（primary + mirror） |
| API 作用域 | 任务 API 全部挂在 `/api/repos/{repo_id}/` 下 | 任务域升为全局资源，仓库前缀降为只读视图 |

一句话：**C 方案把「仓库 = 容器、任务 = 容器里的东西」反转为「任务 = 实体、仓库 = 目的地集合」**，并顺带补掉镜像仓不清理这一既有欠账。

## 2. 现状取证（N:1 模型）

### 2.1 数据模型

```sql
-- 0002_multi_backup_tasks.sql
repo_id TEXT NOT NULL DEFAULT 'default' REFERENCES repos(id);   -- 单值，外键
CREATE INDEX idx_backup_tasks_repo ON backup_tasks(repo_id);    -- 普通索引，无 UNIQUE

-- 0006_task_mirror_repos.sql
mirror_repo_ids TEXT NOT NULL DEFAULT '[]';                     -- JSON 数组，附属目的地
```

结论：一仓多任务是**设计本意**（架构 §13 裁决 ①「同仓库下 N 个备份任务」），且被测试直接断言：`tests/test_api/test_backup_tasks.py:236-239` 在 `default` 下连建两个任务并断言列表返回两条。

### 2.2 API 作用域

- 任务域端点前缀 `/api/repos/{repo_id}/backup-tasks`（`routers/backup_tasks.py:69`），`repo_id` 存在性校验 `_require_repo`（`:78-90`）。
- 创建时**请求体不能指定仓库**：服务端强制 `values["repo_id"] = repo_id`（`:223`）；`TaskUpsertRequest` 无 `repo_id` 字段（`schemas/api_schemas.py:492-533`）。
- 前端任务 API 一律取 `ui.currentRepoId` 注入 `X-Repo-Id`（`api/backupTasks.ts:33-38`、`dependencies.py:24`）。
- 向导第③步只读展示当前仓库 URL + 连通状态，另加「必须先测试通过」硬门禁（`components/TaskWizard.vue:856-871`、`:665`）。

### 2.3 执行与清理

- 锁按 `repo_url`（`job_runner.py:228-234`），提交期内 `async with lock` 只包住「查重 + 落 job 行」，执行期互斥靠 `list_active(repo_id)` 复核（`:304-320`）——**多仓库天然并行，任务内多仓也不会死锁**。
- 调度触发一次只提交一条 backup（`scheduler.py:680-688`，`repo_id=task.repo_id`）。
- 备份成功后的镜像阶段逐仓 `restic copy`（`job_runner.py:534-539` 调用、`:773-803` 实现），失败不降级主目的地终态。
- **保留清理只作用于一个 `repo_id`**（`scheduler.py:644-650` 提交 forget）——镜像仓永远收不到 forget，这是现状欠账（§9.2）。

### 2.4 删除保护

`ReposRepo.ensure_deletable`（`repo_repo.py:194-216`）：default 禁删 + `backup_tasks` 计数 + 活跃 jobs。**镜像仓引用不在检查范围**，《删除依赖与快照可用性保护方案》§1 结论 #4 已单独登记该缺口。

## 3. 目标模型

### 3.1 术语

- **目的地（destination）**：任务的一个写入目标，由 `(task_id, repo_id, role)` 唯一确定。
- **primary**：唯一真相源。backup 在此执行；restore 默认取此仓；copy 的源。
- **mirror**：由 primary 增量复制而来（C4 语义不变），不直接承接 backup。

### 3.2 不变式（实现必须满足）

| # | 不变式 | 落地手段 |
|---|---|---|
| I1 | 每个任务**恰好一个** primary | 部分唯一索引 `ux_task_repos_primary` + 服务层校验 |
| I2 | 同一任务内同一仓库不得重复（含「mirror 指向 primary」） | 主键 `(task_id, repo_id)` 天然约束 |
| I3 | 目的地仓库必须存在且密码已配置（否则运行期必失败） | `TaskService.normalize` 校验，422 |
| I4 | 任务删除 → 目的地行级联删除；仓库删除 → 被引用则 409 | `ON DELETE CASCADE` + `ensure_deletable` 改查 `task_repos` |
| I5 | 任务 tag（`task-<id>`）全局唯一，跨仓共用同一 tag | 现有 `tag TEXT NOT NULL UNIQUE` 不动；copy 依赖它过滤 |
| I6 | 保留规则对**每个目的地**独立执行 | 逐仓提交 forget（§9） |

## 4. 语义裁决点（D1–D4，均待 owner 裁决）

| # | 问题 | 备选 | 推荐 | 理由 |
|---|---|---|---|---|
| **D1** | 一次触发怎么落到 N 个仓 | a) N 条独立 backup job；b) 单 job 内多目标；c) primary backup + 其余 copy | **c**（现状 C4 语义） | 源只扫一次、增量传输、复用现有 job/SSE/日志模型；a 让源扫描与去重计算 ×N；b 破坏「job 单仓」不变式（`jobs.repo_id NOT NULL`、SSE 事件、取消逻辑全要改） |
| **D2** | 是否允许改 primary | 允许 / 禁止 | **禁止原地改** | 改主后两仓各有历史，copy 方向失去定义。UI 只允许增删 mirror；换主 = 新建任务并迁移 |
| **D3** | API 作用域 | 继续 repo 前缀 / 新增全局 `/api/backup-tasks` | **新增全局权威 CRUD，repo 前缀降为只读视图** | 任务不再归属于某仓，继续用 repo 路径会把「归属」概念焊死。**与架构 §13 E6 冲突，须登记例外** |
| **D4** | 仓库被 mirror 引用能否删 | 允许（现状）/ 409 | **409**，复用既有错误码 `REPO_IN_USE_AS_MIRROR` | 与《删除依赖与快照可用性保护方案》§1#4 同一件事，不新造错误码 |

## 5. 数据模型与迁移

### 5.1 Expand（迁移 `0009_task_repos.sql`）

```sql
-- 0009_task_repos.sql —— 任务 × 仓库 关联（C 方案 Expand 阶段）
-- 语义：任务为主实体，仓库为目的地；role='primary' 唯一、restic backup 在此执行，
--       role='mirror' 由 C4 增量 copy 写入。旧列 repo_id / mirror_repo_ids 本阶段保留（双写）。

CREATE TABLE IF NOT EXISTS task_repos (
    task_id    INTEGER NOT NULL REFERENCES backup_tasks(id) ON DELETE CASCADE,
    repo_id    TEXT    NOT NULL REFERENCES repos(id),
    role       TEXT    NOT NULL DEFAULT 'mirror',   -- primary | mirror
    created_at TEXT    NOT NULL,
    PRIMARY KEY (task_id, repo_id)
);
CREATE INDEX IF NOT EXISTS idx_task_repos_repo ON task_repos(repo_id);
-- I1：每任务至多一个 primary（部分唯一索引；SQLite 3.8+）
CREATE UNIQUE INDEX IF NOT EXISTS ux_task_repos_primary
    ON task_repos(task_id) WHERE role = 'primary';

-- 回填①：主仓（JOIN repos 过滤历史脏 id —— 否则 foreign_keys=ON 会让迁移失败）
INSERT OR IGNORE INTO task_repos (task_id, repo_id, role, created_at)
SELECT bt.id, bt.repo_id, 'primary', strftime('%Y-%m-%dT%H:%M:%SZ','now')
FROM backup_tasks bt
JOIN repos r ON r.id = bt.repo_id;

-- 回填②：镜像仓（JSON1 json_each；剔空串、剔自指、JOIN repos 过滤已删仓库）
INSERT OR IGNORE INTO task_repos (task_id, repo_id, role, created_at)
SELECT bt.id, je.value, 'mirror', strftime('%Y-%m-%dT%H:%M:%SZ','now')
FROM backup_tasks bt, json_each(bt.mirror_repo_ids) je
JOIN repos r ON r.id = je.value
WHERE je.value <> '' AND je.value <> bt.repo_id;

PRAGMA user_version = 9;
```

> 迁移器按 `user_version` 守卫、`executescript` + 单事务执行（`db/database.py:122-145`），本脚本多语句与 `json_each` 均可用；实测 SQLite 3.53.1 支持 JSON1（§14）。

### 5.2 双写期（P1–P2）

- **唯一写入点** `TaskRepo.set_destinations(task_id, items)`：一次事务内 ①改 `task_repos` ②同步旧列 `backup_tasks.repo_id`（primary）与 `mirror_repo_ids`（mirror 列表）。
- 读路径一律先读 `task_repos`，为空时回落旧列（仅用于迁移残留，P3 删除）。
- **禁止**路由层直接写 `backup_tasks.repo_id` —— 一旦出现第二写入点立刻双源（与 E07 拒收 `repo.*` 同精神）。

### 5.3 Contract（迁移 `0010_task_repos_contract.sql`）

```sql
-- 0010_task_repos_contract.sql —— 收缩：删除旧列（前置断言见下）
```

## 9. 执行语义与清理

### 9.1 一次触发的完整链路（D1 = c）

```
scheduler._fire_backup(task)
  └─ 记账 last_run_at（任务级一次，语义不变）
  └─ submit("backup", repo_id=primary)      ← 单仓 job
        └─ restic backup → success
        └─ for each mirror: restic copy --tag task-<id>   （失败隔离、不降级主终态）
  └─ [_maybe_prune] for each destination: submit("forget", repo_id=dest)
```

### 9.2 现状欠账：镜像仓永不 forget

`forget` 的 `repo_id` 来自提交方（`scheduler.py:644-650` 只传一个），`_run_mirror_phase` 只做 copy 不做 forget。后果：**mirror 仓的快照只增不减**。本方案在 P2 修掉：对每个目的地各提交一次 forget。

一致性说明（如实标注，不假装强一致）：

- 各仓 forget **独立执行**，不做跨仓事务；
- primary 已删、mirror 仍在 → 无害（下次 copy 按 `Original` 字段跳过，不会复活）；
- mirror 已删、primary 仍在 → 下次 copy 自动补齐；
- 因此语义是**最终一致**，任一时点两仓可能短暂不同步。若需严格一致，需引入跨仓对账任务（超出本文范围）。

### 9.3 并发与限速

- 一任务多仓 = 多仓并行写（不同 `repo_url` 各持锁），吞吐提升但 IO/带宽叠加；任务级 `limit_up/down` 是**每进程**生效，不是全局配额——需在部署文档写明。
- 每日 check 维护已遍历全部仓库（架构 §6 既有），无需改。

## 10. 验收断言（DoD）

**后端**

1. 迁移双跑幂等；回填后每任务恰好 1 条 primary，mirror 数 = `json_each` 去重去自指后数量。
2. 同任务插第二条 primary → IntegrityError（部分唯一索引生效）。
3. 仓库被 mirror 引用时 `DELETE /api/repos/{id}` → 409 `REPO_IN_USE_AS_MIRROR`；`purge_disk=true` 时数据零损失（校验先于 rmtree）。
4. **同仓多任务仍然允许**（本方案不引入独占——与「强制 1:1」路线互斥，不要混用）。
5. 一次调度触发：1 条 backup（primary）+ N 段 copy 日志；`forget` 对 N 个目的地各 1 条 job。
6. 删除任务 → `task_repos` 级联清空，`jobs` 行保留解绑（现状语义）。
7. 改 primary → 422；目的地含未配置密码仓 → 422。
8. `verify_redlines.sh` 全绿；新端点挂 `require_session` + Origin 同源；`task.destinations_update` 入审计。

**前端**

9. 向导配 1 primary + 2 mirror 全链路成功；目的地含已删仓库时给可操作提示。
10. 卡片矩阵展示 3 个目的地状态；`pnpm test`（i18n parity / naive-imports）、typecheck、build 全绿。
